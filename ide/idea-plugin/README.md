# Плагин IntelliJ IDEA для wdl

Теперь также поддерживает Run-конфигурации **wdl**: выбор файла/каталога,
рабочей директории, параметров интерпретатора и аргументов скрипта, запуск из
контекстного меню и зелёной кнопкой. Подробности: [установка и запуск](../../docs/installation.md).

Запуск и анализ LSP используют один корень импортов — каталог открытого проекта
IDEA. Плагин передаёт его в CLI через `--project-root`, а в LSP — как workspace
и `wdl.sourceRoots`. Каталог запускаемого файла и поле «Рабочий каталог» этот
корень не меняют. Правило действует и для сохранённых Run-конфигураций;
ручной `--project-root` из параметров wdl нужно удалить.

Например, при открытом репозитории `wdlanguage` файл
`examples/testing/errors.wdl` должен импортировать библиотеку как
`import examples.testing.lib.test as t`. Если открыть `examples/testing` отдельным
проектом IDEA, тот же модуль называется `lib.test`.

Из корня: `./gradlew prepareWdl installWdl`; готовый ZIP установите через
**Install Plugin from Disk**. `installWdl` настраивает команды CLI/LSP,
`prepareWdl` собирает и проверяет модули и плагин.

Тонкий плагин: запускает интерпретатор `wdl` и языковой сервер
`wdl-lsp`. Подсветка, ошибки, дополнение, переход к объявлению, поиск употреблений
и структура файла приходят по протоколу — из `wdl-tools`, того же кода, которым
пользуются `wdl --catalog` и (в будущем) редактор внутри приложения.

## Требования

* **Платная IDE JetBrains** — IntelliJ IDEA Ultimate, PyCharm Professional и другие.
  Клиента LSP в Community-сборках нет вовсе: это API платформы, доступное только
  в коммерческих продуктах. Отсюда `com.intellij.modules.ultimate` в `plugin.xml`.
* IntelliJ IDEA **2025.3** или новее (`sinceBuild = 253`). Более ранние сборки
  тоже умеют LSP, но API платформы там менялось; понижать планку стоит,
  только проверив на конкретной версии.
* JDK 21 — тот же, что у самого языка.

## Сборка

Сборка отдельная: корневой `./gradlew build` её не трогает и дистрибутив IDE
не качает. Обёртка Gradle берётся из корня репозитория.

```bash
./gradlew :wdl-lsp:installDist            # сначала сам сервер
./gradlew :wdl-dap:installDist            # и адаптер отладки
./gradlew -p ide/idea-plugin buildPlugin  # затем плагин
```

Готовый архив — `ide/idea-plugin/build/distributions/wdl-idea-plugin-0.1.1.zip`;
ставится через **Settings → Plugins → ⚙ → Install Plugin from Disk**.

Запустить IDE с плагином, ничего не устанавливая:

```bash
./gradlew -p ide/idea-plugin runIde
```

Первая сборка скачивает дистрибутив IDE (около двух гигабайт) — это нормально
и происходит один раз.

## Где плагин ищет сервер

По порядку, от явного к угаданному:

1. системное свойство `-Dwdl.lsp.home=<каталог>`;
2. переменная окружения `WDL_LSP_HOME=<каталог>`;
3. `wdl-lsp/build/install/wdl-lsp/bin/wdl-lsp` внутри открытого проекта —
   это работает само, когда открыт сам репозиторий wdl;
4. `wdl-lsp` в `PATH`.

Не нашёлся — файл остаётся обычным текстом, а в журнал IDE (`Help → Show Log`)
пишется строка о том, чего не хватило. Окно с ошибкой на каждый открытый файл
было бы хуже.

Сервер намеренно не лежит внутри плагина: он часть дистрибутива wdl и обязан быть
той же версии, что и движок, которым скрипт будет выполнен. Плагин со своей копией
однажды подскажет имя, которого в запуске уже нет.

## Отладка

Кнопка **Отладить** запускает скрипт под адаптером `wdl-dap` и открывает обычный
сеанс отладки IDEA. Работают точки останова в поле редактора, шаги (`into`,
`over`, `out`), «Выполнить до курсора», пауза, панель кадров, панели переменных
и вычисление выражения в кадре — в поле «Вычислить», в «Watches» и по наведению.
Печать скрипта идёт в консоль сеанса. Связывает её с процессом сам плагин —
в `WdlDebugProcess.createConsole()`: платформа этого не делает, `XDebugProcess`
консоль только **создаёт**, и без явного `attachToProcess` вывод уходил бы в никуда.
Строки, напечатанные раньше, чем консоль появилась, ждут в `AdapterProcess`
и попадают на экран тем же порядком.

Скрипт при этом выполняет **сам адаптер**: движок, отладчик и запуск обязаны быть
одним процессом, иначе точку останова некуда ставить, а кадры не у кого спрашивать.
Поэтому под «Отладить» обычная командная строка `wdl` не строится вовсе, а поля
конфигурации (файл, рабочий каталог, аргументы) уезжают адаптеру запросом `launch`.
Из параметров интерпретатора переносятся только пределы (`--max-steps`,
`--timeout`, `--max-threads`) — остальные к сеансу отладки отношения не имеют,
и о них плагин говорит отдельным сообщением, а не выбрасывает молча.

Точка, поставленная на комментарий или на пустую строку, **уезжает вниз**,
к ближайшей инструкции: где в скрипте инструкции, знает дерево файла на стороне
адаптера, и он отвечает той строкой, на которой точка встала на самом деле.
Строке, ниже которой инструкций нет вовсе, точка помечается недействительной
с объяснением.

Панелей переменных у кадра две: **«Локальные»** — имена, заведённые этой областью,
**«Видимые»** — всё, что кадру видно снаружи, включая параметры вызова, имена файла
и корневую область с библиотекой. Вторая свёрнута: она стоит обхода всех внешних
областей. Свойства (`a.size`) в панель не попадают — за именем свойства стоит вызов,
а выполнять код скрипта на каждый шаг отладчика нельзя; спросить их можно
вычислением.

В окне точек останова есть пункт **«Ошибки выполнения wdl»** — с ним поток встаёт
там, где ошибка случилась, до раскрутки. Выключен по умолчанию: поток встаёт
на любой ошибке, а ошибка внутри `try` — обычное течение скрипта.

Адаптер ищется так же, как сервер: `-Dwdl.dap.home`, `WDL_DAP_HOME`,
`wdl-dap/build/install/wdl-dap/bin/wdl-dap` внутри открытого проекта, затем `PATH`.
Не нашёлся — сеанс не начнётся, и IDEA скажет, чего не хватило. Подробности
протокола и полей запуска — [docs/debugging.md](../../docs/debugging.md).

## Профилирование

Рядом с «Запустить» и «Отладить» есть третья кнопка — **Профилировать**. Она
запускает ту же конфигурацию, дописывая `--profile-out` во временный файл, и по
окончании показывает отчёт в окне **wdl Profile** внизу.

Профилирование — действие, а не настройка конфигурации: одна и та же конфигурация
запускается обычным способом и профилируется, и забыть снятый флажок негде.

В окне две вкладки:

* **Горячие** — таблица «что · вызовов · всего · сам · макс», отсортированная
  по «сам». Двойной щелчок или Enter открывают объявление.
* **Дерево вызовов** — кто кого звал; ветки разворачиваются по мере надобности,
  а повтор функции на своём же пути помечается «рекурсия» и дальше не растёт.

**«Всего» и «сам» — разные числа.** «Всего» считает время вместе со всем, что
вызов позвал изнутри; «сам» — работу самой функции. Функция-раздатчик имеет
большое «всего» и почти нулевое «сам», и править надо не её. Подробно об этом —
[docs/profiling.md](../../docs/profiling.md).

Фильтр по имени и переключатель «встроенные» убирают из таблицы `println` и члены
значений: на длинном скрипте своя функция иначе теряется среди чужих.

Переключатель **«подсказки в редакторе»** дописывает числа к строке объявления
(«21891 вызов · 94,74 мс сам»). Выключен по умолчанию: подсказки, оставшиеся
от вчерашнего прогона, врут молча.

Отчёт, снятый где-то ещё — например, `wdl --profile-out profile.json` в сборке, —
открывается через **Tools → Открыть профиль wdl…**.

Чего ждать не стоит:

* **Под «Профилировать» скрипт идёт медленнее**, чем под «Запустить»: профиль
  считает каждый вызов. Мерить время секундомером надо обычным запуском.
* Отчёт появляется, **когда процесс закончился**. Скрипт с окнами (`sys.gui`)
  живёт, пока окна открыты, — профиль придёт после их закрытия.
* Скрипт, не дошедший до выполнения (ошибка разбора), даёт пустой профиль:
  окно скажет об этом словами.

## Что уже работает и чего ещё нет

Работает: диагностика, дополнение имён (включая встроенные, `std` и модули `sys.*`),
подсказка по наведению, переход к объявлению внутри файла, поиск употреблений,
структура файла, семантическая подсветка, профилирование, отладка.

В отладке ещё нет: условных точек, точек по счёту попаданий, точек на функцию,
изменения переменной из панели и обратного шага — этого нет в самом отладчике,
а не в протоколе.

Ещё нет: форматирования, переименования, инспекций, перехода между файлами
по `import` и членов после точки (кроме имён модуля). Сервер их и не обещает —
возможность объявляется только после того, как сделана.
