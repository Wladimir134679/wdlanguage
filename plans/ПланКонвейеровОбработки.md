# План: конвейеры обработки значений

Замысел — дать языку цепочку обработки: «взять данные, отфильтровать, преобразовать,
свернуть» одним читаемым выражением, как это делают Java Stream, LINQ, Kotlin Sequence
и Elixir `|>`. Документ **проектный**: первый этап уже сделан, остальные описаны
вариантами со стоимостью и решением, какой брать следующим.

Отметки: `[ ]` не начато, `[~]` в работе, `[x]` сделано и проверено сборкой.

---

## Этап 0. Жадные члены массива — `[x]` сделано

Массив умеет обработку сам, каждая стадия отдаёт обычный массив:

```wdl
prices = [120, 80, 200, 50]

println(prices.filter(def(p) => p >= 100).map(def(p) => p * 2).sum)   // 640
println(prices.reduce(def(total, p) => total + p))                    // 450
println(prices.find(def(p) => p < 100))                               // 80
println(prices.any(def(p) => p > 150), " ", prices.all(def(p) => p > 150))
prices.each(def(p) => println("цена: ", p))
```

Что получилось — в [docs/members.md](../docs/members.md#массив), рабочий пример —
в [examples/members.wdl](../examples/members.wdl).

Решения этапа, которые дальше считаются принятыми:

1. **Обработчику приходит один аргумент — элемент.** Правило «второй аргумент даётся,
   если функция его принимает» сделало бы поведение зависимым от чужой сигнатуры
   и разъехалось бы на `*args` (принимает что угодно) и на декорированной функции,
   у которой сигнатура вообще чужая. Индекс даёт `for`.
2. **`sum`, `min`, `max` — свойства**, потому что аргументов нет, а ответ — о массиве,
   каким он виден сейчас. Считают они тем же, чем считает текст скрипта: `sum` — тем же
   `+` (класс с `` def `+` `` складывается своим сложением), `min`/`max` — тем же
   сравнением, что `<` и `sorted`. Отдельной арифметики «только для чисел» здесь нет
   по той же причине, по какой её нет у сортировки.
3. **Работа идёт по снимку** (`ArrayValue.items()` его и отдаёт), поэтому обработчик,
   дописывающий в тот же массив, перебор не зацикливает.
4. **Своей точки проверки лимитов нет**: виток этих циклов — вызов функции скрипта,
   а его уже считает `Run.checkpoint` в `UserFunction.body`. Второй счётчик дал бы
   двойной учёт одной работы ([docs/limits.md](../docs/limits.md)).

**Чего этап не даёт.** Промежуточный массив на каждую стадию; нет короткого замыкания
сквозь стадии (`a.map(тяжёлое).find(...)` считает всё); нет бесконечных и внешних
источников (строки файла, ответы сети); ничего, кроме массива, в цепочку не встаёт.

Для скриптов на тысячи элементов этого достаточно, и следующий этап нужен не «потому
что у Java есть Stream», а под конкретную из трёх нехваток выше.

---

## Что вообще выбирается

Три оси, и они независимы:

| Ось | Крайности |
|---|---|
| **Ленивость** | стадия считает всё сразу ↔ стадия только описывает работу, считает терминал |
| **Форма записи** | цепочка членов `a.f().g()` ↔ оператор конвейера `a \|> f() \|> g()` |
| **Источник** | только массив ↔ любое, что умеет отдавать элементы по одному |

Этап 0 — «жадно, цепочкой членов, только массив». Дальше каждый вариант двигает
ровно одну ось, и брать их можно по отдельности.

---

## Вариант A. Оператор конвейера `|>`

`x |> f(a)` — это `f(x, a)`, ничего больше. Ось: **форма записи**.

```wdl
// вложенность разворачивается в порядок чтения
report = topN(withTotals(byRegion(orders, "EU")), 10)
report = orders |> byRegion("EU") |> withTotals |> topN(10)
```

С [дескрипторами типов](../docs/types.md) он работает с массивами сразу, без единой
новой функции: член типа и так виден функцией от получателя.

```wdl
nums |> Array.filter(def(n) => n > 0) |> Array.sum
```

**Чем хорош.** Не заводит ни типа, ни понятия «поток»: конвейер получают строки,
объекты, экземпляры, значения модулей — всё. Своя функция встаёт в цепочку наравне
со встроенным членом, а сегодня своя функция цепочку рвёт (`total(a.filter(f))`).
Ортогонален ленивости: с ленивой последовательностью он тоже будет работать.

**Чем плох.** Ленивость не появляется, промежуточные массивы остаются. Массивам он
даёт меньше, чем кажется: `a.filter(f).sum` уже короче, чем `a |> Array.filter(f) |> Array.sum`.
Настоящая польза — на своих функциях и на не-массивах.

**Цена.** Токен `|>` в `TokenType`, строка в `parser/Operators` (приоритет ниже всех,
кроме тернарного; левая ассоциативность), узел или переписывание в `CallExpr` при
разборе, ветка в `Interpreter`, документация. Ядро, типы значений и члены не трогаются.

**Что решить до реализации:**

* **куда встаёт значение** — всегда первым аргументом, или есть дырка `x |> f(a, _, b)`.
  Дырка гибче, но `_` уже занят [параметром-дыркой](../docs/functions.md), и одно
  и то же подчёркивание значило бы две разные вещи;
* **`x |> f` без скобок** — законно ли (предлагается: да, это `f(x)`);
* **что справа вообще разрешено** — только вызов и имя, или любое выражение,
  дающее функцию (`x |> handlers[0]()`);
* **жадность лексера**: `a | > b` и `a |> b` обязаны разбираться по-разному, а таблица
  операторов сейчас строится из `TokenType.text()` — проверить выбор длинного варианта.

## Вариант B. Короткая лямбда

Не про потоки вовсе, но по влиянию на читаемость цепочки — самое сильное изменение
из всех перечисленных, поэтому стоит здесь.

```wdl
prices.filter(def(p) => p >= 100).map(def(p) => p * 2)      // сегодня
prices.filter(p -> p >= 100).map(p -> p * 2)                // B1
prices.filter(\p => p >= 100).map(\p => p * 2)              // B2
prices.filter(it >= 100).map(it * 2)                        // B3 — неявный параметр
```

**B1 `param -> выражение`.** Токен `->` **уже лексится** (`TokenType.ARROW`), а парсер
его сегодня не ждёт нигде — имя свободно целиком. Читается как в Java и Kotlin.
Вопросы: скобки для нескольких параметров (`(acc, n) -> acc + n`) и конфликт с
`a -> b` в позиции выражения там, где ждали вычитание с унарным минусом (`a - >`
не бывает, так что конфликта, похоже, нет — проверить лексером).

**B2 `\p => тело`.** Обратная косая свободна, `=>` уже значит «тело-выражение»,
то есть новое здесь только начало записи. Выглядит инородно.

**B3 неявный параметр.** Короче всего, но вводит невидимое имя и ломается на вложенных
цепочках (`it` внутри `it`), а язык обещает, что имя существует с той строки, где его
завели. Скорее нет.

**Цена B1.** Разбор: в позиции выражения имя (или скобочный список имён) плюс `->`
даёт `FunctionExpr` с `BodyStyle.ARROW` — тот же узел, что у `def(p) => ...`, поэтому
ни интерпретатор, ни посетители, ни `Nodes.children` не меняются. Отдельный вопрос —
`AstDumper` и форматтер: стиль записи придётся хранить, как уже хранится `BodyStyle`.

## Вариант C. Ленивая последовательность `Seq` новым типом значения

Ось: **ленивость**. Стадии описывают работу, считает терминал.

```wdl
first10 = orders.seq
    .filter(def(o) => o.paid)
    .map(def(o) => o.total)
    .take(10)
    .array          // терминал: здесь и происходит вся работа
```

**Чем хорош.** Один проход вместо N, короткое замыкание бесплатно (`find`, `any`,
`take` останавливают источник), а бесконечный источник
(`seq.iterate(1, def(n) => n + 1)`) становится законным.

**Чем плох — и это главное.** Новый `ValueType` тянет за собой ответы на вопросы,
которых у ленивого значения честно нет: что печатает `println(s)` (обойти источник
ради печати — побочный эффект в самом безобидном месте), чему равно `len(s)`, что
пишет JSON, что делает `for (x in s)`, как ведёт себя `s == s`. Плюс по рецепту
«Тип значения» из [CLAUDE.md](../CLAUDE.md) — правки во всех `switch` проекта: ядро,
`bridge.Marshal`, `wdl-tools`, DAP, LSP. И отдельно: **ленивость делает порядок
побочных эффектов неочевидным**, а язык до сих пор обещал обратное — «имя существует
с той строки, где его завели», «причина изменения написана в тексте».

**Цена.** Самая большая из всех вариантов, и она размазана по всем модулям.

## Вариант D. Ленивая последовательность классом в `wdl-stdlib`

То же самое, но без нового типа значения: `Seq` — нативный класс
([bridge/NativeClass](../docs/embedding.md)), для языка это обычный экземпляр.

```wdl
import sys.seq

first10 = seq.of(orders)
    .filter(def(o) => o.paid)
    .map(def(o) => o.total)
    .take(10)
    .array()
```

**Чем хорош.** Ядро не трогается вовсе; `display()`, равенство и JSON решаются как
у любого экземпляра; развивать можно быстро, ломая только свой модуль. Параллельная
стадия (`.parallel(4)`) ложится на `sys.thread` естественно и остаётся в том же слое.
Источником может стать что угодно — `sys.io` даёт построчный поток файла вместо чтения
целиком, `sys.net.http` — постраничный ответ.

**Чем плох.** Нужен `import`; `for (x in s)` не работает, пока нет варианта E;
имена стадий дублируют члены массива, и на массиве их будет две штуки — `a.map(f)`
жадный и `a.seq.map(f)` ленивый (это честно, но объяснять придётся).

**Цена.** Модуль в `wdl-stdlib` по рецепту «Встроенный модуль», ноль правок в ядре.

## Вариант E. Протокол перебора

Ось: **источник**. `for (x in v)` сегодня — `switch` по типам значения в
`Interpreter.visitForEach`: массив, строка, объект, диапазон. Протокол снимает это
ограничение: значение, умеющее отдавать элементы по одному, годится в `for`, в
раскрытие `[*v]`, в `in` и в любой источник цепочки.

```wdl
class Pages(url) {
    def iterator() => ...      // трейт Iterable
}

for (page in new Pages(address)) { ... }
```

**Чем хорош.** Это фундамент, а не украшение: после него вариант D становится полным
(ленивый `Seq` перебирается `for`), а класс приложения встаёт в язык наравне
со встроенными контейнерами.

**Чем плох.** Решений много и все неприятные: что считать исчерпанием, как закрывать
источник при `break` (`use`/`Closeable` уже есть — связать с ними), что делать
с ошибкой в середине перебора, попадает ли протокол в `len` и в `in`. И горячий путь
`for` по массиву обязан остаться прежним — протокол спрашивается только там, где
`switch` сегодня бросает ошибку (то же правило, что у перегрузки операторов: ядро
важнее, член спрашивается на запасном пути).

**Цена.** Средняя в ядре, но затрагивает самую горячую конструкцию языка.

---

## Вариант F. Запросный синтаксис (LINQ)

`from o in orders where o.paid select o.total` — **отвергается**. Это второй способ
записать то, что уже записывается выражением, с собственными правилами области
видимости и собственным разделом в каждом документе. Язык держится на «одно понятие —
одна запись».

## Порядок, который предлагается

1. **`[x]` Этап 0** — жадные члены массива. Закрывает подавляющее большинство скриптов.
2. **`[ ]` Вариант B1** — короткая лямбда `p -> p * 2`. Дешевле всех остальных,
   а читаемость цепочек поднимает сильнее, чем любая ленивость: сегодня половину
   строки занимает слово `def`.
3. **`[ ]` Вариант A** — оператор `|>`. Даёт цепочку своим функциям и не-массивам;
   ядро не трогает.
4. **`[ ]` Вариант E** — протокол перебора. Берётся тогда, когда появится источник,
   который нельзя materialise в массив: большой файл, страничный ответ сети.
5. **`[ ]` Вариант D** — `Seq` в stdlib поверх протокола. Ленивость, короткое замыкание,
   `parallel` на `sys.thread`.
6. **Вариант C** — не берётся: всё, ради чего заводился бы новый тип значения, даёт
   пара E + D, а вопросы «что печатает ленивое значение» остаются нерешаемыми
   в любом порядке.

Пункты 2 и 3 независимы: любой можно взять первым и остановиться на нём.

## Открытые вопросы, общие для всех вариантов

* **Дублирование имён.** `a.map(f)` жадный и `a.seq.map(f)` ленивый — одно имя, два
  поведения. Либо разные имена стадий, либо честно объяснённая пара (как `sorted`
  и `sort()` сегодня).
* **Побочные эффекты и ленивость.** `each` в середине ленивой цепочки — когда он
  сработает и сработает ли вообще. Простейший ответ: ленивая цепочка `each`
  не поддерживает вовсе, только терминал.
* **Лимиты и профиль.** Ленивая стадия не должна прятать работу от `Run.checkpoint`:
  счёт остаётся на вызовах функций скрипта, и это работает само.
* **Потоки.** Ленивая последовательность, перебираемая из двух потоков, — либо явный
  запрет (одноразовый источник, как Java Stream), либо конкурентный источник; молча
  оставлять нельзя, [правило ядра](../docs/threads.md) требует ответа.
