# План: ленивые потоки данных — модуль `sys.streams`

Замысел — дать языку конвейер, который **не собирает промежуточных массивов и не
считает лишнего**: `streams.lines(path).filter(p).first()` читает файл до первой
подходящей строки и останавливается. Всё это живёт отдельным модулем `wdl-stdlib`;
в ядре — одна правка, и та про лимиты.

Документ **проектный**: описывает решение, его причину и порядок работ. Примеры
будущего API в нём, в отличие от `docs/`, ещё не выполняются.

Продолжает и заменяет `ПланКонвейеровОбработки.md` — его вариант D (ленивый класс
в stdlib) плюс вариант E (протокол перебора) отдельным этапом. Оттуда же берутся
как принятые решения этапа 0 (жадные члены массива): обработчику приходит один
аргумент, работа идёт по снимку, своей точки проверки лимитов у витка нет.
Вариант A (оператор `|>`) этим планом не закрывается и остаётся независимым —
он про форму записи, а не про ленивость.

Отметки: `[ ]` не начато, `[~]` в работе, `[x]` сделано и проверено сборкой.

---

## Зачем, если у массива уже есть `map` и `filter`

Есть, и они закрывают подавляющее большинство скриптов:

```wdl
println(prices.filter(p => p >= 100).map(p => p * 2))
```

Поэтому поток заводится **не вместо этого**, иначе в языке появится вторая запись
для того же самого — ровно то, чего проект избегает («`=>` не заменяет `def`,
а забирает у него одну нишу»). Ниша потока — четыре случая, которых массив
не даёт и дать не может:

1. **Короткое замыкание сквозь стадии.** `a.map(heavy).find(p)` сегодня считает
   `heavy` для всех элементов; поток посчитает до первого совпадения.
2. **Источник, которого нет в памяти.** Строки большого файла, ответы сети,
   `th.channel`, бесконечная последовательность.
3. **Отсутствие промежуточных копий.** `a.filter(f).map(g)` строит сегодня два
   `ArrayList`; у потока их ноль.
4. **Конкурентная обработка.** У массива её нет и быть не должно.

Отсюда граница, которая пойдёт в документацию дословно:

> **Массив отвечает на «преобразуй эти данные». Поток — на «протяни данные через
> конвейер, не собирая их».**

Скрипту на тысячу элементов поток не нужен, и предлагать его там не надо.

## Решения этого плана

### 1. Поток — нативный класс в `wdl-stdlib`, а не тип значения

`Stream` собирается построителем `bridge/NativeClass`, состояние конвейера лежит
в `NativeInstance.state()`. Для интерпретатора это обычный `ClassValue`: `is`
работает, `use` работает, `println` печатает как экземпляр.

Новый `ValueType` не заводится — по причине, записанной ещё в предыдущем плане:
у ленивого значения честно нет ответов на вопросы, которые тип обязан иметь.
Что печатает `println(s)` — обойти источник ради печати значит устроить побочный
эффект в самом безобидном месте. Чему равно `len(s)`, что пишет JSON, чему равно
`s == s`. Плюс по рецепту «Тип значения» из `CLAUDE.md` — правки во всех `switch`
проекта: ядро, `bridge.Marshal`, `wdl-tools`, DAP, LSP.

Написать поток на самом wdl (лямбды позволяют — замыкание на функцию-источник)
тоже не годится: источники файла, сокета и канала на wdl не пишутся, а каждая
стадия стала бы вызовом функции скрипта с полным `checkpoint` и записью профиля.
Как пример выразительности языка такой класс хорош, как реализация — нет.

### 2. Модель — вытягивание (pull), а не проталкивание (push)

Java выбрала push: `Sink.accept` проталкивает элемент вниз по цепочке, короткое
замыкание — флагом `cancellationRequested`. Это быстро (один обход на весь
конвейер, JIT склеивает цепочку) и **плохо составляется**: `zip` двух потоков
в push-модели не выражается вовсе — отсюда его отсутствие в Java до сих пор.

Здесь берётся pull: у стадии есть `next()`, и она сама тянет из предыдущей.

* **`zip`, `merge`, `chunked`, `windowed` получаются даром** — то, за чем в Java
  ходят в стороннюю библиотеку.
* **Протокол перебора ложится один в один**: `for (item in stream)` — это тот же
  `next()` до исчерпания (этап 5).
* **Цена pull — виртуальный вызов на элемент на стадию.** На фоне вызова функции
  скрипта (`UserFunction.body` с кадром, `checkpoint` и профилем) это шум. Push
  выигрывает там, где стадия дешевле вызова, а здесь стадия и есть вызов.

### 3. Имя: модуль `sys.streams`, класс `Stream`, член массива `.stream()`

```wdl
import sys.streams as streams

streams.lines(path).map(l => l.trim).filter(l => l != "").count()
[1, 2, 3].stream().map(x => x * 2).list()
```

Член `stream()` массиву ставит сам модуль — `Module.Builder.members(ValueType, MemberSet)`
это уже умеет. Без `import` члена нет, ядро не меняется, цена нулевая.

Имя модуля во множественном числе, в отличие от `sys/thread` и `sys/net/socket`.
Пока модуль не выпущен, единообразие стоит одну строку в `Sys.registry()` — если
захочется `sys/stream`, менять здесь.

### 4. `io.Stream` переименовывается в `io.Handle`

Имя `Stream` в стандартной библиотеке занято: `sys.io` отдаёт `Stream`, `Reader`
и `Writer`, где `Stream` — общий предок открытых файлов. Два разных `Stream`
с разным смыслом в одной стандартной библиотеке — гарантированная путаница
в документации, в подсказках редактора и в каталоге имён.

Переименовывается **io-шный**, а не новый, и вот почему: у нового имя единственно
верное (это и есть поток данных, так его зовут во всех языках), а у io-шного —
случайное. Он не поток в смысле конвейера, он **дескриптор открытого файла**,
и так он и описан в собственном javadoc: «дескриптор держится, пока не позовут
`close()`». `Handle` называет ровно это.

Отвергнутые варианты: `Resource` — слишком общо, «ресурс» уже значит `Closeable`
и участника `use`; `Descriptor` — длинно и отдаёт номером в таблице ОС;
`Channel` — занято `th.Channel`; `IoStream` — тавтология внутри `io.`.

Java-класс `stdlib/Streams.java` переименовывается в `Handles.java` тем же
движением: имя `Streams` нужно новому модулю.

### 5. Поток одноразовый

Второе терминальное действие — ошибка скрипта, а не тихий пустой результат.
Текст называет и причину, и выход:

```
поток уже пройден: он читается один раз.
        Если результат нужен дважды, соберите его: 'items = s.list()'
```

### 6. Источник по массиву берёт снимок

`streams.of(a)` фиксирует состав на входе — `ArrayValue.items()` и так отдаёт
снимок, и это ровно то решение, что уже принято для жадных членов. Иначе поток,
собранный сейчас и пройденный через десять строк, отвечал бы на вопрос «какие
данные», заданный в другой момент, — а ленивость и без того делает порядок работы
менее очевидным, чем у массива.

### 7. У потока нет свойств, только методы

Правило `docs/members.md` — «устареет ли ответ». `s.count` свойством соврало бы
дважды: оно потребляет поток и зависит от источника, который живёт снаружи.

### 8. Барьеры называются барьерами

`sorted`, `distinct`, `reversed` вынуждены прочитать вход целиком. Это не дефект,
но на бесконечном источнике они висят, и в документации это пишется прямо, рядом
с самими операциями, а не в разделе «ограничения» в конце.

### 9. Ресурс закрывается каскадом

`Stream` подмешивает `Closeable` из прелюдии, `close()` идёт вверх по стадиям
до источника. Терминальная операция закрывает сама — иначе `lines(path).first()`
оставит дескриптор. `use (s = streams.lines(path)) { ... }` работает без единой
правки: `use` смотрит на трейт, а не на тип. Незакрытые источники держит реестр
модуля и отпускает `.onClose`, как это делает `sys.gui`.

### 10. Профиль и метрики не трогаются

Новой точки съёма профиля **не заводится**: стадия — не шаг скрипта, а вызовы
обработчиков уже считаются в `UserFunction.body`. Второй счётчик развёл бы профиль
с лимитами в ответе на «сколько работы сделано» — та же причина, по которой его
нет у жадных членов массива. В `metrics/Stage` тоже ничего не добавляется: там
этапы конвейера компиляции, а не выполнения.

### 11. Конкурентность — `mapConcurrent`, а не `parallel()`

`.parallel()` в модели Java требует делимого источника, ассоциативного слияния
и разговора про порядок — то есть половины машинерии `Spliterator`, — а выигрыш
даёт на больших вычислительных объёмах, которых у скрипта обычно нет. И он молча
ломается о побочные эффекты, что для скриптового языка хуже, чем для Java.

Берётся явная операция — та, ради которой это вообще нужно:

```wdl
urls.stream().mapConcurrent(8, u => http.get(u).text).list()
```

Она ложится на то, что уже есть: пул берёт фабрику потоков у `ScriptThreads.reserve`,
квота считается, закрытие запуска их останавливает. Порядок результатов сохраняется,
обещание языка про атомарность не трогается.

## Чего плану не хватает от ядра

### Шаг, доступный библиотеке — блокирующий пункт

`Run.checkpoint(Span)` объявлен без модификатора (`wdl-core/.../runtime/Run.java`),
зовут его пять мест, все внутри `ru.wds.wdl.runtime`. Библиотека в `wdl-stdlib`
отметить шаг не может.

Пока каждый виток конвейера — вызов функции скрипта, счёт идёт сам:
`Callback.call` → `FunctionValue.call` → `UserFunction.body` → `checkpoint`.
Но конвейер без функций скрипта существует и пишется естественно:

```wdl
streams.repeat(1).count()                    // цикл целиком внутри Java
streams.iterate(1, x => x + 1).skip(1000000000).first()
```

Ни `maxSteps`, ни `maxTime` тут не сработают: мягкая проверка дедлайна живёт
в `checkpoint`, а сторож умеет только `interrupt`, которого голый цикл не заметит.
Это ровно та дыра, ради закрытия которой лимиты и заводились — «зациклиться
в обход этих точек нельзя».

Предлагается **`CallContext.step(Span)` с `default` no-op**, реализуемый
`ExecutionContext` через `run().checkpoint(span)`. Так граница «значения
не зависят от того, кто их выполняет» остаётся целой, а контекст без запуска
(тест, собирающий вывод в строку) по-прежнему реализуется одной лямбдой.
Открыть сам `checkpoint` проще, но тянет `runtime.Run` в подпись библиотеки.

Зовёт его **источник**, на каждый выданный элемент — там, где поток делает шаг.
Стадии не зовут: у них шага нет, элемент им дал источник.

### Протокол перебора — этап 5, не блокирующий

`visitForEach` перечисляет четыре типа и заканчивается отказом «перебрать можно
массив, строку, объект или диапазон». Значит `for (line in streams.lines(path))`
не заработает, и придётся писать `.each(line => ...)`, где нет ни `break`,
ни `continue`, ни `return` наружу. Для построчного чтения это заметная потеря:
главный сценарий «читаю и выхожу на нужной строке» просится именно в `for`.

Расширение — одна ветка на запасном пути (горячий путь по массиву не трогается,
то же правило, что у перегрузки операторов). Полезно не только потоку: сегодня
и класс на wdl в `for` не встаёт. Но это правка ядра со своими решениями —
что считать исчерпанием, как закрывать источник при `break`, попадает ли протокол
в `len` и в `in`, — и она заслуживает своего плана.

## API

```wdl
import sys.streams as streams

// источники
streams.of(array)                  // снимок массива
streams.of(channel)                // из th.channel
streams.range(1, 100)              // из диапазона, границы включительны
streams.iterate(1, x => x * 2)     // бесконечный
streams.repeat(value)              // бесконечный
streams.lines(path)                // ленивое чтение файла, Closeable
streams.concat(a, b)               // склейка
streams.empty()
array.stream()                     // член массива, ставит модуль

// промежуточные — ленивые, отдают Stream
.map(f)   .filter(p)   .flatMap(f)   .peek(f)
.limit(n) .skip(n)
.takeWhile(p) .dropWhile(p)
.zip(other)  .chunked(n)  .windowed(n)
.distinct()  .sorted()  .sorted(by)         // барьеры: читают вход целиком
.mapConcurrent(n, f)                        // порядок сохраняется

// терминальные — здесь происходит работа
.list()  .object(byKey, byValue)
.each(f) .reduce(f) .reduce(init, f)
.count() .sum() .min() .max()
.first() .find(p) .any(p) .all(p) .none(p)
.join(sep)
.close()                                     // Closeable, обычно зовёт use
```

Читается это так:

```wdl
use (s = streams.lines("access.log")) {
    top = s.filter(l => l.contains(" 500 "))
           .map(l => l.split(" ")[0])
           .limit(100)
           .list()
}
```

## Устройство

Источник и стадия — один интерфейс, стадия декорирует предыдущую. `null` признаком
конца безопасен: элемент потока — всегда `Value` (в худшем случае `NullValue.NULL`),
Java-`null` в значениях не ходит, поэтому коробки на элемент не нужно.

```java
/** Звено конвейера: следующий элемент или null, когда кончилось. */
interface Source extends AutoCloseable {
    Value next();
    @Override default void close() { }
}

record MapStage(Source up, Callback f) implements Source {
    public Value next() {
        Value v = up.next();
        return v == null ? null : f.call(v);
    }
    public void close() { up.close(); }
}

record FilterStage(Source up, Callback p) implements Source {
    public Value next() {
        for (Value v = up.next(); v != null; v = up.next()) {
            if (p.call(v).isTruthy()) {
                return v;
            }
        }
        return null;
    }
    public void close() { up.close(); }
}
```

`limit` — счётчик, `takeWhile` — флаг, `flatMap` — вложенный `Source`, барьеры
материализуют вход в `ArrayList` при первом `next()`. Терминальная операция —
цикл `while ((v = source.next()) != null)` плюс `close()` в `finally`.

Пакет — `wdl-stdlib/src/main/java/ru/wds/wdl/stdlib/streams/`: `Source`,
`Sources` (источники), `Stages` (промежуточные), `Terminals` (терминальные),
`NativeStream` (класс для скрипта), `Streams` (модуль).

## Что сделано иначе, чем записано выше

Три места, где реализация разошлась с планом. Записаны здесь, а не молча исправлены
в тексте выше: план — документ о принятых решениях, и видеть, какое из них не пережило
встречи с кодом, полезнее, чем читать задним числом переписанный.

### `distinct` — не барьер

Решение 8 числит его барьером вместе с `sorted` и обосновывает это тем, что он
«вынужден прочитать вход целиком». Для `sorted` это правда: пока не увиден последний
элемент, неизвестен первый. Для `distinct` — нет: ему довольно помнить уже выданное,
и тогда `iterate(...).distinct().limit(5)` кончается, а не висит. Сделан ленивым;
барьером в документации назван только `sorted`.

Платой остаётся память под уже выданное — на потоке, где различного много, она уходит
вся. Это записано в `docs/streams.md` рядом с самой операцией, там же, где и про
барьер: правило «свойство операции пишется у операции» решение 8 задаёт верно,
а вот отнесено оно было не к той операции.

### `reduce(f, начало)`, а не `reduce(init, f)`

В API-наброске начальное значение стоит первым — за Java. Но в этом же языке уже
написан `a.reduce(f, 0)`, и два одноимённых члена с противоположным порядком
аргументов — ловушка, а не выразительность. Взят порядок массива; заодно
необязательный аргумент остаётся вторым, а не первым, и арность не приходится
разнюхивать.

### Пример лежит в `examples/streams/`, а не в `examples/modules/`

`examples/modules/` — про механику `import`, у неё свой README со своей таблицей
(«каждый файл показывает одну грань `import`»). Пример конвейеров туда не ложится
ни по теме, ни в ту таблицу.

### Попутно: `Files` открыт

`Files.io` и `Files.pathOf` из `ru.wds.wdl.stdlib` стали публичными: файлы читает
не один модуль, а `sys.io` и `sys.streams`, и живут они в разных пакетах. Второй
разбор пути и второй набор текстов «не удалось обратиться к файлу» разошлись бы
с первыми, а автору скрипта одна и та же неудача обязана выглядеть одинаково, каким
бы модулем он ни открыл файл. Тем же движением в `sys.thread` появился
`Threads.channelIn(value)` — одно действие «взять следующее», а не открытая наружу
внутренность канала.

## Что не берётся

* **Новый тип значения** — решение 1: вопросы «что печатает ленивое значение»
  не имеют ответа ни в каком порядке работ.
* **`parallel()` в модели Java** — решение 11: `mapConcurrent` покрывает
  единственный сценарий, ради которого это заводят.
* **Генераторы `yield`** — это корутины: либо преобразование тела, либо поток
  на генератор. Библиотечный ответ уже есть — продюсер в отдельном потоке пишет
  в `th.channel`, поток читает: `streams.of(channel)`, десять строк и ни одной
  правки в языке.
* **Запросный синтаксис (LINQ)** — отвергнут ещё предыдущим планом: второй способ
  записать то, что уже записывается выражением.
* **Оператор `|>`** — независимый вариант A, про форму записи. Он ортогонален
  ленивости и с потоком будет работать так же, как с массивом.
