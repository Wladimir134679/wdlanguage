# План: лямбды на `=>`, ветка `match` на `->`

Замысел — дать языку короткую запись анонимной функции, не заводя третьего понятия:
`p => p * 2` вместо `def(p) => p * 2`. Ради этого два знака **меняются местами**:
`=>` целиком уходит функциям, а разделителем ветки `match` становится `->`.

Документ **проектный**: описывает решение, его причину и порядок работ. Примеры
будущего синтаксиса в нём, в отличие от `docs/`, ещё не выполняются.

Заменяет собой «Вариант B1» из [ПланКонвейеровОбработки.md](ПланКонвейеровОбработки.md):
там предлагалось отдать лямбде свободный `->`, оставив `match` как есть. Разбор ниже
показывает, почему инверсия лучше.

Отметки: `[ ]` не начато, `[~]` в работе, `[x]` сделано и проверено сборкой.

---

## Зачем вообще

Сегодня половину короткой строки занимает служебное слово:

```wdl
prices.filter(def(p) => p >= 100).map(def(p) => p * 2)
suite.test("деление на ноль", def() => divide(1, 0))
def log(meta) => def(*args, **named) => meta.target(*args, **named)
```

Станет:

```wdl
prices.filter(p => p >= 100).map(p => p * 2)
suite.test("деление на ноль", () => divide(1, 0))
def log(meta) => (*args, **named) => meta.target(*args, **named)
```

Последняя строка — самая показательная: две стрелки подряд читались как одно и то же,
а после разделения `def ... =>` остаётся объявлением, `(...) =>` — литералом функции.

---

## Почему знаки меняются местами

### Что `=>` значит сегодня

Четыре места, и объединяет их формулировка «дальше значение вместо блока»:

```wdl
def f(a) => a + 1          // тело функции          — Parser.functionRest
def total() => p * c       // тело метода, фабрики  — TypeParser.memberBody
property area => w * h     // короткое свойство     — TypeParser.property
match (cpu) { case > 90 => "жарко" }   // ветка     — Parser.caseBody
```

Формулировка **синтаксическая**: она описывает форму записи, а не смысл. Именно
поэтому она и растягивается на ветку `match`, которая функцией не является.

### Что `=>` будет значить после

Три места из четырёх — это **буквально один и тот же узел** `FunctionExpr`. Короткое
свойство не исключение: `TypeParser.getterOf` строит из него функцию с синтетическим
именем `Rect.area (get)`. Убрав четвёртое место, получаем знак с единственным смыслом:

> **`=>` — справа тело функции.**

А `->` получает свой, тоже единственный:

> **`->` — эта ветка даёт это значение.**

Два знака с непересекающимися смыслами лучше одного знака с растянутым — это и есть
весь размен.

### Почему нельзя просто добавить лямбду к тому, что есть

Разбирались три пути.

**Путь 1 — лямбда на свободном `->`, `match` не трогаем.** Ничего не ломает, но
оставляет два знака с пересекающимися смыслами: и `=>`, и `->` значат «дальше
значение», а какой именно писать — надо помнить. Дёшево, но мутно.

**Путь 2 — лямбда на `=>`, `match` переводится на двоеточие (`case p: 1`).**
Отвергнут: место, которое двоеточие покупает, **и так свободно**. Образец `case`
разбирается с порогом `Operators.COMPARISON + 1` (`Parser.caseTail`) — это готовый
«механизм запрета» на полное выражение в образце, тот самый, из-за которого
`case score > 90` даёт внятную ошибку. Лямбда с самым низким приоритетом в образец
по этому порогу просто не попадёт:

```wdl
case p => 1        // порог не пускает стрелку → образец 'p', тело '1'
case (p) => 1      // group() вернёт (p), стрелка останется снаружи
```

Так что двоеточие платило бы миграцией и пятым значением знака `:` за то, что уже есть.

**Путь 3 — инверсия (выбран).** `->` в ветку, `=>` функциям. Стоит той же миграции,
что путь 2, но покупает на неё точность знаков, а не пустое место.

### Побочный выигрыш инверсии

При путях 1 и 2 остаётся одно место, где стрелка-оператор всё-таки конфликтует:
условие ветки разбирается с нулевым порогом (`guard = expression(0)` в
`Parser.matchCase`), и `case if throttled => 1` съело бы стрелку в лямбду. Порог
пришлось бы подкручивать.

При инверсии проблема исчезает сама: разделителем ветки становится `->`, а он
**не оператор вовсе** — `expression(0)` на нём остановится, потому что в таблице
`Operators` его нет.

### Чем платим

* Ломающее изменение: все `match` в репозитории и в чужих скриптах.
* Опечатка `>=`, набранная как `=>`, из ошибки разбора превращается в законную
  лямбду — см. «Диагностика, без которой нельзя».
* `->` перестаёт быть свободным. Если когда-нибудь появятся записи типов
  (`cb: (Int) -> Int`), знак придётся делить. Считаем приемлемым: статических типов
  в языке нет и не планируется.

### Про узнаваемость

Половинки знакомы порознь: `->` в ветках — это Java `switch` и Kotlin `when`;
`=>` для лямбд — JS, C# и Scala. Ни один язык не разводит их именно так (Java
и Kotlin берут `->` для обоих, Scala и Rust — `=>`), поэтому отличие осознанное
и должно быть записано в `docs/control-flow.md` вместе с причиной — иначе через год
кто-нибудь «поправит обратно».

## Что получится

```wdl
// один параметр — скобки не нужны
double = x => x * 2

// несколько, ноль, значения по умолчанию и остатки — через скобки
sum = (a, b) => a + b
now = () => time.now()
step = (x, by = 1) => x + by
forward = (*args, **named) => target(*args, **named)

// каррирование: правая ассоциативность
adder = a => b => a + b
println(adder(2)(3))                    // 5

// match переезжает на '->'
level = match (cpu) {
    case > 90 -> "жарко"
    case > 50 -> "тепло"
    case if throttled -> "придержано"
    else -> "холодно"
}

// и они уживаются в одной строке
handler = match (kind) {
    case "sum" -> (a, b) => a + b
    else -> (a, b) => a - b
}
```

Что **не** вводится: блочная лямбда. `x => { ... }` не заводится, потому что `{`
в позиции выражения — литерал объекта, и `() => {a: 1}` обязано возвращать объект.
Функция с блоком остаётся `def`-формой, и это граница, которая держит число форм
записи от роста: **`=>` не заменяет `def`, а забирает у него одну нишу — анонимную
функцию-выражение.**

Убрать `def` совсем нельзя, и не из-за парсера: объявление заводит имя **в текущей
области**, а присваивание ищет существующее наружу; аннотации и `synchronized`
привязаны к объявлению — конструктор `FunctionExpr` прямо запрещает аннотации
у анонимной функции.

## Этап 1. `match` переезжает на `->` — `[ ]`

Шаг самодостаточный, обратимый и **не добавляющий никакой двусмысленности**:
меняется один разделитель. Его можно взять и остановиться на нём.

**Правки в ядре:**

1. `Parser.caseBody` — `cursor.match(TokenType.FATARROW)` → `TokenType.ARROW`.
2. `Parser.startsBody` — `FATARROW` → `ARROW` в списке токенов, с которых начинается
   тело, а не образец.
3. Там же — **ветка на старую стрелку** с подсказкой (см. «Диагностика»).
4. Javadoc `MatchExpr`, `MatchCase`, `CaseTail`, `Parser.caseBody` — примеры
   в комментариях содержат `=>`.

**Миграция (посчитано по репозиторию):**

| Что | Объём |
|---|---|
| `examples/*.wdl` | 40 строк в `language/match.wdl`, `classes/operators.wdl` |
| java-тесты | 246 строк в 7 файлах: `MatchParserTest`, `MatchTest`, `OperatorTest`, `OperatorGroupTest`, `NodesTest`, `StepCoverageTest`, `SExprPrinter` |
| `docs/` | 14 мест, в основном `control-flow.md` |
| плагин IDEA | **ноль** — `=>` там не захардкожен, лексер берётся из ядра |

Остальные 180+ вхождений `=>` в документации — тела функций, они не трогаются.

**Проверка этапа:** `./gradlew build`. Если 246 сниппетов позеленели, миграция верна.

**Отдельно:** в `docs/control-flow.md` объяснить, почему знак именно `->`, — иначе
раздел останется без причины, а `docs/README.md` требует записывать её.

## Этап 2. Лямбда на `=>` — `[ ]`

**Две точки входа в разбор, и это не дублирование, а разные ситуации.**

*Без скобок* — обычный инфикс. В `Parser.expression(int)` ветка рядом с той, что
обрабатывает `?`: тернарник встроен туда же и по той же причине — «правая часть
не такая, как у бинарного оператора».

```java
if (type == TokenType.FATARROW) {
    if (Operators.LAMBDA < minPower) {
        return left;
    }
    left = lambda(left);
    continue;
}
```

`Operators.LAMBDA = 1` — ниже `TERNARY = 2`, шаг таблицы там как раз оставляет место.
Тело разбирается с порогом `LAMBDA`, а не `LAMBDA + 1`: отсюда правая ассоциативность
и каррирование `a => b => c`.

*Со скобками* — скан вперёд в `Parser.prefix()`, ветка `case LPAREN`. Причина: `(`
в позиции выражения ведёт в `group()`, который разбирает **одно** выражение и требует
`)`, поэтому `(a, b)` и `()` через инфикс не пройдут в принципе. Скан идёт от `(`
до парной `)` со счётчиком вложенности и проверяет, стоит ли за ней `=>`. Токены
лежат готовым списком, `cursor.peek(n)` есть, приёмы такого рода в парсере уже
применяются (`isMirrorAhead`, `shortTryAhead`).

Скан окупается: если он сработал, дальше зовётся тот же `types.parameters()`,
и короткая форма **бесплатно** получает значения по умолчанию, `*args`, `**named`
и параметр-дырку.

**Остальные правки:**

1. `Parser.lambda(Expr left)` — левая часть обязана быть `VariableExpr`; иначе ошибка
   с внятным текстом (см. «Диагностика»). Тело — `state.inFunctionBody(...)`, как
   в `functionRest`: иначе `break`/`continue`/`yield` из окружающего цикла или
   ветки-значения окажутся видны внутри лямбды.
2. Узел — тот же `FunctionExpr` с `ReturnStmt` внутри. Ни `Interpreter`,
   ни `Nodes.children`, ни посетители не меняются.
3. `BodyStyle` — третий элемент `LAMBDA`: «тело-выражение, заголовок без `def`».
   Без него форматтер не отличит `def(p) => p` от `p => p`. Альтернатива — отдельный
   `HeaderStyle`; она честнее по смыслу (речь о заголовке, а не о теле), но заводит
   второе поле ради одного бита. Берётся первая, javadoc `BodyStyle` объясняет почему.
4. `FunctionExpr.title()` — сегодня подставляет слово `def` там, где имени нет,
   и сообщение `функция 'def' принимает ровно 1 аргумент` для лямбды станет враньём:
   слова `def` в тексте нет. Смотреть на `style()`.
5. `AstDumper.visitFunction` — строка с `", тело-выражение '=>'"` получает третий
   вариант.
6. Скобки вокруг единственного параметра **не хранятся**: они восстанавливаются
   из `span` — если интервал функции начинается с интервала первого параметра,
   скобок не было. Поле ради этого не заводится.

**Тесты:**

* `ParserTest` — форма дерева через `SExprPrinter`: `x => x * 2` обязано дать ровно
  то же дерево, что `def(x) => x * 2`. Это и есть главное утверждение этапа.
* Приоритеты: `x => x > 0 ? 1 : -1` (тернарник внутри тела), `a => b => c` (правая
  ассоциативность), `f(p => p, 10)` (запятая обрывает тело).
* `InterpreterTest` — вызов, замыкание, `arity`, `params`, `name` и `anonymous`
  у `double = x => x * 2`. Имя подставляется тем же `Parser.named`, что и сегодня
  у `f = def(x) => x`; `anonymous` остаётся `true` — два разных ответа на два разных
  вопроса, и это уже так работает.
* `AstInvariantTest` — интервал узла внутри родителя; добавить в корпус
  `wdl-core/src/test/resources/malformed/` недописанную лямбду и недописанную ветку
  `match`.

## Диагностика, без которой нельзя

**1. Лямбда в позиции условия.** Главный риск всей затеи:

```wdl
if (count => limit) { ... }     // опечатка в '>=' — сегодня ошибка разбора
```

Сегодня `=>` в позиции инфикса парсер не ждёт, и это внятный отказ. Как только `=>`
станет оператором, строка станет законной: `count => limit` — функция, а функция
истинна всегда, значит `if` сработает **всегда**. Тихая ошибка ровно того класса,
ради которого язык запретил `if (x = 5)` в принципе.

Лекарство — запрет разбора: лямбда в позиции условия `if`, `while`, `case if`
и тернарника есть ошибка. Механизм тот же, что у `doesSomething()` в теле ветки.

```
ошибка: здесь ожидалось условие, а записана функция — она истинна всегда.
        Если это сравнение, знак пишется '>='
```

**2. Старая стрелка в ветке `match`** — переходная подсказка, но нужна надолго: так
написано во всех существующих скриптах и во всех текстах о языке.

```
ошибка: в ветке 'match' тело отделяется стрелкой '->'.
        '=>' теперь значит «дальше тело функции»
```

**3. Левая часть `=>` не имя.**

```
ошибка: слева от '=>' ожидался параметр или список параметров в скобках,
        а записано выражение
```

## Открытые вопросы

* **Параметр-дырка без скобок.** `_ => 42`: `_` в позиции выражения — не выражение,
  через инфикс не пройдёт. Либо отдельная ветка в `prefix()` на `HOLE` перед `=>`,
  либо требовать скобки `(_) => 42`. Предлагается второе: дырка — редкий случай,
  а ветка в `prefix()` заводит `HOLE` в позицию, где его сегодня нет вовсе.
* **`SExprPrinter`.** Печатать ли лямбду иначе, чем `def`. Предлагается **не**
  печатать: тесты парсера сравнивают *форму дерева*, а форма у них одна — в этом
  и утверждение. Стиль записи проверяется отдельно, дампом.
* **Форматтер.** Переписывает ли он `def(p) => p` в `p => p`. Предлагается нет:
  форма записи хранится именно затем, чтобы её сохранять.
* **Пустой список без скобок.** `=> 42` как «функция без параметров» не вводится:
  выражение не может начинаться с `=>`, и заводить ради этого исключение незачем —
  `() => 42` короче любого объяснения.

## Что этот план не делает

* Не заводит блочную лямбду `x => { ... }` — см. выше.
* Не трогает `def`: объявление, аннотации, `synchronized`, методы и фабрики остаются
  как есть.
* Не убирает форму `def f(a) return a;` (тело одной инструкцией без скобок). Это
  единственная форма записи, которая не даёт ничего сверх пары осей «объявление ×
  тело», и если когда-нибудь захочется сократить их число, кандидат именно она —
  но это отдельное решение и отдельная миграция.
* Не вводит неявный параметр `it`: он ломается на вложенных цепочках и спорит
  с правилом «имя существует с той строки, где его завели».
