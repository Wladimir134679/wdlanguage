# План: лямбды на `=>`, ветка `match` на `->`

Замысел — дать языку короткую запись анонимной функции, не заводя третьего понятия:
`p => p * 2` вместо `def(p) => p * 2`. Ради этого два знака **меняются местами**:
`=>` целиком уходит функциям, а разделителем ветки `match` становится `->`.

Документ **проектный**: описывает решение, его причину и порядок работ. Примеры
будущего синтаксиса в нём, в отличие от `docs/`, ещё не выполняются.

Заменяет собой «Вариант B1» из [ПланКонвейеровОбработки.md](ПланКонвейеровОбработки.md):
там предлагалось отдать лямбде свободный `->`, оставив `match` как есть. Разбор ниже
показывает, почему инверсия лучше.

Отметки: `[ ]` не начато, `[~]` в работе, `[x]` сделано и проверено сборкой.

---

## Зачем вообще

Сегодня половину короткой строки занимает служебное слово:

```wdl
prices.filter(def(p) => p >= 100).map(def(p) => p * 2)
suite.test("деление на ноль", def() => divide(1, 0))
def log(meta) => def(*args, **named) => meta.target(*args, **named)
```

Станет:

```wdl
prices.filter(p => p >= 100).map(p => p * 2)
suite.test("деление на ноль", () => divide(1, 0))
def log(meta) => (*args, **named) => meta.target(*args, **named)
```

Последняя строка — самая показательная: две стрелки подряд читались как одно и то же,
а после разделения `def ... =>` остаётся объявлением, `(...) =>` — литералом функции.

---

## Почему знаки меняются местами

### Что `=>` значит сегодня

Четыре места, и объединяет их формулировка «дальше значение вместо блока»:

```wdl
def f(a) => a + 1          // тело функции          — Parser.functionRest
def total() => p * c       // тело метода, фабрики  — TypeParser.memberBody
property area => w * h     // короткое свойство     — TypeParser.property
match (cpu) { case > 90 => "жарко" }   // ветка     — Parser.caseBody
```

Формулировка **синтаксическая**: она описывает форму записи, а не смысл. Именно
поэтому она и растягивается на ветку `match`, которая функцией не является.

### Что `=>` будет значить после

Три места из четырёх — это **буквально один и тот же узел** `FunctionExpr`. Короткое
свойство не исключение: `TypeParser.getterOf` строит из него функцию с синтетическим
именем `Rect.area (get)`. Убрав четвёртое место, получаем знак с единственным смыслом:

> **`=>` — справа тело функции.**

А `->` получает свой, тоже единственный:

> **`->` — эта ветка даёт это значение.**

Два знака с непересекающимися смыслами лучше одного знака с растянутым — это и есть
весь размен.

### Почему нельзя просто добавить лямбду к тому, что есть

Разбирались три пути.

**Путь 1 — лямбда на свободном `->`, `match` не трогаем.** Ничего не ломает, но
оставляет два знака с пересекающимися смыслами: и `=>`, и `->` значат «дальше
значение», а какой именно писать — надо помнить. Дёшево, но мутно.

**Путь 2 — лямбда на `=>`, `match` переводится на двоеточие (`case p: 1`).**
Отвергнут: место, которое двоеточие покупает, **и так свободно**. Образец `case`
разбирается с порогом `Operators.COMPARISON + 1` (`Parser.caseTail`) — это готовый
«механизм запрета» на полное выражение в образце, тот самый, из-за которого
`case score > 90` даёт внятную ошибку. Лямбда с самым низким приоритетом в образец
по этому порогу просто не попадёт:

```wdl
case p => 1        // порог не пускает стрелку → образец 'p', тело '1'
case (p) => 1      // group() вернёт (p), стрелка останется снаружи
```

Так что двоеточие платило бы миграцией и пятым значением знака `:` за то, что уже есть.

**Путь 3 — инверсия (выбран).** `->` в ветку, `=>` функциям. Стоит той же миграции,
что путь 2, но покупает на неё точность знаков, а не пустое место.

### Побочный выигрыш инверсии

При путях 1 и 2 остаётся одно место, где стрелка-оператор всё-таки конфликтует:
условие ветки разбирается с нулевым порогом (`guard = expression(0)` в
`Parser.matchCase`), и `case if throttled => 1` съело бы стрелку в лямбду. Порог
пришлось бы подкручивать.

При инверсии проблема исчезает сама: разделителем ветки становится `->`, а он
**не оператор вовсе** — `expression(0)` на нём остановится, потому что в таблице
`Operators` его нет.

### Чем платим

* Ломающее изменение: все `match` в репозитории и в чужих скриптах.
* Опечатка `>=`, набранная как `=>`, из ошибки разбора превращается в законную
  запись. Чем это закрывается — в «Риск, который приходит вместе с бесскобочной
  формой»; без того правила брать бесскобочную запись нельзя.
* `->` перестаёт быть свободным. Если когда-нибудь появятся записи типов
  (`cb: (Int) -> Int`), знак придётся делить. Считаем приемлемым: статических типов
  в языке нет и не планируется.

### Про узнаваемость

Половинки знакомы порознь: `->` в ветках — это Java `switch` и Kotlin `when`;
`=>` для лямбд — JS, C# и Scala. Ни один язык не разводит их именно так (Java
и Kotlin берут `->` для обоих, Scala и Rust — `=>`), поэтому отличие осознанное
и должно быть записано в `docs/control-flow.md` вместе с причиной — иначе через год
кто-нибудь «поправит обратно».

## Что получится

```wdl
// одно имя — без скобок
double = x => x * 2

// всё остальное — в скобках
now = () => time.now()
sum = (a, b) => a + b
step = (x, by = 1) => x + by
forward = (*args, **named) => target(*args, **named)
ignore = (_) => 42                      // у дырки нет имени, поэтому скобки

// каррирование: правая ассоциативность
adder = a => b => a + b
println(adder(2)(3))                    // 5

// match переезжает на '->'
level = match (cpu) {
    case > 90 -> "жарко"
    case > 50 -> "тепло"
    case if throttled -> "придержано"
    else -> "холодно"
}

// и они уживаются в одной строке
handler = match (kind) {
    case "sum" -> (a, b) => a + b
    else -> (a, b) => a - b
}
```

### Без скобок пишется одно имя

Ради этого всё и затевалось: `filter(p => p > 0)` короче `filter((p) => p > 0)`
ровно настолько, насколько цепочка вообще читается. Скобки остаются там, где без
них список параметров не собрать: ноль, два и больше, значения по умолчанию, остатки.

**Дырка пишется в скобках — `(_) => 42`, — и это не исключение из правила,
а следствие.** У дырки нет имени: `Param.HOLE` заводится ровно затем, чтобы занять
позицию, ничего не назвав, и `TypeParser.addHole` говорит это прямым текстом —
«у дырки нет имени». Правило «без скобок пишется **одно имя**» дырку не покрывает
по определению, оговорки к нему не нужно.

Совпадает и разбор. Бесскобочная форма разбирается инфиксом: к моменту встречи
с `=>` левая часть уже разобрана как **выражение**, а `_` выражением не является —
в `Parser.prefix()` его нет вовсе. То есть `_ => 42` пришлось бы заводить отдельной
веткой, которая тащит `HOLE` в позицию, где его сегодня нет; `(_) => 42` работает
через `types.parameters()` **бесплатно**, вместе со всей уже написанной там
диагностикой: у дырки не бывает значения по умолчанию, дырка не идёт после остатка,
в заголовке трейта её нет.

Второй выигрыш от того же решения — в правиле про неиспользованный параметр
(следующий раздел). Будь `_ => 42` законным, оно звучало бы «параметр обязан
встречаться в теле, кроме дырки»; со скобками оговорка не нужна: **всякий
бесскобочный параметр встречается в теле**, и точка.

Платим случаем `each((_) => count++)` — двумя символами там, где лямбда короче
всего. Случай редкий: дырка обычно стоит рядом с другими параметрами
(`(_, second) => second`), а там скобки нужны и так.

### Риск, который приходит вместе с бесскобочной формой

```wdl
ready = count => limit      // хотел '>=', получил функцию
if (ready) { ... }          // функция истинна всегда — ветка сработает всегда
```

Перестановка `>=` в `=>` — известная опечатка: в JS ради неё держат отдельное
правило линтера (`no-confusing-arrow`). Обязательные скобки закрывали бы класс
целиком (слева от `=>` не бывало бы ничего), но скобки на каждой лямбде — та самая
цена, ради отказа от которой запись и затевается.

**Через истинность это не лечится.** Сделать функцию ложной или запретить её
в условии значило бы завести исключение в правило «ложны только `null` и `false`»
([docs/types.md](../docs/types.md#истинность)) — оно держится плоским нарочно, одно
правило вместо списка исключений.

**Лечится через параметр.** У настоящей лямбды параметр в теле используется;
у мнимой — нет, потому что тела там и не писали:

```wdl
count => limit      // 'count' в теле не встречается — почти наверняка опечатка
p => p * 2          // встречается
```

Отсюда правило: **бесскобочный параметр обязан встречаться в теле**. Оно ловит
`count => limit` точно и опирается не на догадку, а на существующую запись языка.
Проверка синтаксическая — обход только что построенного тела через `Nodes.children`;
отдельной стадии не заводится, как её не завели для проверки «значение по умолчанию
видит параметры слева».

**Правило привязано именно к бесскобочной форме**, и это тоже следствие, а не выбор:
опечатка в `>=` может дать только её. `(a, b) => a` со свободным `b` остаётся
законным ровно как `def(a, b) => a` — там сомневаться не в чем, скобки уже сказали
«это функция».

Отсюда и выход из ошибки для настоящей константной функции: скобки. `map(x => 0)`
отвергается, `map((_) => 0)` — правильная запись, `map((x) => 0)` — тоже законная,
если имя нужно для читателя.

Заодно правило записывается одной фразой: **лямбда — это `def`-форма без слова
`def`**. `def(p) => p` и `p => p` отличаются словом и скобками, а слово нужно там,
где функции дают имя, аннотации или `synchronized`.

Что **не** вводится: блочная лямбда. `x => { ... }` не заводится, потому что `{`
в позиции выражения — литерал объекта, и `() => {a: 1}` обязано возвращать объект.
Функция с блоком остаётся `def`-формой, и это граница, которая держит число форм
записи от роста: **`=>` не заменяет `def`, а забирает у него одну нишу — анонимную
функцию-выражение.**

Убрать `def` совсем нельзя, и не из-за парсера: объявление заводит имя **в текущей
области**, а присваивание ищет существующее наружу; аннотации и `synchronized`
привязаны к объявлению — конструктор `FunctionExpr` прямо запрещает аннотации
у анонимной функции.

## Этап 1. `match` переезжает на `->` — `[x]`

Шаг самодостаточный, обратимый и **не добавляющий никакой двусмысленности**:
меняется один разделитель. Его можно взять и остановиться на нём.

**Правки в ядре:**

1. `Parser.caseBody` — `cursor.match(TokenType.FATARROW)` → `TokenType.ARROW`.
2. `Parser.startsBody` — `FATARROW` → `ARROW` в списке токенов, с которых начинается
   тело, а не образец.
3. Там же — **ветка на старую стрелку** с подсказкой (см. «Диагностика»).
4. Javadoc `MatchExpr`, `MatchCase`, `CaseTail`, `Parser.caseBody` — примеры
   в комментариях содержат `=>`.

**Миграция (посчитано по репозиторию):**

| Что | Объём |
|---|---|
| `examples/*.wdl` | 40 строк в `language/match.wdl`, `classes/operators.wdl` |
| java-тесты | 246 строк в 7 файлах: `MatchParserTest`, `MatchTest`, `OperatorTest`, `OperatorGroupTest`, `NodesTest`, `StepCoverageTest`, `SExprPrinter` |
| `docs/` | 14 мест, в основном `control-flow.md` |
| плагин IDEA | **ноль** — `=>` там не захардкожен, лексер берётся из ядра |

Остальные 180+ вхождений `=>` в документации — тела функций, они не трогаются.

**Проверка этапа:** `./gradlew build`. Если 246 сниппетов позеленели, миграция верна.

**Отдельно:** в `docs/control-flow.md` объяснить, почему знак именно `->`, — иначе
раздел останется без причины, а `docs/README.md` требует записывать её.

### Как сделано

Сделано ровно по списку, с тремя уточнениями по ходу.

*`startsBody` знает обе стрелки, а не одну.* Замена `FATARROW` на `ARROW` списком
не ограничилась: старая стрелка там оставлена наравне с новой, иначе `case => 1`
(забытый образец, написанный по-старому) уходил бы разбирать `=>` как образец
и получал бы «ожидалось выражение» вместо «после 'case' нужен образец».

*Подсказка не обрывает разбор.* Ветка на `=>` в `caseBody` сообщает об ошибке
и **съедает стрелку**, разбирая тело дальше как обычно. Иначе на каждую строку
приходилось бы по две ошибки: подсказка и следом «у ветки нет тела». Правило
«ошибка не прерывает разбор» тут работает буквально: дерево остаётся целым для
форматтера и подсветки, а выполнение останавливает `diagnostics.hasErrors()`.

*`SExprPrinter` печатает `->`.* Печать ветки шла через `" => "`, и все 246 ожиданий
в тестах содержали её; знак сменился вместе с ними — форма дерева от этого не зависит,
но читать ожидание рядом с исходником проще, когда знаки совпадают.

Мигрировано: `examples/language/match.wdl`, `examples/classes/operators.wdl`,
7 java-файлов тестов, `docs/control-flow.md`, `README.md`, `Основные идеи.md`.
Плагин IDEA не тронут, как и предсказывалось. Новый тест —
`MatchParserTest.oldArrowInBranchIsRejected`: подсказка есть, ошибка ровно одна.

## Этап 2. Лямбда на `=>` — `[x]`

**Две точки входа, по одной на форму записи. Это не дублирование: формы разные.**

*Одно имя без скобок* — обычный инфикс. В `Parser.expression(int)` ветка рядом
с той, что обрабатывает `?`: тернарник встроен туда же и по той же причине — «правая
часть не такая, как у бинарного оператора».

```java
if (type == TokenType.FATARROW) {
    if (Operators.LAMBDA < minPower) {
        return left;
    }
    left = lambda(left);
    continue;
}
```

`Operators.LAMBDA = 1` — ниже `TERNARY = 2`, шаг таблицы там как раз оставляет место.
Тело разбирается с порогом `LAMBDA`, а не `LAMBDA + 1`: отсюда правая ассоциативность
и каррирование `a => b => c`.

*Скобки* — скан вперёд в `Parser.prefix()`, ветка `case LPAREN`. Через неё же идут
ноль параметров, несколько, дефолты, остатки и дырка. Причина: `(`
в позиции выражения ведёт в `group()`, который разбирает **одно** выражение и требует
`)`, поэтому `(a, b)` и `()` через инфикс не пройдут в принципе. Скан идёт от `(`
до парной `)` со счётчиком вложенности и смотрит, стоит ли за ней `=>`. Если да —
заголовок читает `types.parameters()`, и лямбда бесплатно получает всё, что умеет
заголовок: значения по умолчанию, `*args`, `**named`, аннотации параметров.

Токены лежат готовым списком, `cursor.peek(n)` есть, и приёмы такого рода в парсере
уже применяются (`isMirrorAhead`, `shortTryAhead`). Бэктрекинг («разобрать как
параметры, при неудаче откатиться») не годится: парсер накапливает диагностику
на ходу, и откат оставил бы за собой чужие сообщения.

**Остальные правки:**

1. `Parser.lambda(...)` — общее тело для обоих входов: список параметров, затем
   `FATARROW`, затем тело в `state.inFunctionBody(...)`, как в `functionRest`. Иначе
   `break`/`continue`/`yield` из окружающего цикла или ветки-значения окажутся видны
   внутри лямбды. Там же — проверка «бесскобочный параметр используется в теле».
2. Узел — тот же `FunctionExpr` с `ReturnStmt` внутри. Ни `Interpreter`,
   ни `Nodes.children`, ни посетители не меняются.
3. `BodyStyle` — третий элемент `LAMBDA`: «тело-выражение, заголовок без `def`».
   Без него форматтер не отличит `def(p) => p` от `p => p`. Альтернатива — отдельный
   `HeaderStyle`; она честнее по смыслу (речь о заголовке, а не о теле), но заводит
   второе поле ради одного бита. Берётся первая, javadoc `BodyStyle` объясняет почему.
4. `FunctionExpr.title()` — сегодня подставляет слово `def` там, где имени нет,
   и сообщение `функция 'def' принимает ровно 1 аргумент` для лямбды станет враньём:
   слова `def` в тексте нет. Смотреть на `style()`.
5. `AstDumper.visitFunction` — строка с `", тело-выражение '=>'"` получает третий
   вариант.
6. Ветка-совет в `Parser.prefix()` на `HOLE`, за которым стоит `=>`: она **не**
   разбирает лямбду, а только объясняет, что делать. Приём в этом `switch` уже
   заведён — так же отвечают `try` в позиции выражения и `synchronized` без `def`.

```
ошибка: у пропуска '_' нет имени, поэтому без скобок он не пишется: '(_) => 42'
```

**Тесты:**

* `ParserTest` — форма дерева через `SExprPrinter`: `x => x * 2`, `(x) => x * 2`
  и `def(x) => x * 2` обязаны дать **одно и то же** дерево. Это и есть главное
  утверждение этапа.
* Границы тела: `x => x > 0 ? 1 : -1` (тернарник целиком уходит в тело),
  `a => b => a + b` (правая ассоциативность), `f(p => p, 10)` (запятая обрывает тело).
* Скан не путается: `(a + b) * c` остаётся группировкой, `(a)(b)` — вызовом,
  вложенность `((a, b) => a)(1, 2)` разбирается.
* Дырка: `(_) => 42` и `(_, second) => second` разбираются, вся диагностика
  `addHole` работает и здесь (`(_ = 1) => 42`, `(*rest, _) => 42`); `_ => 42` даёт
  совет про скобки, `_` в любой другой позиции — по-прежнему «ожидалось выражение».
* Неиспользованный параметр: `count => limit` — ошибка с подсказкой,
  `(count) => limit` и `(_) => limit` — законны, `p => p * 2` — законно.
* `InterpreterTest` — вызов, замыкание, `arity`, `params`, `name` и `anonymous`
  у `double = x => x * 2`. Имя подставляется тем же `Parser.named`, что и сегодня
  у `f = def(x) => x`; `anonymous` остаётся `true` — два разных ответа на два разных
  вопроса, и это уже так работает.
* `AstInvariantTest` — интервал узла внутри родителя; добавить в корпус
  `wdl-core/src/test/resources/malformed/` недописанную лямбду и недописанную ветку
  `match`.

### Как сделано

Сделано по списку; ниже — то, что список не предусмотрел.

*Скану понадобился дешёвый отсев, и он же закрыл открытый вопрос о стоимости.*
Скан не запускается вовсе, если сразу за `(` стоит токен, которым параметр начаться
не может: список параметров начинается именем, пропуском, звёздочкой, аннотацией
или сразу `)`. `((((a))))` при этом отсеивается на каждом уровне первой же проверкой,
и квадратичного случая, о котором беспокоился раздел «Открытые вопросы», не возникает.

*Начальное значение скрытого поля разбирается порогом выше лямбды.* Единственное
место во всём разборе, где `=>` внешней конструкции стоит сразу за `expression(0)`:
у `property x = 0 => 1` нуль уходил в параметр лямбды, и сообщение «у свойства есть
скрытое поле, поэтому короткой формы `=>` ему мало» переставало появляться. Порог
`LAMBDA + 1` в `TypeParser.property` возвращает стрелку короткой форме; бесскобочная
лямбда начальным значением и не нужна — она пишется там в скобках. Больше нигде
подкручивать не пришлось: у `def f(a = ...)` и у аргумента вызова список закрывает
скобка, а она разбор выражения и так останавливает.

*Ошибка «слева не имя» молчит, когда о ней уже сказали.* `_ => 42` даёт ровно одну
ошибку — совет про скобки, — потому что `lambda()` не повторяет претензию к левой
части, если та уже `ErrorExpr`. Без этого на каждую такую строку приходилось бы
по две ошибки, а вторая была бы производной от первой.

*`title()` у безымянной лямбды — это `=>`.* Слова `def` в её тексте нет, и сообщение
«функция 'def' принимает ровно 1 аргумент» указывало бы на запись, которой никто
не писал. `writtenName()` при этом не тронут: `SExprPrinter` печатает форму дерева,
а она у лямбды и у анонимного `def` одна — в этом и утверждение этапа. Форму записи
показывает дамп: `функция (x), лямбда '=>'`.

Тесты: `LambdaParserTest` (20 проверок — форма дерева, границы тела, скан,
пропуск, неиспользованный параметр), раздел лямбд в `FunctionTest`, два новых файла
в корпусе недописанного (`partial-lambda.wdl`, `partial-match-branch.wdl`).
Документация: раздел «Лямбды» в `docs/functions.md`, ссылка из `docs/control-flow.md`,
строки в `README.md` и `docs/overview.md`, пример в `examples/language/functions.wdl`.

## Диагностика, без которой нельзя

**1. Бесскобочный параметр не использован в теле.** Главная проверка всей затеи —
именно она отделяет лямбду от опечатки в `>=` (разобрано выше). Сообщение обязано
назвать обе причины, потому что их правда две:

```wdl
ready = count => limit
```

```
ошибка: параметр 'count' не используется в теле функции.
        Если это сравнение, знак пишется '>=';
        если функция — параметр без имени пишется '(_) => ...'
```

Порядок подсказок не случаен: опечатка вероятнее намеренной константной функции,
и первой должна стоять она.

**2. Старая стрелка в ветке `match`** — переходная подсказка, но нужна надолго: так
написано во всех существующих скриптах и во всех текстах о языке.

```
ошибка: в ветке 'match' тело отделяется стрелкой '->'.
        '=>' теперь значит «дальше тело функции»
```

**3. В скобках не параметры.** Скан нашёл `(...) =>`, а внутри оказалось выражение:

```wdl
(a + b) => c
```

Сообщение даёт `types.parameters()` сам — «ожидалось имя параметра». Проверить, что
оно понятно в этой позиции, и что интервал указывает на `a + b`, а не на всю строку.

**4. Дырка без скобок** — `_ => 42`. Ветка-совет в `prefix()`, текст в этапе 2.

## Открытые вопросы

> Три из четырёх закрыты этапом 2 — как именно, отмечено ниже. Открытым остаётся
> только форматтер: его самого ещё нет.

* **Стоимость скана.** Скан запускается на каждой `(` в позиции выражения, поэтому
  на глубоко вложенных скобках (`((((a))))`) он линеен по глубине, а суммарно
  квадратичен. На реальных выражениях глубина мала, но замерить на `examples/`
  стоит — стадия разбора считается `--metrics`, и регрессия будет видна сразу.
  Если понадобится, дешёвый отсев: скан не нужен, когда сразу за `(` стоит токен,
  которым параметр начаться не может.
  **Закрыт:** отсев поставлен сразу, не дожидаясь замера, — он стоит одну проверку
  и снимает квадратичный случай целиком.
* **`SExprPrinter`.** Печатать ли лямбду иначе, чем `def`. Предлагается **не**
  печатать: тесты парсера сравнивают *форму дерева*, а форма у них одна — в этом
  и утверждение. Стиль записи проверяется отдельно, дампом.
  **Закрыт так, как предлагалось:** форму записи показывает дамп — `функция (x),
  лямбда '=>'`.
* **Форматтер.** Переписывает ли он `def(p) => p` в `p => p`, а `(p) => p` в `p => p`.
  Предлагается нет: форма записи хранится (`BodyStyle`) именно затем, чтобы её
  сохранять. Отсюда второй вопрос — различать ли `(p) => p` и `p => p` в дереве.
  Отдельного поля не нужно: скобки видны по `span` — если интервал функции начинается
  с интервала первого параметра, скобок не было. **Остаётся открытым:** форматтера
  ещё нет, а `span` для ответа уже достаточно.
* **Строгость правила про неиспользованный параметр.** Ошибка разбора или
  предупреждение. Предлагается ошибка: тихое «всегда истинно» — тот же класс, ради
  которого запрещён `if (x = 5)`, а выход из неё у пишущего есть и он однострочный —
  скобки. Если окажется, что константные лямбды в цепочках встречаются чаще, чем
  кажется, правило смягчается до предупреждения без правки разбора.
  **Закрыт:** сделана ошибка.

## Что этот план не делает

* Не заводит блочную лямбду `x => { ... }` — см. выше.
* Не трогает `def`: объявление, аннотации, `synchronized`, методы и фабрики остаются
  как есть.
* Не убирает форму `def f(a) return a;` (тело одной инструкцией без скобок). Это
  единственная форма записи, которая не даёт ничего сверх пары осей «объявление ×
  тело», и если когда-нибудь захочется сократить их число, кандидат именно она —
  но это отдельное решение и отдельная миграция.
* Не вводит неявный параметр `it`: он ломается на вложенных цепочках и спорит
  с правилом «имя существует с той строки, где его завели».
