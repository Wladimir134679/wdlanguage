# План: подсказки после точки и межфайловые модули

Цель: чтобы completion понимал получателя в `a.` настолько, насколько это можно
установить **без выполнения пользовательского WDL-кода**, и показывал методы,
свойства, фабрики и поля собственных, нативных и импортированных классов.

План дополняет существующие `FileAnalysis`, `Catalog`, `Lookup` и LSP. Он не
вводит статическую типизацию языка и не меняет поведение рантайма.

## Границы и принципы

1. Анализ не исполняет пользовательские файлы и не вызывает пользовательские
   функции. Читать, лексировать и разбирать `.wdl` на диске безопасно.
2. Ответы имеют степень уверенности. Точный тип даёт только его члены; неизвестный
   тип не становится фиктивно известным.
3. Нативный API описывается теми же построителями, которыми он открывается
   рантайму. Рукописный второй список методов запрещён.
4. Открытый несохранённый буфер всегда сильнее текста файла на диске.
5. Каталог внешних библиотек и индекс пользовательских файлов — разные источники
   данных, но для `Lookup` выглядят единым снимком.
6. Циклические импорты, отсутствующие файлы и неполный код — штатные состояния
   редактора, не причины для сбоя сервера.

## Целевой результат

| Код | Ожидаемая подсказка | Источник |
| --- | --- | --- |
| `"abc".` | члены `String` | `BuiltinMembers` |
| `new File("a").` | члены `File` | дескриптор класса |
| `File.` | фабрики/статические члены класса | дескриптор класса |
| `import sys.io as io; io.File.` | члены `File` | модульный каталог → класс |
| `file = new io.File("a"); file.` | члены `File` | однозначное присваивание |
| `import app.shapes as shapes; shapes.Circle.` | члены `Circle` | workspace-модуль |
| `circle.` после неоднозначного присваивания | нет ложного точного списка | `Unknown` |

## Этап 1. Семантические дескрипторы для получателя

В `wdl-tools` добавить протокол-независимую модель `ReceiverType` (или `ValueShape`):

* `Unknown` — тип установить нельзя;
* `Builtin(ValueType)` — строка, список, число и прочие значения ядра;
* `Class(SymbolDescriptor)` — конкретный WDL/нативный класс;
* `Trait(SymbolDescriptor)` — известный трейт;
* `Module(ModuleDescriptor)` — импортированный модуль;
* `Function`, `Union` и `Error` — только если понадобятся следующему правилу;
* у каждого результата: `confidence` (`EXACT`, `INFERRED`, `UNKNOWN`) и источник.

Не связывать эту модель с LSP DTO: ей должны пользоваться `LanguageService`, IDEA
плагин и встроенный редактор напрямую.

Также добавить `MemberLookup`:

* `members(ReceiverType)` возвращает `MemberDescriptor`;
* у `Class` берёт `SymbolDescriptor.members()`;
* у `Builtin` — `Catalog.members(ValueType)`;
* у `Module` — публичные имена модуля;
* не теряет kind, сигнатуру, документацию, признак snapshot и происхождение.

**Проверки:** unit-тесты на члены строк, класса и модуля; неизвестный получатель
даёт пустой список на первом шаге.

## Этап 2. Разрешение access-цепочки, видимой из текста

Создать `ReceiverResolver` над AST, `FileAnalysis` и составным каталогом. Он
получает выражение слева от текущей точки и не запускает код.

Поддержать в порядке ценности:

1. литералы и коллекции: `"x".`, `[1].`, `{a: 1}.`;
2. выражение создания: `new C(...).`;
3. имя класса из локального файла или каталога: `C.`;
4. импортированный модуль: `io.`;
5. доступ к классу/константе из модуля: `io.File.`;
6. цепочки известных статических фабрик, если их возвращаемый класс указан в
   метаданных;
7. переменная с единственным доминирующим присваиванием известного выражения:
   `f = new File(...); f.`.

Важные правила:

* Любое затенение проверять через `FileAnalysis.resolve`, а не по строке имени.
* При нескольких несовместимых присваиваниях возвращать `Unknown` либо `Union`;
  никогда не выбрать один вариант произвольно.
* `AccessExpr` уже позволяет разобрать недописанное `x.`. Не восстанавливать
  получателя эвристикой по токенам.
* Для класса отдельно решить, какие имена доступны на самом классе (`C.`), а
  какие на экземпляре (`new C().`), чтобы не смешать фабрики и методы.

**Проверки:** `io.File.`, `new File(...).`, локальный `class Box { def open() }`,
однократное присваивание, затенённый alias, ветвление с разными типами и
незавершённый `AccessExpr`.

## Этап 3. Подключить resolver к completion, hover и signature help

Заменить в `Lookup.completeAt()` правило «после точки работает только alias
модуля» на вызов `ReceiverResolver`.

* Completion получает члены известного получателя и правильный `CompletionItemKind`.
* Hover на `io.File.read` проходит всю цепочку: модуль → `File` → член.
* Добавить `signatureHelp` для вызова известной функции/метода, используя
  `MemberDescriptor.signature` и метаданные параметров.
* Для `Unknown` сначала оставлять completion пустым. Объединённый список членов
  всех типов рассматривать только отдельной опцией и ранжировать ниже точных:
  он полезен в динамическом языке, но слишком шумен для дефолта.

**Шлюз:** весь прежний набор completion остаётся без изменений; `io.` продолжает
работать; неизвестный получатель не рекламирует неверные методы.

## Этап 4. Дополнить метаданные нативных классов

Состояние сейчас: `Catalogs.snapshot()` устанавливает нативную библиотеку в
изолированную область, а `Catalogs.describe()` читает у `ClassValue` имена методов,
свойств и полей. Этого достаточно для перечисления экземплярных членов уже
зарегистрированного класса.

Нужно закрыть пробелы метаданных:

* расширить `MemberDescriptor`, если текущих полей недостаточно, данными о
  статичности, результате вызова и типе свойства;
* в `NativeClass.Builder` добавить декларативные аннотации результата, например
  `returns(ClassValue)` / `propertyType(ClassValue)`, не Java-reflection по
  неограниченному API;
* `FromJava` должен экспортировать только явно разрешённые методы/bean-свойства,
  уже доступные рантайму; не сканировать все public Java methods ради подсказок;
* документация, сигнатуры WDL и return shape задаются у `.method(...)`,
  `.factory(...)`, `.property(...)` рядом с реализацией;
* объединить наследованные и собственные члены ровно по правилам рантайма,
  включая override и скрытие.

Для host-модулей отдельного процесса LSP нужен transport метаданных: JSON manifest
или configuration capability с `ModuleDescriptor`/`SymbolDescriptor`. Сервер не
может увидеть Java-объекты приложения, если сам не запущен в его JVM. Manifest
генерируется тем же `Catalogs.snapshot()` при сборке/старте host, а не ведётся вручную.

**Проверки:** каждый объявленный нативный член виден и выполняется; скрытый рантаймом
член не попадает в каталог; у `io.File.` предлагаются только доступные члены;
отсутствие GUI/optional dependency даёт пустой модуль, но не ломает LSP.

## Этап 5. Индекс рабочей папки и файловые модули

Создать в `wdl-tools` `WorkspaceIndex`, а не размещать семантику в `wdl-lsp`.

### Состав индекса

* настроенные source roots и правила `module key ↔ URI`;
* `DocumentId → FileAnalysis + export snapshot + version/content hash`;
* `module key → ModuleDescriptor` для пользовательских файлов;
* прямые и обратные рёбра `import`;
* overlay открытых документов из `DocumentStore`;
* диагностики разрешения импорта: missing, ambiguous, cycle.

### Алгоритм

1. На `initialize` сервер принимает workspace folders и конфигурацию WDL
   (`sourceRoots`, module mapping, optional host catalog manifest).
2. Индексирует только `.wdl` в source roots, не выполняя их.
3. Для каждого файла строит `FileAnalysis` и экспортную поверхность: публичные
   class/trait/def/const и их члены. Внутренние локальные объявления не экспортирует.
4. Разрешает import в URI; поверх диска использует открытый буфер, если он есть.
5. При `didOpen`/`didChange`/`didSave` обновляет snapshot, пересчитывает только
   зависимые модули и уведомляет затронутые документы о новых diagnostics.
6. При цикле выдаёт предсказуемый частичный snapshot и диагностику; не рекурсирует
   бесконечно и не обнуляет уже известные независимые экспорты.

Сначала достаточно alias-импорта: `import app.shapes as shapes`. Развёрнутый import
добавлять после того, как будет формально описано его затенение и конфликты имён.

**Шлюз:** изменение `shapes.wdl` меняет completion в импортирующем несохранённом
файле; definition у `shapes.Circle` переходит в соседний URI; цикл и удалённый файл
дают диагностику без падения сервера.

## Этап 6. Единый снимок каталога и правила приоритета

Собрать в точке запроса `ProjectCatalog` из:

1. символов текущего файла и локальных scope — сильнее всех;
2. модулей workspace;
3. host/native manifest или живого host catalog;
4. standard `Sys` и builtins.

`Catalog` оставить API для внешних значений; не заставлять его читать файловую
систему. `WorkspaceIndex` предоставляет отдельный `WorkspaceCatalog`, а
`Catalog.merged(...)` объединяет их. У коллизий прописать диагностику и единое
правило приоритета, а не зависеть от порядка обхода каталогов.

Добавить кеширование по revision snapshot; completion читает неизменяемый снимок,
индексация публикует новый атомарно. Это исключит ответ из наполовину обновлённого
проекта при параллельных LSP-запросах.

## Этап 7. LSP-возможности поверх workspace

После индекса разрешить и объявить capabilities только по факту реализации:

* cross-file `definition` и `references`;
* `workspace/symbol` по экспортам;
* `signatureHelp`;
* позже `prepareRename`/`rename`, когда будут полностью обработаны импортные
  aliases, затенение и все обратные ссылки.

`WdlWorkspaceService` должен обрабатывать configuration и watched files, а
`didSave` — обновлять disk snapshot при отсутствии текста в уведомлении. Наблюдение
за файлами — вспомогательное: correctness не должен зависеть от того, прислал ли
клиент уведомление.

## Порядок поставки

1. Этапы 1–3: точные подсказки собственных и уже каталогизированных нативных
   классов, без workspace.
2. Этап 4: полные метаданные host/native API и return shape.
3. Этапы 5–6: соседние WDL-модули, overlay и инвалидация.
4. Этап 7: навигация, ссылки и rename между файлами.

## Набор обязательных интеграционных сценариев

* Нативный: `import sys.io as io; io.File.` и `new io.File("a").`.
* Собственный файл: локальный `class File` со свойством, полем и методом.
* Соседний модуль: изменение метода в открытом `shapes.wdl` сразу видно в
  открытом импортёре без сохранения.
* Тень: локальная `io` не получает членов `sys.io`.
* Неполный код: `new File(`, `io.File.`, `x.` не выбрасывают исключение.
* Динамика: переменная с двумя разными присваиваниями не получает ложного списка.
* Безопасность: файл с побочным эффектом не выполняется во время индексации.
* Производительность: изменение одного файла не перечитывает весь workspace;
  completion использует уже опубликованный snapshot.
