# План: измерение этапов конвейера

Замер времени лексера, парсера, выполнения и закрытия запуска: включается флагом,
накапливается объектом запуска, доступен геттерами и печатается в конце `wdl --metrics`.

Отметки: `[ ]` не начато, `[~]` в работе, `[x]` сделано и проверено сборкой.

---

## Решения, из которых следует остальное

**1. Метрики — зависимость, а не статика.** Ровно как `Output` и `Diagnostics`.
Счётчик в `static`-поле сложил бы вместе два интерпретатора, работающих в одном
процессе, — а изоляция запусков и есть то, ради чего проект переписан (инвариант 3).
Приёмник создаёт вызывающий и передаёт его в конвейер.

**2. По умолчанию метрик нет.** `Metrics.off()` — синглтон, чей `begin` возвращает
синглтон-заглушку с пустым `close()`. Ни аллокации, ни `nanoTime` на выключенном пути;
JIT такую пару выкидывает целиком. Движок, встроенный в чужое приложение, не платит
за то, чего не просил, — то же правило, что у вывода в никуда.

**3. Меряет тот, кто запускает стадию, а не сама стадия.** `Lexer.tokenize` и
`Parser.parseProgram` не меняются вовсе: их время полностью видно снаружи одним
охватом. Протаскивать приёмник внутрь горячего кода пришлось бы ради нуля новой
информации. Исключение одно и оно вынужденное: разбор и выполнение **модуля**
случаются внутри движка (`ModuleUnits`, `runtime.Modules`) — снаружи туда не дотянуться,
поэтому приёмник туда передаётся.

**4. Сумма по стадиям не обязана равняться времени по стенным часам.** Внутри запуска
работает сколько угодно потоков (`docs/threads.md`), и два `EXECUTE` идут одновременно.
Поэтому отчёт держит оба числа: сумму замеров и стену от начала до конца, — и в выводе
они подписаны по-разному. Молчаливое «итого» из суммы врало бы ровно на многопоточном
скрипте, то есть там, где метрики и нужны.

**5. Время модуля входит во время скрипта.** Замеры вложены по построению: `import`
выполняется внутри `EXECUTE` главного файла. Не разбираем это на непересекающиеся
куски — показываем строкой «в том числе модули», а вложенность считаем
по `start`/`duration`.

## Этап 1. Ядро: пакет `ru.wds.wdl.metrics`

- [x] 1.1 `Stage` — `LEX`, `PARSE`, `EXECUTE`, `SHUTDOWN`; у каждого русское `title()`
      для вывода
- [x] 1.2 `Measurement` — `record(Stage stage, String subject, boolean module,
      long startNanos, long durationNanos, String thread)`.
      `subject` — путь файла или ключ модуля; `module` отделяет импортированное
      от главного файла; `thread` нужен затем, чтобы «сумма больше стены» читалась,
      а не удивляла
- [x] 1.3 `Measure extends AutoCloseable` — `close()` без `throws`, чтобы
      `try`-с-ресурсами не тащил за собой `catch`
- [x] 1.4 `Metrics` — интерфейс приёмника:
      ```java
      Measure begin(Stage stage, String subject, boolean module);
      default Measure begin(Stage stage, String subject);   // module = false
      static Metrics off();                                 // ничего не делает
      static MetricsCollector collecting();
      static MetricsCollector collecting(Consumer<Measurement> listener);
      ```
      `listener` — то самое «включить логирование этапа»: замер уходит слушателю
      сразу по завершении стадии, а не в конце запуска. Приложению этого хватает,
      чтобы слать этапы в свой лог или в свою систему метрик, ничего не зная про отчёт
- [x] 1.5 `MetricsCollector implements Metrics` — накопление и геттеры:
      ```java
      List<Measurement> all();                 // в порядке завершения
      Map<Stage, Duration> byStage();
      Duration total(Stage stage);
      Duration total(Stage stage, boolean module);
      int count(Stage stage);
      Duration wall();                         // стена: от создания до finish()
      MetricsCollector finish();               // фиксирует стену; идемпотентен
      void adopt(MetricsReport other);         // втянуть чужие замеры (см. 4.2)
      String render();                         // готовая таблица для консоли
      ```
      Внутри — `ConcurrentLinkedQueue<Measurement>` плюс `LongAdder` на стадию:
      замеры приходят из потоков скрипта, а глобального замка больше нет (инвариант 3)
- [x] 1.6 `MetricsReport` — интерфейс только на чтение; `MetricsCollector` его
      реализует. Приложению отдаётся отчёт, а не приёмник: право писать замеры
      и право их читать — разные права
- [x] 1.7 `package-info.java` и строка `exports ru.wds.wdl.metrics;`
      в `module-info.java` (инвариант 6)
- [x] 1.8 Тесты: суммирование, пустой отчёт у `off()`, конкурентная запись
      из нескольких потоков, `wall() >= max(duration)`

## Этап 2. Точки замера в ядре

- [x] 2.1 `ModuleUnits(ModuleSource, Metrics)` — второй конструктор; старый остаётся
      с `Metrics.off()`. Замеры `LEX` и `PARSE` с `module = true` и `subject = key`
      вокруг двух вызовов в `parse()`
- [x] 2.2 `Run` — поле `metrics` (`volatile`, задаётся при сборке запуска, как и
      `modules`), геттер пакетного уровня
- [x] 2.3 `ExecutionContext.withMetrics(Metrics)` и `metrics()` — по образцу
      `withModules`: новый контекст, тот же сеанс
- [x] 2.4 `Interpreter.run(Unit, ExecutionContext)` и `run(Program, ...)` — охват
      `EXECUTE` на **верхнем уровне файла**. Не в `entering()`: туда приходит и каждый
      вызов функции скрипта из приложения, и мерять его — это уже профилировщик,
      другая задача
- [x] 2.5 `runtime.Modules.fileModule` — охват `EXECUTE` с `module = true` вокруг
      выполнения файла модуля
- [x] 2.6 Тесты интерпретатора: скрипт с `import` даёт по замеру `LEX`/`PARSE`/`EXECUTE`
      на модуль; выключенные метрики не меняют поведения

## Этап 3. CLI

- [x] 3.1 `--metrics` — печать сводки после выполнения. В `stderr`, а не в `stdout`:
      вывод скрипта — это данные, и `wdl script.wdl > out.txt` не должен получить
      в файл нашу таблицу
- [x] 3.2 `--metrics-each` — вдобавок строка на каждый замер по мере завершения
      (`Metrics.collecting(listener)`), чтобы было видно, какой именно модуль тормозит
      на длинном запуске
- [x] 3.3 Замеры в `Main.execute`: `LEX`, `PARSE` вокруг существующих вызовов,
      `SHUTDOWN` вокруг блока `finally` (остановка потоков и закрытие модулей — это
      тоже время запуска, и на `sys.gui` оно бывает основным)
- [x] 3.4 Печать в `finally` — **после** закрытия, чтобы `SHUTDOWN` в таблицу попал;
      таблица печатается и когда скрипт упал: время до падения тоже ответ
- [x] 3.5 Формат:
      ```
      ── метрики ──────────────────────────────
        лексер            3,2 мс
        парсер           33,4 мс
        выполнение       13,4 мс   в т.ч. модули 2,6 мс
        модули: разбор    1,0 мс   1 файл
        закрытие          0,0 мс
      ── сумма замеров 53,7 мс · по часам 122,3 мс
      ```
      «по часам» отдельной строкой — см. решение 4. Счётчик файлов приписывается
      только там, где замеров больше одного: «1 файл» у лексера главного файла —
      шум. «· потоков N» появляется, когда замеры пришли из разных потоков
- [x] 3.6 Флаги описаны в `footer` команды

## Этап 4. Встраивание (`wdl-api`)

- [x] 4.1 `WdlEngine.Builder.metrics(boolean)` и `metrics(Supplier<Metrics>)` —
      супплиер, а не готовый приёмник, по той же причине, что и у библиотек:
      накопитель принадлежит запуску, а движок — это рецепт
- [x] 4.2 `WdlScript.metrics()` — отчёт о разборе; `WdlInstance.metrics()` — отчёт
      запуска, куда при создании втягиваются (`adopt`) замеры разбора. Так у приложения
      один отчёт на «скомпилировали и выполнили», хотя стадии эти разнесены по разным
      объектам
- [x] 4.3 `WdlInstance.close()` меряет `SHUTDOWN` своим же приёмником
- [x] 4.4 Тесты `WdlEngineTest`: по умолчанию отчёт пустой; с `metrics(true)` —
      непустой и стадии на месте

## Чего здесь сознательно нет

* **Профилирования по функциям.** Замер на каждом `call` — это другая задача
  и другая цена; `Stage` до неё не растягивается, и делать вид, что растягивается,
  вредно.
* **Счётчиков памяти и аллокаций.** JVM их даёт своими средствами, и дублировать
  плохой копией незачем.
* **Экспорта в JSON или Prometheus.** Приложению для этого хватает `all()`
  и слушателя, а формат — не дело ядра (инвариант 1: у `wdl-core` ноль внешних
  зависимостей).

## Журнал

### Всё сделано, `./gradlew build` зелёный

Пакет `ru.wds.wdl.metrics` (`Stage`, `Measurement`, `Measure`, `Metrics`, `NoMetrics`,
`MetricsCollector`, `MetricsReport`), замеры в ядре, флаги CLI, отчёты в `wdl-api`,
`docs/metrics.md` и рецепт в `CLAUDE.md`. Тесты: `MetricsTest` (9 случаев),
`runtime.MetricsIntegrationTest` (5), плюс 5 в `WdlEngineTest`.

**Четыре отличия от задуманного.**

1. **Идиома замера — `try/finally`, а не `try`-с-ресурсами.** Проверено экспериментом:
   javac с `-Xlint:all` выдаёт `[try] auto-closeable resource ... is never referenced`
   на любой `try`-с-ресурсами, тело которого к переменной не обращается, — а это ровно
   наш случай, и имя вроде `ignored` (в отличие от Eclipse) ничего не подавляет. Ставить
   `@SuppressWarnings` в десяток мест или заводить лямбда-форму `measure(stage, () -> ...)`
   оказалось дороже, чем написать явный `finally`: он читается не хуже и не создаёт
   захватывающей лямбды на каждой стадии. Решение записано в javadoc `Measure`
   и в рецепте `CLAUDE.md`.

2. **Замер `EXECUTE` встал в одно место вместо двух.** Планом он был в
   `Interpreter.run(Unit, ...)` и в `Modules.fileModule` (пункты 2.4 и 2.5), но обе
   дороги сходятся в приватном `Interpreter.execute(Program, ExecutionContext)` —
   туда приходят и главный скрипт, и модуль, и строка REPL. Признак «это модуль»
   выводится из `unit.key() != null`: у модуля юнит с ключом, у главного файла — нет.
   Правки в `Modules` не потребовалось вовсе.

3. **В `wdl-api` вместо `metrics(Supplier<Metrics>)` — `metrics(Consumer<Measurement>)`.**
   Супплиер не работал: приложение подсунуло бы свой `Metrics`, и тогда
   `WdlScript.metrics()` нечего было бы вернуть — произвольный приёмник не является
   отчётом. Слушатель покрывает тот же случай (отправить стадии в свою систему метрик)
   и при этом не отнимает у приложения отчёт. Осталось два метода: `metrics(boolean)`
   и `metrics(Consumer<Measurement>)`, второй включает накопление сам.

4. **Отчёт получил больше, чем планировалось**: `sum()`, `threads()`,
   `count(stage, module)` и `Measurement.insideOf(outer)`. Первые два понадобились
   последней строке таблицы (сумма против часов и объяснение, откуда разница),
   `insideOf` — чтобы «время модуля входит во время скрипта» можно было не только
   написать в документе, но и проверить тестом.

**Что проверено руками:** `wdl --metrics examples/modules/plain.wdl` (модули видны
отдельной строкой), `wdl --metrics-each examples/threads.wdl` (стадии печатаются
по ходу), `--metrics` вместе с `--ast` (стадии, до которых дошли), падающий скрипт
(таблица есть, время до падения в ней).

**Чего в отчёте пока не видно.** Строка «· потоков N» на практике почти не появляется:
стадии запускает главный поток, а потоки скрипта выполняют функции, а не файлы.
Она станет видимой, когда `import` случится внутри потока скрипта, — и это правильный
момент, чтобы её показать.
