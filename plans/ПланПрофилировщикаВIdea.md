# План: профилировщик в IntelliJ IDEA

Кнопка «Профилировать» рядом с «Запустить», а после прогона — окно с горячими
функциями и деревом вызовов, из которого двойным щелчком попадаешь на объявление.

Отметки: `[ ]` не начато, `[~]` в работе, `[x]` сделано и проверено сборкой.

---

## Решения, из которых следует остальное

**1. Считает `wdl`, показывает плагин.** Плагин остаётся тонким — ровно как с LSP,
где правил языка в нём нет вовсе. Ни `wdl-core`, ни `wdl-api` он в зависимости
не берёт: свои record-классы отчёта и парсер JSON. Иначе плагин пришлось бы
пересобирать под каждую версию языка, а он ставится из ZIP и живёт своей жизнью.

**2. Обмен — файл JSON, а не протокол.** `wdl --profile-out <файл>` уже умеет всё,
что нужно: пишет отчёт в конце запуска, в том числе у скрипта, который упал.
Сокет или порт добавили бы третью движущуюся часть там, где хватает файла во временном
каталоге. Живого профиля «по ходу выполнения» в первой версии нет — и это осознанно:
он требует потока событий из процесса, а вопрос «где скрипт проводит время» на него
не опирается.

**3. Профилирование — действие, а не настройка конфигурации.** Поэтому свой
`Executor` (третья кнопка рядом с Run и Debug), а не флажок в редакторе конфигурации.
Одна и та же конфигурация запускается обычным способом и профилируется — без
дублирования настроек и без риска забыть снятый флажок и получить медленный прод-запуск.
Флаг `--profile-out` дописывает сама конфигурация, когда видит наш `executorId`.

**4. Формат отчёта версионирован.** В корне JSON лежит `"version": 1`. Читатель внешний
и обновляется отдельно от `wdl`, поэтому «поле пропало» он обязан отличать от «файл
не тот»: незнакомая версия — понятное сообщение, а не исключение парсера.

**5. Дерево строится из графа, а не приходит готовым.** `wdl` отдаёт рёбра
«вызывающий → вызываемый» с числами; дерево вызовов плагин разворачивает лениво,
узел за узлом. Готовое дерево росло бы вместе с запуском (миллион итераций — миллион
узлов), а рёбер столько, сколько в коде таких пар. Цикл в графе (рекурсия) узел
не разворачивает дальше, а помечает: «рекурсия».

**6. Навигация — по смещению, а не по имени.** В записи есть `file` и `offset`
в единицах UTF-16 — то же, чем меряет документ IntelliJ (`docs/tooling.md`), поэтому
`OpenFileDescriptor(project, file, offset)` открывает объявление без поиска. Имя
осталось бы неоднозначным: одноимённые функции в разных файлах — обычное дело.

**7. Путь может быть относительным.** Главный файл назван в отчёте так, как его дали
`wdl` в командной строке; файлы модулей — абсолютные. Плагин разрешает относительный
путь от рабочего каталога конфигурации, а не от корня проекта: рабочий каталог — это
то, с чем процесс запускался.

## Этап 1. Чтение отчёта в плагине

Отдельным этапом, потому что всё остальное на нём стоит и проверяется без запуска IDE.

- [ ] 1.1 `ide/idea-plugin/.../profile/ProfileReport.java` — record-модель:
      `record ProfileReport(int version, String script, long calls, long selfNanos,
      long wallNanos, int threads, List<ProfileSite> sites, List<ProfileEdge> edges)`;
      `ProfileSite(String kind, String name, String file, int line, int offset,
      long calls, long totalNanos, long selfNanos, long maxNanos)`;
      `ProfileEdge(int caller, int callee, long calls, long totalNanos)`

      из платформы (своей зависимости не добавляем). Незнакомая `version` — своё
      исключение с текстом «отчёт от другой версии wdl: ожидалась 1, получена N»
- [ ] 1.3 Разрешение путей: `ProfileSite.file()` → `VirtualFile` через
      `LocalFileSystem`, относительный — от рабочего каталога конфигурации.
      Пустой `file` (встроенная функция) — это не ошибка: у записи просто нет места,
      и переход по ней недоступен
- [ ] 1.4 Тест на образце JSON в `src/test/resources`: разбор, порядок записей,

## Чего в первой версии нет

* **Живого профиля по ходу выполнения.** Требует потока событий из процесса и своего
  протокола; вопрос «где скрипт проводит время» на него не опирается.
* **Сравнения двух прогонов.** Полезно, но это отдельный экран и отдельное понятие
  «база»; появится, когда накопится привычка смотреть профиль вообще.
* **Профиля памяти.** Движок его не считает — считать нечего.
* **Профиля строк.** Точки съёма стоят на вызовах, и добавлять их на узлы дерева
  ради IDE нельзя: это плата в самой горячей точке движка для всех запусков.

## Что может пойти не так

* **Скрипт с окнами (`sys.gui`).** Процесс живёт, пока открыты окна, — отчёт появится
  только после закрытия. Это не поломка, но в уведомлении стоит сказать прямо.
* **Профиль пуст.** Скрипт не дошёл до выполнения (ошибка разбора) — окно должно
  сказать это словами, а не показать пустую таблицу.
* **Тысячи записей.** Таблица без фильтра станет нечитаемой; отсюда пункт 3.6,
  а не «потом посмотрим».
* **Путь с кириллицей и пробелами.** Файл пишется в UTF-8; читать его надо явно
  в UTF-8, а не в кодировке платформы, иначе имена файлов поедут на Windows.
* **Профиль замедляет скрипт.** Тот, кто мерит по секундомеру, обязан знать, что
  под кнопкой «Профилировать» время не то же самое, что под «Запустить», —
  строка об этом в README плагина.
