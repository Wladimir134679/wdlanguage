# Нативные модули: расширение языка на Java

> **Состояние: база сделана.** Этапы 1, 2 и 4 из раздела 11 выполнены — встроенные
> модули работают, `sys.json`, `sys.io` и `sys.net.http` написаны, библиотеки
> закрываются вместе с запуском. Что именно получилось и чем реализация отличается
> от плана — в разделе 15 внизу. Не сделаны 6.1–6.3 (трейты и наследование)
> и вся глава 8 про асинхронность: многопоточность решено делать отдельно.

Проект: как `import sys.net.http`, `import sys.json` или обёртка чужой библиотеки
должны выглядеть для автора скрипта и во что это обходится движку.

Одной фразой: **нативный модуль — это `Library`, положенная не в корневую область,
а в свою собственную.** Для языка он неотличим от модуля-файла, потому что модуль
и так определён как «имена, оставшиеся в корневой области после выполнения», —
а кто их туда положил, интерпретатору знать незачем.

---

## 1. Чего требует задача

1. `import sys.nio`, `import org.json` — обращение к классам, функциям и константам,
   реализованным на Java.
2. Наследоваться от того, что модуль отдаёт, и **реализовывать его интерфейсы**.
3. Оборачивать сторонние библиотеки (JSON, HTTP, SQL) отдельными подключаемыми кусками.
4. Неблокирующая работа с сетью, не ломающая однопоточность интерпретатора.
5. Приложение решает, какие модули скрипту доступны, — движок ничего не подключает сам.

## 2. Решение: модуль — это набор имён, а не файл

`docs/modules.md` начинается с фразы «модуль — это обычный скрипт, а не особый вид
файла. У него нет ни списка экспорта, ни заголовка. Содержимое модуля — то, что
осталось в его корневой области после выполнения». Из этого определения выполнение
файла вообще выпадает: важен результат — таблица «имя → значение», то есть
`ModuleScope`, который и есть `ModuleValue`.

Нативный модуль занимает ровно это место:

```
файл модуля:      Source → Lexer → Parser → Interpreter.run(ModuleScope) → ModuleValue
нативный модуль:                            Library.installTo(ModuleScope) → ModuleValue
```

Правая половина конвейера общая. Значит **ни одной правки в интерпретаторе, парсере
и типах значений не нужно** — и всё поведение модулей достаётся нативным даром:

| Что | Почему работает |
|---|---|
| `import sys.json` и `import sys.json as json` | обе формы читают `ModuleValue`, а не файл |
| `json.parse(...)`, `json["parse"]`, `new http.Client()` | [единое обращение](docs/access.md) к модулю |
| `typeof(json)` → `module`, `println(json)` → `module sys/json` | `ModuleValue` один на оба вида |
| модуль выполняется один раз за запуск | `Modules` кэширует значение по ключу |
| опечатка `json.pares` — ошибка, а не `null` | правило `ModuleValue`, не файла |
| `json.parse = ...` запрещено | там же |
| импорт в невызванной функции не стоит ничего | значение строится при выполнении `import` |

Отдельного вида значения (`NativeModuleValue`), отдельного типа в `ValueType`
и отдельной ветки в `visitImport` не появляется. Это главная экономия всего проекта,
и получена она не приёмом, а тем, что определение модуля с самого начала было
сформулировано через имена, а не через файл.

**Следствие, которое стоит отдельного упоминания:** `Std` становится импортируемым
без единой правки. Одна и та же `Library` либо кладётся в корень (как сегодня —
`pow`, `sqrt`, `File` видны всем), либо регистрируется ключом и приезжает по `import`.
Разница только в том, куда её установили.

## 3. Ключ нативного модуля — имя, а не путь

Здесь единственное место, где нативный модуль обязан вести себя иначе, и молчать
об этом нельзя. Ключ файла считается **от каталога импортирующего файла**:
`import sys.json` внутри `lib/tools.wdl` даст ключ `lib/sys/json`. У нативного
модуля каталога нет — его не существует на диске.

**Правило: нативный модуль ищется по написанному имени, до разрешения
относительного пути.**

```wdl
import sys.json            // всегда встроенный sys/json, из любого файла
import "sys/json"          // то же самое
import "./sys/json"        // заведомо файл: путь начинается с точки
import "/sys/json"         // заведомо файл: от корня запуска
import "../sys/json"       // заведомо файл
```

Признак «это заведомо файл» — ведущий `.`, ведущий `/` или `..` в пути. Всё остальное
сперва спрашивается у встроенных, потом разрешается как путь. Обоснование то же,
по которому имя переменной ищется в области видимости, а не в каталоге: у имени
`sys.json` нет и не может быть смысла «относительно текущего файла».

Плата честная: имена зарегистрированных встроенных модулей заняты, и файл
`sys/json.wdl` рядом со скриптом по короткой записи недостижим. Достижим по `"./sys/json"`,
и это ровно та же развилка, что `./node_modules` против встроенных модулей Node.

## 4. Откуда движок берёт модули: один провайдер вместо двух реестров

Сегодня источник один — `ModuleSource`: ключ → `Source` или `null`. Нативному модулю
исходника не существует, поэтому интерфейс расширяется до «ключ → содержимое»:

```java
public interface ModuleProvider {

    /** Что лежит под этим ключом, или null. */
    Found find(String key);

    sealed interface Found {
        /** Модуль-скрипт: его ещё предстоит разобрать и выполнить. */
        record Script(Source source) implements Found {}
        /** Модуль на Java: имена в область кладёт библиотека. */
        record Native(Library library) implements Found {}
    }
}
```

`ModuleSource` остаётся — как частный случай и как готовая реализация для файлов
(`ModuleProvider.ofSource(ModuleSource.ofDirectory(path))`). Приложение собирает
цепочку, и порядок задаёт оно же:

```java
ModuleProvider modules = ModuleProvider.first(
        ModuleProvider.ofNatives(Map.of(                 // встроенные — первыми
                "sys/json",     Json::library,
                "sys/net/http", Http::library,
                "sys/async",    Async::library)),
        ModuleProvider.ofSource(ModuleSource.ofDirectory(scriptHome)));
```

Три решения внутри этого куска:

* **Регистрируется фабрика, а не готовая библиотека.** `Json::library` зовут при
  первом `import`, и не зовут никогда, если импорта не случилось. Это то же обещание
  «за неиспользуемое не платят», что дала ленивая загрузка файлов, и для нативных оно
  весит больше: у модуля бывает пул потоков, драйвер или разбор конфигурации.
* **Никакого `ServiceLoader` по умолчанию.** Движок внутри чужого приложения не должен
  подцеплять из его classpath что попало — по той же причине, по которой он не читает
  файлы без `ModuleSource` и не печатает в чужую консоль. Автообнаружение уместно
  ровно в одном месте — в `wdl-cli`, где хозяин запуска и есть CLI; там это флаг.
* **Отсутствие библиотеки в classpath — ошибка на строке `import`.** Фабрика
  оборачивается так, чтобы `NoClassDefFoundError`/`ClassNotFoundException` превращались
  в `WdlRuntimeError` с текстом «модуль 'json' объявлен, но его библиотеки нет
  в classpath: добавьте …». Java-стек автору скрипта бесполезен, а падать всем
  процессом из-за необязательного модуля тем более незачем.

### Что для этого правится в коде

`ModuleUnits` сегодня делает две работы: **ищет** исходник и **разбирает** его.
Ищущая половина переезжает в `runtime.Modules`, потому что решение «это встроенный
или файл» принимается один раз и в одном месте:

| Файл | Что меняется |
|---|---|
| `module/ModuleProvider` | новый: поиск с двумя видами ответа |
| `module/ModuleSource` | остаётся как есть, становится частным случаем |
| `module/ModuleUnits` | `load(key)` → `parse(key, source)`; поиск уходит, защита от круга при разборе остаётся |
| `runtime/Modules` | спрашивает провайдер; `Native` → `install`, `Script` → как сегодня |
| `runtime/ExecutionContext` | `withModules(ModuleProvider)` рядом с двумя существующими перегрузками |
| `runtime/Interpreter.visitImport` | развилка «имя или путь» из раздела 3 — единственная правка интерпретатора |

Установка нативного модуля в `Modules`:

```java
ModuleScope scope = new ModuleScope(key, root);   // тот же класс, что у файла
library.installTo(scope);
values.put(key, scope.module());
```

Круг здесь невозможен — нативный модуль ничего не выполняет, — но реестр `running`
трогать не надо: `install` просто не рекурсивен.

## 5. Как выглядит нативный модуль на Java

Ничего нового: `Library` + `NativeClass` + `BuiltinFunction`, уже описанные
в [docs/embedding.md](docs/embedding.md).

```java
public final class Json implements Library {

    public static Library library() {
        return new Json();
    }

    @Override
    public String name() {
        return "sys/json";
    }

    @Override
    public Environment installTo(Environment scope) {
        scope.define("parse", BuiltinFunction.of("parse", Arity.exactly(1),
                (context, arguments, span) -> toValue(text(arguments.get(0), span), span)));
        scope.define("stringify", BuiltinFunction.of("stringify", Arity.between(1, 2),
                (context, arguments, span) -> StringValue.of(write(arguments, span))));
        scope.defineConstant("NULL", NullValue.NULL);
        return scope;
    }
}
```

**Данные отдаются значениями языка, а не обёртками.** `parse` возвращает `MapValue`
и `ArrayValue`, а не объект `JsonNode`. Тогда `data.items[0].name`, `for (key in data)`,
`len(data)` и печать работают сами собой, и автору скрипта нечего учить. Обёртка
оправдана только там, где данных больше, чем памяти, или где нужен ленивый доступ;
это исключение, и его надо обосновывать каждый раз отдельно.

Подмодули достаются даром: ключ — обычная строка с `/`, поэтому `sys.net.http`
и `sys.net.tcp` — два независимых модуля, а `sys.net` может не существовать вовсе.

## 6. Классы и интерфейсы из нативного модуля

Это самая содержательная часть запроса — «наследовать и реализовывать». Она делится
на три задачи разной цены, и путать их не стоит.

### 6.1 Нативный трейт: «реализовать интерфейс» (нужно, дёшево)

Трейт в wdl — это обязательство: требования проверяются при объявлении класса,
и ради этого трейты заведены. Именно он, а не наследование, отвечает на «модуль
даёт интерфейс, скрипт его реализует»:

```java
NativeTrait handler = NativeTrait.named("Handler")
        .requireMethod("onMessage", Arity.exactly(2))
        .requireMethod("onClose", Arity.exactly(0))
        .build();
```

```wdl
import sys.net as net

class EchoHandler with net.Handler {
    fun onMessage(client, text) => client.send(text)
    fun onClose() => println("клиент отключился")
}

net.listen(8080, new EchoHandler())
```

Забытый `onClose` — ошибка на строке `class`, тем же текстом и в тот же момент,
что у трейта на wdl. Нативная часть при этом не обязана ничего знать про скрипт:
она получает объект и зовёт `instance.method("onMessage")` — обычное значение-функцию.

**Что для этого нужно в ядре.** `TraitShape` сегодня — финальный класс, построенный
из `TraitDeclStmt`. Он становится интерфейсом с двумя реализациями (из AST и из
построителя), а требование методом — самостоятельным `record Requirement(String name,
Arity arity)` вместо `TraitDeclStmt.Requirement`, у которого арность приходится
вычислять из списка параметров. `Linker.checkRequirements` при этом не меняется
по существу — только перестаёт звать `ClassShape.arityOf`.

**Ограничение v1: у нативного трейта нет методов по умолчанию** — только требования
и константы. Причина техническая и общая с 6.3: метод в плоской таблице
(`MethodSlot`) держит `FunctionExpr`, то есть кусок дерева, а у Java-метода дерева нет.
Обобщение тела — работа из 6.3, и делать её ради методов по умолчанию отдельно незачем.

### 6.2 Нативный класс наследует нативный класс (нужно, дёшево)

Внутри Java-модуля иерархия строится без участия языка: `NativeClass.Builder`
получает `.extending(NativeClass parent)`, таблица методов склеивается плоско
(родитель → свои), `conformsTo` начинает отвечать `true` предку, поля заголовка
дописываются в конец родительских. Ни `Linker`, ни `ClassShape` в этом не участвуют —
формы у нативных классов нет и не нужно.

Это же закрывает `Response`/`HttpResponse`, `TcpSocket`/`Socket` и любую нормальную
библиотечную иерархию.

### 6.3 Скрипт наследует нативный класс (дорого, откладываем)

`class MyServer(port) : net.TcpServer(port)` сегодня даёт внятный отказ: «встроенный
класс: наследоваться можно только от класса, объявленного на wdl»
(`Interpreter.parentOf`). Чтобы это заработало, надо тронуть три вещи:

1. **`MethodSlot.declaration` — `FunctionExpr`.** Нужен `sealed interface MethodBody
   permits Scripted, Native`, и вслед за ним правки в `WdlClass` (таблица `Method`),
   `InstanceScope` (виртуальный поиск голых имён), `super`.
2. **Состояние.** Java-объект живёт в `NativeInstance.state()`, а экземпляр наследника
   создаёт `WdlClass` и делает `InstanceObjectValue.of(this)`. Значит состояние должно
   переехать на `InstanceObjectValue` (карта «класс-владелец → объект»), а `NativeInstance`
   — раствориться. Это, кстати, упрощение: сегодняшнее деление на два класса экземпляра
   существует только из-за одного поля.
3. **Конструкторы.** `init` нативного родителя обязан выполниться в цепочке
   `construct()` на своём месте — от дальнего предка к потомку.

Работа не запредельная, но это правка ядра ради сценария, который в 6.1 и 6.2
закрывается композицией. **Рекомендация: не делать до первого настоящего требования.**
Фреймворки, которые заставляют наследоваться от своего класса, — не тот образец,
к которому стоит стремиться; `with net.Handler` читается лучше и связывает слабее.

## 7. Жизненный цикл: у нативного модуля бывают ресурсы

Файл-модуль после выполнения не держит ничего. Нативный держит: пул потоков,
соединение, открытый канал. Значит у запуска появляется конец, которого сейчас нет.

```java
public interface Library {
    ...
    /** Отпустить ресурсы. По умолчанию — ничего. */
    default void close() {}
}
```

`Modules` запоминает созданные библиотеки в порядке создания и закрывает их
в обратном порядке по `Modules.shutdown()`. Звать `shutdown` обязан хозяин запуска:
`wdl-cli` — в `finally`, будущий `WdlEngine` — из `close()`, чтобы движок ложился
в try-with-resources. Ошибку в `close()` глотать нельзя, но и ронять ей запуск,
который уже отработал, тоже нельзя — она уходит в диагностику как предупреждение.

Это не противоречит неизменяемости `ExecutionContext`: реестр модулей и так изменяемое
состояние запуска, разделяемое вложенными контекстами, — так и написано в его javadoc.

## 8. Сеть и неблокирующие функции

Здесь проектировать надо не API, а **модель потоков**, потому что API из неё следует.

### 8.1 Правило, из которого всё выводится

`Environment`, `Modules`, `Linker` не потокобезопасны, и делать их такими — значит
заплатить синхронизацией за всё выполнение ради редкого случая. Поэтому:

> **Чужой поток никогда не входит в интерпретатор.** Скрипт одного запуска всегда
> выполняется одним потоком; параллелизм живёт в Java-части модуля.

Из этого сразу следует, чего в языке не будет: колбэка, который «сам сработает
когда-нибудь потом». Java-код не имеет права позвать `FunctionValue.call` из своего
пула — значение результата обязано вернуться в поток скрипта.

### 8.2 UX: ожидание вместо колбэков

```wdl
import sys.net.http as http

a = http.request("https://api.example.com/users")     // ушёл в сеть, скрипт не ждёт
b = http.request("https://api.example.com/orders")    // ушёл второй

users = http.await(a)                                 // ждём здесь
orders = http.await(b)                                // этот уже готов

println(users.status, " ", len(json.parse(users.body)))
```

Два запроса летят одновременно, скрипт остаётся однопоточным, и никакой лапши
из `then`. `await` — **обычная функция модуля**, а не ключевое слово: ради библиотеки
язык новых слов не заводит, а без синтаксиса ничего не теряется, потому что
приостанавливать интерпретатор всё равно не нужно.

Групповая форма для веера запросов — там же:

```wdl
responses = http.awaitAll([a, b, c])
```

### 8.3 Что происходит внутри

`http.request` отдаёт `NativeInstance`, чьё состояние — `CompletableFuture`.
`await` вызывает `future.get()` и блокирует поток скрипта. Всё.

Именно поэтому решение дешёвое: **ядро не трогается вообще**. А чтобы блокировка
не стоила потока операционной системы, приложение запускает скрипт в виртуальном
потоке (JDK 21 у проекта уже требуется) — тогда тысяча одновременных скриптов на сервере
это тысяча дешёвых потоков, каждый из которых честно спит на своём `await`.

Таймаут и отмена — параметрами запроса, не отдельным механизмом:

```wdl
r = http.request(url, {timeout: 5, method: "POST", body: payload})
```

### 8.4 Событийный цикл — там, где он неизбежен

Сервер — обратная задача: события приходят снаружи. Ответ тот же — их принимает
поток скрипта:

```wdl
import sys.net as net

server = new net.Server(8080)
server.serve(fun(request) => respond(request))   // блокирующий цикл в потоке скрипта
```

`serve` крутит цикл на своём потоке: берёт готовое соединение из очереди, которую
наполняют потоки ввода-вывода, и зовёт wdl-функцию. Выход — `server.stop()` из самого
обработчика или таймаут. Ввод-вывод при этом неблокирующий и многопоточный, а скрипт —
нет, и это ровно то разделение, которое нужно.

### 8.5 Чего сознательно не даём

* **`spawn`/`go`** — параллельного выполнения самого скрипта. Две «корутины» на общем
  `Environment` — это гонки в языке, где переменная модуля живая и общая. Если понадобится,
  честный путь один: явная блокировка запуска, отпускаемая только на `await`, то есть
  GIL со всеми его следствиями. До первого настоящего требования этого делать не стоит:
  `awaitAll` закрывает параллельные запросы, а они и есть 90 % задачи.
* **Колбэков, которые зовёт Java-поток.** См. 8.1. Единственный способ отдать управление
  скрипту — вернуть значение из функции, которую скрипт сам вызвал.

## 9. Раскладка по gradle-модулям

Инвариант «у `wdl-core` ноль внешних runtime-зависимостей» не двигается, и он же
диктует раскладку:

| Модуль | Что внутри | Зависимости |
|---|---|---|
| `wdl-core` | `ModuleProvider`, `Library`, `NativeClass`, `NativeTrait` — API и ничего больше | нет |
| `wdl-stdlib` | `sys.json`, `sys.io`, `sys.net.http`, `sys.time` — всё на JDK (`java.net.http`, `java.nio`) | core |
| `wdl-mod-<имя>` | обёртки сторонних библиотек, по jar на библиотеку | core (+ своя) |
| `wdl-cli` | список того, что подключено по умолчанию, и флаг для остального | api, tools, stdlib |

JSON пишется своим разборщиком в `wdl-stdlib` — он маленький, а тянуть зависимость
в библиотеку, которая идёт по умолчанию, значит навязывать её всем встраивающим.
Обёртка `org.json` или Jackson, если понадобится, живёт отдельным `wdl-mod-*`
и подключается тем, кому нужна именно она.

### Имена ключей

`sys.*` — то, что даёт движок. Всё остальное именуется по задаче, а не по Java-пакету:
`import json`, а не `import org.json`. Причина простая: обёртка не повторяет чужой API
один в один, и обещать это именем нечестно — сегодня внутри `org.json`, завтра Jackson,
а скрипты переписывать. Имя Java-пакета уместно ровно тогда, когда модуль
и вправду буквальный мост к конкретной библиотеке и меняться не может.

## 10. Безопасность достаётся даром

Скрипту доступно ровно то, что приложение зарегистрировало. Не дали `sys.net` — его нет,
и обойти это нечем: глобальной таблицы модулей в языке не существует, как не существует
таблицы библиотек и таблицы функций. Ограничение по подмножеству пишется обёрткой
над провайдером в три строки, а тест подменяет `sys/net` фейком, зарегистрировав
под тем же ключом свою фабрику.

Это прямое следствие того, что реестр — параметр запуска, а не статика.

## 11. Этапы

1. **`ModuleProvider` и нативные модули без классов.** Поиск переезжает из `ModuleUnits`
   в `Modules`, `visitImport` учится отличать имя от пути, появляется `ofNatives`.
   Приёмка: `import sys.json as json; println(json.parse("{\"a\":1}").a)` печатает `1`,
   а `import std as s; println(s.pow(2, 10))` работает без единой правки в `Std`.
2. **`sys.json`, `sys.io`, `sys.time`** в `wdl-stdlib` — три модуля, на которых видно,
   что API достаточно, и заодно первый набор примеров в `examples/modules/`.
3. **`NativeTrait` и `.extending` у `NativeClass`** (6.1 и 6.2). Приёмка: класс на wdl
   реализует нативный трейт, забытое требование даёт ошибку на строке `class`.
4. **Жизненный цикл** (`Library.close`, `Modules.shutdown`, `finally` в CLI).
5. **`sys.net.http` и `await`** (8.2–8.3) — после жизненного цикла, потому что пул
   соединений закрывать надо.
6. **`sys.net.Server`** и событийный цикл (8.4) — отдельной задачей.
7. **Наследование от нативного класса** (6.3) — только по требованию.

## 12. Что надо будет записать в документацию

* `docs/embedding.md` — раздел «Модуль на Java»: `Library` + ключ, фабрика вместо
  готового значения, `close`.
* `docs/modules.md` — раздел «Встроенные модули»: имя против пути (раздел 3 этого
  документа), и что состав встроенных задаёт запуск.
* Новый `docs/async.md` — правило «чужой поток не входит в интерпретатор» и то,
  что из него следует для автора скрипта.
* `README.md` — состояние: какие `sys.*` есть.

## 13. Тесты, которые понадобятся

* `import` встроенного модуля из файла в подкаталоге — ключ не зависит от каталога;
* `import "./sys/json"` при зарегистрированном `sys/json` — берётся файл;
* фабрика зовётся один раз на два `import` и **ни разу**, если импорта не было;
* фабрика бросила `NoClassDefFoundError` — ошибка на строке `import` с внятным текстом;
* нативный и файловый модуль ведут себя одинаково: `typeof`, печать, опечатка в имени,
  запрет присваивания;
* класс на wdl реализует нативный трейт; забытый метод — ошибка на строке `class`;
* `shutdown` закрывает библиотеки в обратном порядке и переживает ошибку в `close`;
* `awaitAll` на двух задержках занимает время большей, а не суммы.

## 14. Открытые вопросы

* **Выборочный импорт** (`import sys.json as {parse}`) для нативных хочется сильнее,
  чем для файлов, — но это общая фича языка, и решаться должна для обоих сразу.
* **Версии модулей.** Ключ ничего не говорит о версии. Пока приложение одно и собирает
  classpath само — не проблема; для площадки с чужими плагинами понадобится.
* **Мост к произвольному Java-объекту** (`player.getName()` без описания класса руками)
  остаётся в списке «чего пока нет» из `docs/embedding.md`. Нативные модули его
  не приближают и не отменяют: это другая ветка реализации того же обращения по ключу.

## 15. Что получилось

Сборка и тесты зелёные: `./gradlew build`.

### Код

| Появилось | Что делает |
|---|---|
| `module/NativeModules` | реестр «имя → фабрика библиотеки»: `of(Map)`, `first(a, b)`, `none()`/`NONE` |
| `module/ModuleKey.name`, `.isExplicitPath` | превращение записи в имя и признак «речь заведомо о файле» |
| `embed/Library.close()` | необязательное закрытие ресурсов, по умолчанию пустое |
| `runtime/Modules` — ветка встроенных | установка библиотеки в `ModuleScope`, свой реестр выполненных, `shutdown()` |
| `ExecutionContext.withNativeModules`, `.shutdownModules()` | как задать набор и как закрыть его в конце запуска |
| `stdlib/Json`, `JsonReader`, `JsonWriter` | `sys.json` со своим разбором и записью, без зависимостей |
| `stdlib/Io` | `sys.io`: функции над путём плюс тот же класс `File`, что в `std` |
| `stdlib/Http` | `sys.net.http`: синхронный клиент, класс `Response`, ленивое создание и `close()` |
| `stdlib/Sys` | готовый набор `std`, `sys.io`, `sys.json`, `sys.net.http` для запуска |

Правок в интерпретаторе — одна строка: `visitImport` больше не разрешает путь сам,
а отдаёт запись реестру. Ни нового вида значения, ни нового `ValueType`,
ни ветки «а это встроенный» в вычислении выражений не появилось.

### Отличия от плана

1. **Вместо цепочки `ModuleProvider` — два реестра.** План предлагал один провайдер
   с ответом `Script | Native` и порядком, который задаёт приложение. Но раздел 3
   принял правило «встроенный ищется по имени, файл — по пути», а оно делает порядок
   предопределённым: цепочке нечего решать. Поэтому `ModuleSource` остался как был,
   а рядом встал независимый `NativeModules`. Заодно исчезла неприятность, которую
   цепочка тянула за собой: единый поиск заставлял бы спрашивать файл дважды,
   то есть читать его с диска впустую.
2. **Реестра выполненных модулей тоже два.** Из того же правила: ключ `sys/json`
   означает разное для встроенного модуля и для файла `./sys/json`, и в одной таблице
   они бы столкнулись.
3. **`Loaded.missing`** — новое поле в итоге загрузки: ошибка «модуль не найден»
   должна называть оба места, где искали, а «в модуле есть ошибки» — не должна.
   Про встроенные при этом не поминается, если их в запуске нет вовсе.
4. **`sys.io` вместо только класса `File`.** План говорил про модуль, но не про состав;
   в итоге в модуле и функции (`io.read(path)` одной строкой), и класс — они закрывают
   разные случаи, а `File` при этом тот же самый объект, что кладёт `std`.

### Что изменилось для автора скрипта

* `import sys.json`, `import sys.io`, `import sys.net.http` и `import std` работают
  в консольном запуске; для встроенного движка состав задаёт приложение;
* имя встроенного модуля не зависит от каталога файла, где написан `import`,
  а `import "./sys/json"` по-прежнему означает файл;
* JSON превращается в обычные объекты и массивы, а не в обёртки, поэтому к нему
  применимо всё, что язык уже умеет;
* ответ HTTP — обычный класс с полями, и `r.status`, `r.headers["content-type"]`,
  `r is http.Response` работают без единой строчки нового синтаксиса.
