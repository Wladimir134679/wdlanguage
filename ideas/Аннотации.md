# Аннотации: `@{...}`

> **Сделано.** Описание живёт в [`docs/annotations.md`](../docs/annotations.md),
> рабочий пример — в [`examples/annotations.wdl`](../examples/annotations.wdl),
> журнал работы — в [`plans/ПланАннотаций.md`](../plans/ПланАннотаций.md).
> Этот файл остаётся историей решения — как `plans/ПланРеализацияДекораторов.md`
> рядом с `docs/decorators.md`, — и не обновляется: то, что здесь расходится
> с `docs/`, устарело, а не отменено.
>
> Разошлось с реализацией немногое: описание параметра — обычный объект, поэтому
> аннотации у него читаются как `p["annotations"]`; `typeof(x) == "number"` в языке
> не работает (`typeof` отдаёт дескриптор — пишется `x is Number`); а `Cls.method(имя)`
> и `Cls.property(имя)` из «второго этапа рефлексии» сделаны сразу.

## Одной строкой

Аннотация — **данные, приписанные объявлению и доступные потом**. Не действие,
не проверка, не тип. Пишется перед объявлением объектным литералом, хранится в самом
объявленном значении, читается членом `annotations` — тем же путём, что `f.name`
и `Cls.params`.

```wdl
@{route: "/users", method: "GET"}
def listUsers(page = 1) => db.users(page)

println(listUsers.annotations["route"])     // /users
```

## Чем это не является

**Не декоратор.** Декоратор отвечает на вопрос «что сделать в момент объявления»,
аннотация — «что про это известно». Разница видна на времени: декоратор отработал
и исчез, аннотация лежит и ждёт того, кто спросит.

|  | Декоратор `@[...]` | Аннотация `@{...}` |
|---|---|---|
| Что это | функция | объект |
| Когда работает | в момент объявления | никогда — она данные |
| Может подменить цель | да | нет |
| Виден потом | нет, если сам не зарегистрировался | да, через `annotations` |
| Сколько потребителей | один — он сам | сколько угодно, не знающих друг о друге |

Смешение этих двух ролей — известная беда JS-декораторов: `@Component({...})` там
одновременно данные и побочный эффект, и прочитать метаданные, не выполнив
регистрацию, нельзя. Java разделила и выиграла; здесь делается то же самое.

**Не система типов.** `@{type: "int"}` — строка в объекте, движок про неё не знает
ничего и ничего не проверяет. Проверку пишет тот, кому она нужна.

**Не декларация с гарантиями.** Аннотация не мешает вызвать функцию, создать объект,
записать поле. Всё, что она делает, — существует.

## Зачем, если декораторы уже есть

Честно: почти всё это делает декоратор-регистратор, и делает **сегодня**, без единой
правки движка — ключом карты может быть любое значение, а у функции равенство
по тождеству:

```wdl
META = {}
def annotate(meta, data) { META[meta.target] = data }

@[annotate]({route: "/users"})
def listUsers() { }

println(META[listUsers]["route"])       // /users — работает уже сейчас
```

Аннотации покупают три вещи, и это же критерий, когда их брать, а когда нет.

1. **Потребителей несколько, и они не знают друг о друге.** Валидатор, сериализатор
   и генератор документации читают одни данные. С декораторами это три реестра,
   три импорта и три строки обвеса над каждым объявлением.
2. **Данные объявляются без объявления функции.** Чтобы написать `@{max: 100}`, не нужно
   заранее завести `maxLength`, положить её в модуль и импортировать. Порог входа
   для «просто пометить» падает до нуля — а именно на этом пороге метаданные обычно
   и не пишут.
3. **Данные видны инструментам.** Аннотация лежит в дереве: форматтер, будущий линтер,
   LSP и `--ast` её видят, не выполняя код. Декоратор в дереве — просто выражение,
   и что оно регистрирует, до выполнения не знает никто.

**Если потребитель ровно один и работает в момент объявления — это декоратор.**
Аннотация там лишняя сущность.

## Синтаксис

```
@{ключ: значение, ...}
```

Внутри — обычный литерал объекта: ключ-имя без кавычек, ключ-строка, ключ-выражение
в скобках. Значение — любое выражение, включая вызов.

```wdl
@{table: "users"}
class User(id, name) { }

@{schema: buildSchema("user.json"), since: version(), (KEY): 1}
def handler() { }
```

Несколько блоков подряд **сливаются в один объект**:

```wdl
@{route: "/users"}
@{method: "GET", auth: true}
def listUsers() { }

listUsers.annotations       // {route: "/users", method: "GET", auth: true}
```

Одинаковый ключ в двух блоках — **ошибка**, а не «последний победил». Та же причина,
что у коллизии в аргументах: блоки независимы, порядок их записи ничего не значит
для читателя, и молчаливый выбор одного из двух означал бы, что смысл программы
зависит от того, какой блок автор напечатал первым.

Пустая `@{}` разрешена и даёт пустой объект — запрещать нечего, но и смысла в ней нет:
для потребителя она неотличима от отсутствия аннотаций.

## На что вешается

**Ровно туда же, куда декоратор, плюс параметры.** Одно правило вместо двух — это
и есть причина, по которой список именно такой.

```wdl
@{a: 1} def command() { }               // да
@{a: 1} class Command(id) { }           // да
@{a: 1} trait Printable { }             // да

class User(
    @{column: "id", primary: true} id,          // да — параметр заголовка
    @{column: "full_name", max: 100} name
) {
    @{transactional: true}
    def save() { }                              // да — метод

    @{computed: true}
    property label => name + " #" + id          // да — свойство

    @{factory: true}
    def of(row) => new User(row.id, row.name)   // да — фабрика
}

def total(@{min: 0} price, @{min: 1} count = 1) => price * count    // да — параметр
```

Не цель:

```wdl
@{max: 100} x = 1               // ошибка: аннотация вешается на объявление
@{a: 1} f = def (x) => x        // ошибка: у анонимной функции нет объявления
@{a: 1} import sys.io           // ошибка
```

### Почему не на переменную

Это главный отказ в дизайне, и причина техническая, а не вкусовая.

Аннотация должна к чему-то привязываться. Привязка к значению работает только там,
где у значения есть **тождество**. У функции, класса, трейта, экземпляра оно есть.
У числа, строки, диапазона — нет: это записи, равные по содержимому.

```wdl
@{max: 100} count = 5
other = 5
// откуда движку знать, что эта пятёрка — не та же самая?
```

Любая пятёрка в программе — та же пятёрка. Аннотация на переменной либо протекла бы
на все одинаковые значения, либо должна была бы вешаться не на значение,
а на **связывание имени в области** — а связывание не значение, его не передать
в `annotations`, и понадобился бы второй способ доступа вида
`annotationsOf(scope, "count")`, который разваливается на замыканиях, вложенных
областях и переприсваивании.

Практика от этого не страдает: поле класса — это параметр заголовка, а его
аннотировать можно. Переменная верхнего уровня, которую надо описать снаружи, —
редкий случай, и он закрывается полем класса или константой в объекте.

### Позиция относительно декораторов и модификаторов

Разрешено вперемешку, порядок записи роли не играет:

```wdl
@{route: "/users"}
@[traced]
@{auth: true}
synchronized def listUsers() { }
```

**Аннотации всех блоков собираются и применяются к цели до того, как отработает
первый декоратор.** Иначе `@[deco] @{a: 1}` и `@{a: 1} @[deco]` значили бы разное,
а разницы в записи читатель не заметит. Из этого же следует самое полезное:
декоратор видит аннотации своей цели.

```wdl
ROUTES = {}

def route(meta) {
    a = meta.target.annotations
    ROUTES[a["route"]] = meta.target
}

@{route: "/users", method: "GET"}
@[route]
def listUsers() { }
```

По стилю аннотации ставятся выше декораторов: сначала «что это», потом «что с этим
сделать».

## Где хранятся

**В самом значении**, неизменяемым объектом: поле в `FunctionValue`, `ClassValue`,
`TraitValue`, ключ в `Signature.Param`. Глобального реестра нет.

Альтернатива — карта «значение → аннотации» на запуске — отвергнута, и вот почему:

* **утечка.** Ключи пришлось бы держать слабыми, иначе каждая функция, созданная
  в цикле, живёт до конца запуска. Нужного класса в JDK нет: `WeakHashMap` не по
  тождеству, `IdentityHashMap` не слабый, `ConcurrentHashMap` ни то ни другое —
  пришлось бы писать свой с `ReferenceQueue`, и писать в ядре;
* **потоки.** Долгоживущее изменяемое состояние в ядре обязано быть конкурентным
  или под замком — глобального замка больше нет (`docs/threads.md`). Поле в значении,
  заполненное при создании и дальше неизменное, безопасно по построению;
* **время жизни.** Аннотации должны умирать вместе с функцией. В поле это так само
  собой, в реестре — только если не забыть.

Отсюда же следует, что **аннотации неизменяемы**: `annotations.clear(f)` в языке нет
и не будет. Изменяемая свалка метаданных ломает воспроизводимость — результат
начинает зависеть от порядка импортов: чужая библиотека вычистила аннотации у общего
класса, и валидатор перестал видеть правила. Она же требует замка на каждое чтение
и превращает `annotations` в вопрос «а кто уже успел». Нужны изменяемые метаданные —
это обычная карта, и она в языке уже есть: `STATE[f] = {...}`.

## Чтение

Тем же путём, что вся остальная интроспекция, — **членом значения, а не модулем**.
Отдельный `reflection` был бы вторым путём к той же категории фактов, а рядом
с `f.name`, `f.params`, `Cls.methods` он ещё и разошёлся бы по стилю.

```wdl
f.annotations               // объект; snapshot — копия на каждое чтение
Cls.annotations
Trait.annotations

Cls.params[0].annotations   // поле заголовка: новый ключ в уже существующем описании
f.params[0].annotations     // параметр функции — тот же ключ
```

`annotations` — **`snapshot`**, а не `property`: возвращается копия, чтобы запись
в неё не портила само объявление. По той же причине снимками отдаются `Cls.methods`
и `Cls.properties`. Для линтера это заодно значит «не звать в цикле».

Аннотаций нет — возвращается **пустой объект, а не `null`**. Здесь нет различия
«неизвестно» и «пусто», которое заставило `params` отдавать `null` у контракта без
имён: аннотация либо написана, либо не написана. У встроенных функций и у классов
приложения `annotations` тоже пустой.

Проверка ключа отдельным членом не нужна — у объекта уже есть `has`:

```wdl
if (f.annotations.has("route")) { ... }
for (key in f.annotations) println(key, " = ", f.annotations[key])
```

### Методы и свойства класса: чего пока нет

`Cls.methods` и `Cls.properties` отдают **имена строками** — значения у них снаружи
не существует. Чтобы добраться до аннотаций метода, нужны два новых члена:

```wdl
Cls.method("save").annotations        // метод — обычная функция, у неё уже есть annotations
Cls.property("label").annotations     // свойство — объект-описание {name, readonly, annotations}
```

Это добавка к существующей рефлексии, а не часть аннотаций: `Cls.method(name)`
полезен сам по себе. Поэтому он вынесен в отдельный этап — аннотации на функциях,
классах, трейтах и параметрах работают и без него.

### Наследование: его нет

`Cls.annotations` — только свои. Родительские берутся у родителя, и склеивает их тот,
кому это нужно: политика склейки у каждого потребителя своя, и выбирать её за него
язык не должен.

```wdl
def inherited(cls) {
    return cls.parent == null
        ? cls.annotations
        : {**inherited(cls.parent), **cls.annotations};      // ближний побеждает
}
```

Ровно за этим и нужно слияние объектов — следующий раздел.

## Связанная возможность: `*` и `**` в литералах

Раскрытие в языке уже есть — в вызовах: `f(*values, **options)`. Та же пара символов
работает и в литералах массива и объекта. Второго синтаксиса (`...` из JS) не будет:
два способа сказать одно — это выбор, который читателю приходится делать на каждой
строке.

```wdl
head = [1, 2]
values = [*head, 3, 4]                      // [1, 2, 3, 4]

defaults = {retries: 3, timeout: 30}
options  = {**defaults, timeout: 60}        // {retries: 3, timeout: 60}
merged   = {**defaults, **overrides}
```

**В литерале действует «последний победил», хотя в вызове коллизия — ошибка.**
Разойтись здесь можно, потому что причина запрета в вызове тут не действует.
В вызове `f(*arr, **map)` массив и объект — два независимых источника, и порядок их
объединения читателю не виден; в литерале порядок написан автором явно, слева
направо, и переопределение — ровно то, зачем сливают. Запрет коллизий сделал бы
`{**defaults, timeout: 60}` невыразимым, а это самый частый случай.

Раскрывать можно только подходящее: `*` — массив или диапазон, `**` — объект.
`{**[1, 2]}` — ошибка: у элементов массива нет ключей.

## Сценарии

### 1. Роутинг: аннотация несёт данные, декоратор регистрирует

Разделение труда, ради которого всё и затевалось.

```wdl
ROUTES = []

def route(meta) {
    a = meta.target.annotations
    ROUTES.push({**a, handler: meta.target, name: meta.name})
}

@{path: "/users", method: "GET", auth: false}
@[route]
def listUsers(page = 1) => db.users(page)

@{path: "/users", method: "POST", auth: true}
@[route]
def createUser(body) => db.insert(body)

def dispatch(method, path, request) {
    for (r in ROUTES) {
        if (r["method"] == method && r["path"] == path) {
            if (r["auth"] && request.user == null) throw new Exception("нужна авторизация")
            return r["handler"](request);
        }
    }
    throw new Exception("нет обработчика: " + method + " " + path);
}
```

Второй потребитель тех же данных не трогает ни одного объявления:

```wdl
def openapi() {
    doc = []
    for (r in ROUTES) doc.push(r["method"] + " " + r["path"])
    return doc.join("\n");
}
```

### 2. Валидация полей по заголовку класса

Аннотация на параметре — она же аннотация на поле.

```wdl
class User(
    @{required: true, max: 50} name,
    @{min: 0, max: 150} age = 0,
    @{contains: "@"} email = ""
) { }

def validate(cls, instance) {
    errors = []
    for (p in cls.params) {
        a = p.annotations
        value = instance[p.name]

        if (a.get("required", false) && value == "") {
            errors.push(p.name + ": обязательное поле")
        }
        if (a.has("max") && typeof(value) == "number" && value > a["max"]) {
            errors.push(p.name + ": не больше " + a["max"])
        }
        if (a.has("contains") && !(a["contains"] in value)) {
            errors.push(p.name + ": ожидается " + a["contains"])
        }
    }
    return errors;
}

println(validate(User, new User("", 200, "нет")))
// ["name: обязательное поле", "age: не больше 150", "email: ожидается @"]
```

Здесь же видно, чего аннотации **не** делают: `new User("", 200, "нет")` создался
без единой жалобы. Проверку зовут явно.

### 3. Сериализация: одни данные, три потребителя

```wdl
@{table: "users"}
class User(
    @{column: "id", primary: true} id,
    @{column: "full_name", json: "fullName"} name,
    @{column: "created_at", json: "createdAt", readonly: true} created = null
) { }

def toJson(cls, instance) {
    result = {}
    for (p in cls.params) {
        key = p.annotations.get("json", p.name)      // get с запасным значением
        result[key] = instance[p.name]
    }
    return result;
}

def insertSql(cls) {
    columns = []
    for (p in cls.params) {
        if (!p.annotations.get("readonly", false)) columns.push(p.annotations["column"])
    }
    return "INSERT INTO " + cls.annotations["table"] + " (" + columns.join(", ") + ")";
}
```

Третий потребитель — генератор формы для `sys.gui` — пишется так же и снова
не требует правок в классе. Это и есть случай, где декораторы проигрывают: три
обвеса вместо одной пометки.

### 4. Тестовый фреймворк на самом языке

В `examples/testing/` он уже есть; аннотации снимают с него разбор имён.

```wdl
@{test: true, name: "сложение целых"}
def additionWorks() { assertEquals(2 + 2, 4) }

@{test: true, skip: "падает на Windows", issue: 42}
def pathsAreNormalized() { }

@{test: true, timeout: 500, tags: ["slow", "io"]}
def readsBigFile() { }

def run(suite) {
    for (name in suite) {
        f = suite[name]
        a = f.annotations
        if (!a.get("test", false)) continue
        title = a.get("name", f.name)
        if (a.has("skip")) {
            println("SKIP ", title, " — ", a["skip"])
            continue
        }
        try { f(); println("OK   ", title) }
        catch (e) { println("FAIL ", title, ": ", e.message) }
    }
}
```

`@{skip: "причина"}` вместо `@[skip]("причина")` выигрывает ровно в том, что причина
и номер задачи остаются данными: их можно напечатать в отчёте, сгруппировать,
проверить линтером на «skip без issue».

### 5. Сборка CLI по функции

`examples/introspection.wdl` уже собирает вызов по `f.params`. Аннотации добавляют
то, чего в сигнатуре нет и быть не может, — текст справки.

```wdl
@{command: "deploy", help: "выкатить сборку на стенд"}
def deploy(
    @{help: "имя стенда", short: "e"} env,
    @{help: "версия; по умолчанию последняя", short: "v"} version = "latest",
    @{help: "не спрашивать подтверждения", flag: true} force = false
) { }

def usage(f) {
    a = f.annotations
    lines = [a["command"] + " — " + a["help"], ""]
    for (p in f.params) {
        pa = p.annotations
        flag = "--" + p.name + (pa.has("short") ? ", -" + pa["short"] : "")
        lines.push("  " + flag + "  " + pa.get("help", "") + (p.required ? " (обязательно)" : ""))
    }
    return lines.join("\n");
}
```

### 6. Слой над мостом в Java

`@{}` на классе-обёртке держит то, что сейчас живёт в комментарии: какой Java-тип
за ним стоит и что с ним нельзя делать.

```wdl
@{backing: "javax.swing.JButton", threadSafe: false, since: "0.4"}
class Button(text = "") { }
```

Движок это не читает — читают документатор и линтер, который ругается на вызов
не из потока GUI.

## Чего аннотации не делают

* **Не проверяют.** `@{max: 100}` не мешает записать 200. Проверку зовут явно.
* **Не выполняются.** Значение вычисляется один раз, при проходе объявления; побочный
  эффект внутри `@{...}` сработает и будет сюрпризом — то же предупреждение, что
  и для декораторов. Объявление внутри функции проходится на каждом вызове,
  и аннотация вместе с ним.
* **Не наследуются.** См. выше.
* **Не изменяются.** `clear` нет.
* **Не видны экземпляру напрямую.** `instance.annotations` — это обычное обращение
  к полю `annotations`, если автор его завёл. Аннотации класса берутся у класса.
  Иначе член затирал бы данные, а правило «данные раньше членов» одно на весь язык.
* **Не участвуют в равенстве и печати.** Два класса с разными аннотациями различны
  и без них — это и так разные значения.

## Открытые вопросы

1. **От экземпляра к классу.** В сценариях 2 и 3 класс передан аргументом, потому что
   способа спросить класс у экземпляра под рукой не оказалось. Если такого пути в языке
   нет, его стоит завести отдельно — на аннотациях это скажется в половине сценариев.
2. **Аннотации через мост.** Должен ли `NativeClass` уметь объявлять аннотации и должен
   ли `FromJava` переносить Java-аннотации открытого типа? Скорее да для первого (одна
   строка в построителе) и нет для второго — чужая модель метаданных протечёт в язык.
3. **`extend`.** Член, добавленный через `extend`, аннотаций не имеет. Разрешать ли их
   там — вопрос к тому, как `extend` вообще относится к рефлексии.
4. **Короткая форма.** `@name(...)` в стиле Java здесь невозможна: она неотличима
   от декоратора без скобок, который сознательно отложен. Вопрос закрыт — короткой
   формы у аннотаций не будет.
5. **Аннотация на модуле или файле.** `@{version: "1.0"}` в начале файла выглядит
   осмысленно, но цель («файл») в языке не значение. Отложено.

## План реализации

**Этап 0. Слияние в литералах** — независим от аннотаций и полезен сам по себе.
`ObjectExpr.Entry` и `ArrayExpr` получают форму записи (как `Argument.Kind`),
`Interpreter` раскрывает при сборке литерала, правило «последний победил» —
в `docs/expressions.md` вместе с причиной отличия от вызова. Тесты: форма дерева
в `ParserTest`, результат и ошибки типа в `InterpreterTest`.

**Этап 1. Дерево.** Запись `@{...}` в `Parser` там же, где читаются декораторы; поле
аннотаций в `DecoratedStmt` (или соседний узел — решается по тому, во что превращается
`DecoratedStmt` без декораторов), в `FunctionExpr.Param` и в `ClassDeclStmt`. Разбор
не должен ломаться на `@{` без объявления после него: диагностика и `ErrorStmt`,
как везде.

**Этап 2. Значения.** Неизменяемое поле в `FunctionValue`, `ClassValue`, `TraitValue`
и в `Signature.Param`; заполняется при создании значения, до применения декораторов.
`like` переносит аннотации вместе с именем и арностью — без этого обёрнутая
декоратором функция теряет аннотации, и роутер из сценария 1 не находит ничего.

**Этап 3. Чтение.** `snapshot("annotations", ...)` в `FunctionMembers`, `ClassMembers`,
`TraitMembers`; ключ `annotations` в `Introspection.params`. Ни `Interpreter`,
ни таблицу членов трогать не надо — путь через дескриптор и диагностика промаха
собираются сами.

**Этап 4. Инструменты.** `AstDumper` печатает аннотации, `--ast` показывает их
на объявлении.

**Этап 5. Второй этап рефлексии** (можно отложить): `Cls.method(name)`,
`Cls.property(name)`.

**Этап 6. Документы.** `docs/annotations.md` со строкой в таблице `docs/README.md`,
раздел «Декоратор или аннотация» с критерием из начала этого файла, пример
`examples/annotations.wdl` (роутинг, валидация и отчёт по одним данным), строка
в `examples/README.md`, состояние — в `README.md` и `docs/overview.md`.
