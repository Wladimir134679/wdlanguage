# Лимиты выполнения

Пределы, под которыми работает запуск: сколько скрипту можно **шагов**, **времени**,
**потоков** и **вложенности вызовов**. Это то, чем движок отвечает на вопрос «а если
скрипт чужой»: без лимитов `while (true) {}` висит навсегда, а `for (;;) th.spawn(...)`
кладёт не скрипт, а приложение, в которое движок встроен.

Лимиты — свойство **запуска**, а не языка: в тексте скрипта их нет и быть не может.
Ставит их тот, кто запускает, — приложение или консольный `wdl`.

## Коротко

```java
WdlEngine engine = WdlEngine.builder()
        .stdlib(Stdlib.SAFE)          // модули + Limits.safeDefaults()
        .maxSteps(10_000_000)         // своё поверх умолчания
        .timeout(Duration.ofSeconds(5))
        .maxThreads(4)
        .build();
```

```bash
wdl --max-steps=1000000 --timeout=5 --max-threads=4 script.wdl
```

По умолчанию лимитов **нет**: движок не платит за то, о чём его не просили, — то же
правило, что у вывода в никуда и у выключенных метрик. Исключение одно и осмысленное:
набор `Stdlib.SAFE` ставит `Limits.safeDefaults()` сам (сто миллионов шагов, тридцать
секунд, восемь потоков), потому что своё обещание — «скрипт от пользователя не уронит
хозяина» — без них не держит.

## Что считается шагом

Шаг — это **итерация цикла** (`while`, `for`, перебор) и **вход в тело функции или
конструктора**. Не узел дерева и не операция.

Причина в двух словах: зациклиться, не пройдя ни разу ни через итерацию, ни через
вызов, нельзя, а счётчик на каждом узле пришлось бы платить в самой горячей точке
интерпретатора — ради точности, которой никто не пользуется. Вопрос лимита звучит
как «скрипт зациклился?», а не «сколько именно сложений он сделал».

```
скрипт.wdl:2:1: ошибка: выполнение остановлено: скрипт исчерпал отведённые 500 шагов.
Проверьте условие выхода из цикла или рекурсии
```

Счётчик **один на запуск**, а не на поток: восемь потоков по лимиту каждому — это
не лимит. Чтобы общий счётчик не стал точкой раздора, поток копит шаги у себя и вливает
их в общий раз в двести пятьдесят шесть; предел меньше этого числа работает точно —
батч подрезается под него.

## Время: два слоя

**Мягкий дедлайн** проверяется в тех же точках, что и шаги, и даёт остановку с местом
в исходнике:

```
скрипт.wdl:1:1: ошибка: выполнение остановлено: вышло отведённое время (5000 мс)
```

**Сторож** — отдельный поток, который заводится на первом входе в скрипт, если таймаут
задан, и по истечении срока прерывает всех, кто внутри запуска. Он нужен потому, что
скрипт, ушедший в `th.sleep(600000)`, в чтение из сокета или в ожидание замка, ни одной
точки проверки не проходит и мягкий дедлайн его не достанет. Прерывание блокирующие
библиотеки уже понимают и отвечают на него остановкой выполнения — той же, что и
на `t.interrupt()`.

Называется остановка при этом всё равно таймаутом: библиотека знает только про
прерывание, а причину подставляет граница запуска — иначе хозяин, поставивший
таймаут, читал бы «выполнение прервано» и искал, кто же нажал стоп.

```
скрипт.wdl:3:1: ошибка: выполнение остановлено: вышло отведённое время (1000 мс)
  3 | th.sleep(600000)
    | ^^^^^^^^^^^^^^^^
```

Отсчёт идёт от **первого входа в скрипт**, а не от сборки движка: чтение файлов и разбор
модулей не должны съедать бюджет скрипта.

Поток приложения, вошедший в скрипт, сторож прерывает наравне с остальными — он внутри
скрипта, — но флаг прерывания наружу не уходит: на границе выхода запуск его гасит.
Иначе приложение получило бы `InterruptedException` где-нибудь в своём коде через
десять минут после того, как забыло про скрипт.

## Потоки

`maxThreads` — сколько потоков скрипт вправе держать одновременно. Считаются оба способа
их завести:

* `th.spawn(...)` — один поток, место освобождается, когда поток закончился;
* `th.pool(n)` — сразу `n` мест, освобождаются при закрытии пула. По числу потоков,
  которое пул вправе держать, а не по числу заведённых: иначе `th.pool(1000)` проходил бы
  любую проверку, пока в него не положили задачу.

Отказ — **обычная ошибка скрипта**, а не остановка выполнения, и это единственный лимит,
устроенный так:

```wdl
try {
    worker = th.spawn(job)
} catch (e) {
    println("потоков нет, сделаю сам: ", e.message)
}
```

Разница с остальными лимитами в том, что «потоков больше не дам» — про неудавшуюся
операцию, а не про остановленное выполнение: подождать и попробовать снова — законное
поведение. Обойти этим лимит нельзя: цикл, вечно ловящий отказ, не создаёт ни одного
потока и упирается в шаги и время.

## Вложенность вызовов

`maxCallDepth` (по умолчанию 256) и `maxEntries` (32) — не про чужой скрипт, а про стек:
бесконечная рекурсия обязана давать ошибку с местом в исходнике, а не
`StackOverflowError` в чужом приложении. Поэтому они работают **всегда**, даже когда
остальных лимитов нет.

`maxEntries` считает цепочку «скрипт → приложение → скрипт» на одном потоке: кадры
скрипта на каждом внешнем входе начинаются заново, и `maxCallDepth` такую цепочку
не видит.

## Исчерпание лимита нельзя поймать

Остановка по шагам и по времени — `FatalError`: она не ловится ни `catch (e)`,
ни `catch (e is ...)`, ни `try?`. Иначе

```wdl
while (true) {
    try { ... } catch (e) { }      // съел бы собственный предохранитель
}
```

работал бы вечно — ровно то, ради чего лимит и ставили.

`defer`, `finally` и `use` при этом **выполняются**: закрыть своё на пути наружу можно
и нужно, а подавить причину — нет.

```wdl
def process() {
    defer println("файл закрыт")
    while (true) { }
}
```

Скрипт остановится по лимиту, и «файл закрыт» будет напечатано.

## Чего лимитами не закрыть

* **Одну долгую операцию на Java.** Сортировка массива на миллион элементов,
  регулярное выражение с возвратом, тяжёлый разбор JSON — не проходят ни одной точки
  проверки и не блокируются, значит их не достаёт ни дедлайн, ни сторож. Средства
  прервать такое в JVM нет: `Thread.stop` убран, и заменять его нечем. Единственная
  защита — не давать недоверенному скрипту тех модулей, где такая операция бывает
  дорогой.
* **Память.** Ни размера значений, ни числа объектов движок не считает: `a = a + a`
  в цикле съест кучу раньше, чем кончатся шаги. Это отдельная работа — учёт в каждом
  контейнере, — и она не про безопасность цикла.
* **Файлы, сокеты и окна.** Это не лимиты, а **набор**: не положил `sys.io` — читать
  нечего. См. [встраивание](embedding.md).

## Как это устроено внутри

| Что | Где |
|---|---|
| Значения пределов | `runtime.Limits` — неизменяемый `record`, ноль значит «без предела» |
| Счётчики, дедлайн, сторож | `runtime.Run` — сеанс, которому лимиты и принадлежат |
| Единственная точка проверки | `Run.checkpoint(span)` — прерывание, шаги, время |
| Точки вызова | циклы `Interpreter`, `UserFunction.body`, `WdlClass.create` |
| Квота потоков | `runtime.RunThreads` — один счёт на `spawn` и на пулы |
| Сообщения | `FatalError.stepsExhausted`, `timedOut`, `tooDeep` |

Выключенные лимиты стоят ровно столько же, сколько стоила прежняя проверка флага
прерывания: чтение поля и сравнение. Ни `System.nanoTime()`, ни общего счётчика
на этом пути нет.
