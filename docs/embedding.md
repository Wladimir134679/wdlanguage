# Встраивание: свои классы и функции

Приложение добавляет в язык своё — функции, классы, константы — и скрипт не видит
разницы между ними и написанным на wdl. Это не отдельный механизм: класс на Java
и класс на wdl — две реализации одного интерфейса, и интерпретатор их не различает.

```java
Environment scope = Builtins.installTo(Scope.root());
Std.install(scope);                     // стандартная библиотека
scope.define("app", myApplicationValue); // и что угодно ещё
```

```wdl
f = new File("данные.txt")
f.write("привет")
println(f.read(), " ", f.path, " ", f is File)   // привет данные.txt true
```

## Четыре вещи, которые можно положить в область видимости

### Функция

```java
scope.define("pow", BuiltinFunction.of("pow", Arity.exactly(2), (context, args, span) -> {
    NumberValue base = args.number(0, "основание");
    NumberValue exponent = args.number(1, "показатель");
    ...
}));
```

Число аргументов проверяется до входа в тело, по `Arity`, — тем же кодом и с тем же
сообщением, что у функций языка. Поэтому тело начинается с дела, а не с проверок.
`context` даёт вывод (`context.write(...)`), `span` — место вызова в исходнике
для ошибок.

Аргументы приходят объектом `Args` — обычным `List<Value>`, который вдобавок отвечает
за их тип: `args.string(0, "путь")`, `args.integer(1, "размер", 10)`, `args.object(2)`,
`args.function(0, "обработчик")`, `args.instance(0, "клиент", Handler)`. Проверка
написана один раз, поэтому и сообщение у всех библиотек одинаковое:

```
open(): путь к файлу: ожидалась строка, а здесь число (5)
```

Тому, что сюда не поместилось — значению внутри переданного объекта, элементу массива, —
доступен тот же шаблон: `Args.because("http: 'headers'", "ожидался объект", given)`.

#### Имена параметров

`Arity` говорит, сколько аргументов принимает функция, но не как их зовут, — поэтому
позвать такую функцию [по имени](functions.md#именованные-аргументы) нельзя. Чтобы
можно было, вместо `Arity` объявляется `Signature`:

```java
scope.define("grid", BuiltinFunction.of("grid", Signature.of(
        Signature.Param.required("rows"),
        Signature.Param.required("cols"),
        Signature.Param.optional("hgap", IntValue.of(0)),   // готовое значение
        Signature.Param.optional("vgap", IntValue.of(0))),
        (context, args, span) -> ...));                     // grid(rows: 2, cols: 3)
```

Тело при этом не меняется: имена раскладываются по позициям **до** входа в него,
и `args` остаётся обычным плотным списком. Значение по умолчанию у встроенной функции
— готовое `Value`, поэтому пропуск в середине закрывает движок. Параметр, у которого
значения нет вовсе (`Signature.Param.optional("constraint")`), пропустить можно только
в хвосте: подставить `null` значило бы соврать телу, которое отличает «не передали»
от «передали null».

`Arity` никуда не делась и остаётся правильным выбором там, где имён нет: у функции
с любым числом аргументов вроде `println`. Остатка (`*args`, `**named`) у встроенной
функции не бывает и не надо: «сколько угодно аргументов» — это `Arity.any()`, а список
тело и так получает целиком. Раскрытие в вызове при этом работает и здесь —
`println(*values)` говорит, сколько аргументов, а не как их зовут.

### Класс

```java
NativeClass file = NativeClass.named("File")
        .field("path")                                  // заголовок: new File(path)
        .init((self, ctx, args, span) -> { ... })       // после заполнения полей
        .method("read", Arity.exactly(0), (self, ctx, args, span) -> ...)
        .method("write", Arity.exactly(1), (self, ctx, args, span) -> ...)
        .factory("temp", Arity.between(0, 1), (type, ctx, args, span) -> ...)
        .constant("SEPARATOR", StringValue.of(File.separator))
        .build();

scope.define(file.name(), file);
// имена полей — это и контракт создания: new File(path: "данные.txt") работает сразу
```

**Построитель зовут из `installTo`, а не из статического поля.** Поля самого класса
(`File.SEPARATOR`, `File.temp`) изменяемы — скрипт вправе в них писать, как и в поля
класса на wdl, — поэтому класс, общий для всех запусков, переносил бы `File.mark = 1`
из одного скрипта в следующий. Сборка стоит недорого, а свой класс фабрика получает
первым аргументом, так что ссылаться на статику незачем.

Построитель, а не аннотации с рефлексией: имена и число аргументов видны в одном
месте, опечатку ловит компилятор, а не запуск, и ничего не нужно открывать через
`module-info`.

Правила те же, что у [классов языка](classes.md), и это не совпадение, а условие:

* **заголовок — это поля.** Сколько полей, столько и аргументов у `new`; поле
  со значением по умолчанию делает аргумент необязательным. Обязательное поле
  не может идти после необязательного — пропуск в середине нечем записать;
* **`init` выполняется по готовому объекту** — как конструктор `def File()`
  в языке. К этому моменту поля уже записаны, поэтому их можно проверить,
  посчитать производное и завести состояние;
* **фабрика — место записи, а не вид члена.** `File.temp()` ложится в поле самого
  класса обычным значением, ровно как `def User.of(...)` в языке;
* **поле перекрывает метод.** Отсюда следствие, о которое легко споткнуться:
  если путь лежит полем `path`, метода `path()` быть не может — `f.path` вернёт
  строку, и вызывать её нечем. Это правило языка, а не ограничение API.

Иерархия внутри Java-модуля строится обычным `.extending(parent)`: заголовок родителя
продолжается своими полями, таблица методов склеивается плоско (свои побеждают),
`init` выполняются от дальнего предка к потомку, `is` отвечает `true` предку и его
трейтам. Ни `Linker`, ни формы в этом не участвуют — формы у нативных классов нет.

### Трейт

Трейт — это то, чем модуль даёт скрипту **интерфейс для реализации**. Отвечает
на это именно он, а не наследование: требования проверяются на строке `class`,
а связывает трейт слабее, чем родитель.

```java
NativeTrait handler = NativeTrait.named("Handler")
        .requireMethod("onMessage", Arity.exactly(1))   // класс обязан уметь
        .requireField("name")                           // и обязан объявить
        .field("retries", IntValue.of(3))               // а это достаётся ему готовым
        .build();

scope.define(handler.name(), handler);
```

```wdl
import sys.net as net

class Echo(name) with net.Handler {
    def onMessage(text) => "эхо: " + text
}

net.deliver(new Echo("первый"), "пинг")
```

Забытый `onMessage` или неверное число его аргументов — ошибка на строке `class`,
тем же текстом и в тот же момент, что у трейта на wdl: проверяет их один и тот же
`Linker`. Java-часть при этом о скрипте ничего знать не обязана — она получает объект
и берёт метод обычным значением:

```java
InstanceObjectValue target = args.instance(0, "обработчик", handler);
target.owner().method(target, "onMessage").call(context, List.of(message), span);
```

Правила те же, что у [трейта языка](classes.md): в заголовке переменные (со значением —
готовое поле, без значения — требование), в теле методы. С одной оговоркой —
**методов с телом у нативного трейта нет**: метод в плоской таблице держит кусок дерева,
а у Java-метода дерева нет. Готовые методы даёт класс, а не трейт.

### Библиотека

```java
public final class Std implements Library {
    public String name() { return "std"; }
    public Environment installTo(Environment scope) { ... return scope; }
}
```

Библиотека ничего не «регистрирует» и никуда не прописывается — она заводит имена
в переданной области. Отсюда всё остальное: подключить её можно к одному запуску
и не подключить к другому, а тест может подменить любое имя, определив его после.
Отдельной таблицы библиотек в языке нет, как нет и таблицы функций.

## Где хранить состояние

**Что выразимо значением языка — храните полем.** Путь к файлу это строка, значит
и лежать он должен полем: тогда `f.path`, `println(f)` и `for (key in f)` работают
сами собой, без единой строчки в библиотеке.

```java
.field("path")                          // и всё, больше ничего не нужно
```

**Что не выразимо — в состоянии экземпляра.** Открытый поток, соединение,
генератор случайных чисел значениями языка не бывают:

```java
.init((self, ctx, args, span) -> {
    self.state(new java.util.Random(seed));
    return NullValue.NULL;
})
.method("next", Arity.exactly(0), (self, ctx, args, span) ->
        FloatValue.of(self.state(Random.class).nextDouble()))
```

Разделение то же, что и в самом ядре: `MapValue` — карта пар, `InstanceObjectValue` —
она же со ссылкой на класс, `NativeInstance` — она же с местом под Java-объект.
Что нужно частному случаю, живёт в частном случае.

## Ошибки

Ошибка библиотеки должна выглядеть как ошибка скрипта — с местом в исходнике,
которое движок покажет так же, как деление на ноль:

```java
throw new WdlRuntimeError(span, "не удалось обратиться к файлу: " + reason);
```

`IOException` в чужом приложении бесполезен: он расскажет про Java-стек, а автору
скрипта нужна строка, на которой он ошибся.

```
stdlib.wdl:1:9: ошибка: не удалось обратиться к файлу: нет.txt
  1 | println(new File("нет.txt").read())
    |         ^^^^^^^^^^^^^^^^^^^^^^^^^^
```

**У ошибки бывает класс** — тот же, что у ошибок движка, и скрипт ловит её так же:

```java
throw new WdlRuntimeError(ErrorKind.VALUE, span, "http: адрес без схемы");
```

```wdl
try {
    r = http.get(address)
} catch (e is ValueError) {
    println("адрес не годится: ", e.message)
}
```

`Args` расставляет их сам: «не тот тип» — `TypeError` (`args.string(...)`),
«тип тот, а значение не годится» — `ValueError` (`args.bad(...)`). Без класса
ошибка остаётся `RuntimeError`, и это верно для сбоя ввода-вывода, который скрипт
не мог предвидеть.

## Что уже написано этим способом

Модуль [`std`](../wdl-stdlib/src/main/java/ru/wds/wdl/stdlib/Std.java) — он же
пример на все случаи:

| Что | Показывает |
|---|---|
| `pow`, `sqrt`, `abs` | функции, проверка аргументов, целое остаётся целым |
| `File(path)` | класс, поля, методы-цепочки, фабрика `File.temp()`, константа `File.SEPARATOR`, ошибки ввода-вывода |
| `Random(seed)` | необязательное поле и Java-состояние, которого в языке нет |

Три модуля рядом — на них видно ту же работу, собранную в модуль:

| Модуль | Показывает |
|---|---|
| [`sys.json`](../wdl-stdlib/src/main/java/ru/wds/wdl/stdlib/Json.java) | данные отдаются значениями языка, ошибки разбора называют место внутри документа |
| [`sys.io`](../wdl-stdlib/src/main/java/ru/wds/wdl/stdlib/Io.java) | функции и класс в одном модуле, один и тот же `File`, что и в `std` |
| [`sys.net.http`](../wdl-stdlib/src/main/java/ru/wds/wdl/stdlib/Http.java) | ленивый клиент, `close()`, ответ обычным классом с полями |

Рабочие скрипты — [`examples/stdlib.wdl`](../examples/stdlib.wdl)
и [`examples/sys.wdl`](../examples/sys.wdl).

Стандартная библиотека подключается консольным запуском по умолчанию, но остаётся
обычной библиотекой: встроенный в приложение движок сам решает, подключать её,
заменить своей или не подключать вовсе.

## Модуль на Java

Библиотека, положенная не в корневую область, а в свою собственную, — это
[модуль](modules.md), и скрипт получает его через `import`:

```java
NativeModules natives = NativeModules.of(Map.of(
        "sys/json",     Json::library,
        "sys/net/http", Http::library,
        "app/world",    () -> new WorldLibrary(server)));

ExecutionContext context = ExecutionContext.of(scope, output)
        .withModules(ModuleSource.ofDirectory(scripts))
        .withNativeModules(natives);
```

```wdl
import app.world as world

world.spawn("зомби", 3)
```

Ничего нового писать для этого не нужно: модуль — это та же `Library` с теми же
`define`, что кладут имена в корень. Разница только в том, куда её установили,
и отсюда же берётся приятное следствие — одну и ту же библиотеку можно и раздать
всем, и отдать по имени. `Std` работает обоими способами без единой правки.

Три решения, о которые стоит не споткнуться:

* **Регистрируется фабрика, а не готовая библиотека.** Её зовут при выполнении
  `import` и не зовут вовсе, если импорта не случилось, — то же «за неиспользуемое
  не платят», что у файлов. И второе: один реестр обслуживает много запусков,
  а библиотека у каждого запуска своя, поэтому состояние модуля между запусками
  не течёт.
* **Имя, а не путь.** `import sys.json` означает одно и то же в любом файле,
  потому что каталога у встроенного модуля нет. Подробности и способ попросить
  именно файл — в [модулях](modules.md).
* **Ошибка при подготовке — ошибка на строке `import`.** Нет библиотеки в classpath,
  упала фабрика, не собралось соединение — всё это `WdlRuntimeError` с местом
  в скрипте, а не `NoClassDefFoundError` посреди чужого приложения.

### Что закрывать после запуска

Файл-модуль после выполнения не держит ничего, а вот на Java бывает клиент,
соединение или открытый канал. Для них у `Library` есть `close()`:

```java
@Override
public void close() {
    if (client != null) {
        client.close();
    }
}
```

Зовёт его хозяин запуска — `context.shutdownModules()`, — и зовёт в обратном порядке
создания. Консольный интерпретатор делает это в `finally`, приложение — из своего
`close()`. Ошибка в одном `close` не мешает закрыть остальные: скрипт уже отработал,
и ронять его на уборке нечестно.

Как это выглядит целиком — [`Json`](../wdl-stdlib/src/main/java/ru/wds/wdl/stdlib/Json.java),
[`Io`](../wdl-stdlib/src/main/java/ru/wds/wdl/stdlib/Io.java),
[`Http`](../wdl-stdlib/src/main/java/ru/wds/wdl/stdlib/Http.java) и набор
[`Sys`](../wdl-stdlib/src/main/java/ru/wds/wdl/stdlib/Sys.java).

**Данные отдавайте значениями языка, а не обёртками.** `json.parse` возвращает
обычные `object` и `array`, поэтому `data.items[0].name`, `for (key in data)`
и `len(data)` работают сами собой. Обёртка оправдана только там, где данных больше,
чем памяти, — и каждый раз это отдельное решение, а не привычка.

## Модули-файлы

По той же причине приложение решает и то, откуда скрипту брать
[модули-файлы](modules.md). Пока источник не задан, `import` отвечает ошибкой:
движок внутри чужого приложения не должен читать его файлы без спроса.

```java
ModuleUnits modules = new ModuleUnits(ModuleSource.ofDirectory(Path.of("scripts")));

ExecutionContext context = ExecutionContext.of(scope, logger::info).withModules(modules);
```

`ModuleSource` — интерфейс из одного метода: ключ модуля (`"lib/math"`) → `Source`
или `null`. Кроме `ofDirectory` есть `ofMap` — для скриптов, которые лежат не в файлах,
и для тестов, — и `none()`, стоящий по умолчанию. Своя реализация в пару строк закрывает
и буферы редактора, и модули из базы, и белый список каталогов.

**Спрашивают у источника только при выполнении `import`.** Разбор скрипта не открывает
ни одного модуля, поэтому источник вправе отдавать то, чего в момент запуска ещё
не существует: сгенерированный код, свежезагруженный плагин, запись из базы, появившуюся
минуту назад. Приложению это ничего не стоит — метод просто позовут позже.

`ModuleUnits` — реестр разобранных модулей, и он **один на запуск**. Разбери модуль
дважды — получишь два дерева и два набора форм, и класс из первого не будет тем же
классом, что из второго. Короткая форма `withModules(ModuleSource)` заводит реестр сама.

Область, которая была текущей в момент `withModules`, становится **корнем для всех
модулей**: они увидят встроенные функции и библиотеки, положенные до этого вызова,
и не увидят имён того файла, который их импортирует.

## Одно дерево, много запусков

Разобрать скрипт один раз и запускать его на каждого игрока — законный и дешёвый
сценарий: дерево неизменяемо, интерпретатор без состояния, всё изменяемое живёт
в `ExecutionContext`.

Одна оговорка касается классов. Класс связывается при выполнении своего объявления,
поэтому **у каждого запуска получаются свои формы классов**: родитель — это значение,
а значения у запусков разные. Внутри запуска всё как обычно, но экземпляр из первого
запуска на `is` из второго ответит `false`.

**То же самое и у классов, встроенных приложением, — намеренно.** Библиотека собирает
их в `installTo`, а не держит статическим полем: поля класса изменяемы, и общий
на процесс `File` донёс бы `File.mark = 1` из одного скрипта до следующего. Правило
короткое: **между запусками не переносится ничего**, а библиотека, которой это правило
нужно соблюсти, просто не заводит статических полей.

Внутри одного запуска класс при этом остаётся одним. `File`, положенный `std` в корень,
и `File`, который отдаёт `sys.io`, — тот же объект: модуль спрашивает его у области,
в которую устанавливается, а её корень — корень запуска. Тот же приём, которым
`sys.io` берёт трейт `Closeable` из прелюдии; в `wdl-stdlib` он записан один раз
в `Types.in(scope, имя, сборка)`.

## Функция скрипта в руках приложения

Значение-функцию можно достать из скрипта, унести куда угодно и позвать — из своего
потока, из обработчика фреймворка, через час после того, как файл дочитан. Работает
это потому, что функция несёт с собой **всё, что нужно для выполнения**: область,
где объявлена, файл, где написана, и запуск, которому принадлежит (`runtime.Run`).
От вызывающего ей нужен только вывод — печатать надо туда, где позвали.

```java
try (WdlInstance script = engine.compile(path).instance()) {
    script.execute();
    bus.subscribe(script.function("onMessage").as(MessageHandler.class));
}
```

Библиотеке для того же есть `Args.callback(0, "обработчик")` — она получает `Callback`
и зовёт его, ничего не спрашивая о том, откуда функция пришла: из главного файла,
из метода класса, из модуля или из замыкания на пять уровней вложенности.

### Потоки и вызовы из приложения

**Звать из любого числа потоков одновременно можно.** Вызовы не выстраиваются
в очередь: замка запуска больше нет, а области видимости, объекты, массивы и реестр
модулей внутри конкурентны. Раньше здесь было обещание «внутри запуска работает один
поток» — оно перестало быть правдой, и вместе с ним перестала быть правдой молчаливая
атомарность `count = count + 1` в скрипте.

Что запуск обещает автору скрипта, коротко: **одно обращение атомарно** — чтение
и запись переменной, поля, элемента не увидят «половину» значения и не потеряются;
выражение целиком — нет. Склеить несколько обращений в одно можно `synchronized`
на функции, `th.lock()` и `th.counter()`; полностью — в [потоках](threads.md).

**Режима «вернуть прежний замок» нет намеренно.** Такой был — один флаг на сборщике
движка, — и держался он на рассуждении «чужие скрипты писались в расчёте на очередь».
Оказалось, что он несовместим с `sys.thread`: главный поток входит в скрипт и держит
замок, порождённый поток встаёт на нём, `t.join()` ждёт вечно — простейший
`spawn` + `join` вешался намертво. Совместимость с невыпущенной версией не стоит мины
под самой заметной возможностью языка, поэтому семантика здесь одна.

Скрипту, который полагался на молчаливую атомарность, нужна одна правка — `synchronized`
перед `def` там, где несколько обращений обязаны быть одним целым.

**Закрытие запуска останавливает то, что он породил** — и порядок здесь важнее самих
шагов:

1. **потоки скрипта** — пока модули ещё открыты, чтобы их `defer` и `use` успели
   закрыть своё по живому соединению, а не по закрытому;
2. **модули и библиотеки корня** — и вход в скрипт при этом **ещё открыт**. Модуль
   вправе звать скрипт во время собственного закрытия, и это не теоретическая
   возможность: `sys.gui` ждёт в `close()`, пока пользователь закроет окна, а
   обработчики кнопок всё это время работают;
3. **потоки скрипта ещё раз** — те, что завелись на шаге 2 (у клиента с интерфейсом это
   слушатель сокета: он появляется по нажатию кнопки);
4. **вход** — последним. С этого момента вызов функции даёт внятную остановку
   выполнения, а не работу по закрытым ресурсам.

Ждать потоки движок готов пять секунд; не завершившиеся за это время называются
по именам в логе — «приложение не завершается» без имени потока это загадка на полдня.

Из этого же следует правило для библиотек: **`new Thread` заводить нельзя**. Поток
берётся у `CallContext.threads()` — иначе запуск о нём не знает, и он переживёт
закрытие. Стек такому потоку задан явно: предел вложенности вызовов рассчитан
на нормальный стек, а в коротком рекурсия упрётся в `StackOverflowError` раньше своего
предела.

Изоляция запусков при этом никуда не делась и остаётся самым простым ответом там, где
общее состояние не нужно вовсе: несколько `WdlInstance` не делят ничего — см. «Одно
дерево, много запусков» выше.

## Чего пока нет

* **Наследования скрипта от встроенного класса.** `class My : http.Response` даёт
  внятный отказ: плоскую таблицу по Java-методам не собрать. Обратное — нативный класс
  от нативного — работает (`.extending`), а «реализовать интерфейс модуля» закрывает
  `NativeTrait`, и связывает он слабее. Что нужно для оставшегося случая — разобрано
  в [Нативные модули.md](../Нативные%20модули.md), раздел 6.3.
* **Методов с телом у нативного трейта.** Метод в плоской таблице держит кусок дерева;
  это та же работа, что и предыдущий пункт.
* **Моста к произвольному Java-объекту**: `player.getName()` без описания класса
  руками. Это тот же поиск по ключу, только ветка реализации другая.
* **Лимитов выполнения**: числа шагов и таймаута. Предел глубины вызовов есть
  (`ExecutionContext.MAX_CALL_DEPTH`), но он константа. Место для настраиваемых —
  `runtime.Run`, где уже лежит всё остальное, принадлежащее запуску.

Фасад `WdlEngine` в `wdl-api` — есть: он собирает библиотеки, набор модулей и вывод
в одном месте, а `WdlScript`/`WdlInstance` разделяют разбор и состояние.
