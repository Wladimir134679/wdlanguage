# Игровой движок: модуль `game`

`wdl-game` — маленький игровой движок на Java Swing и `Graphics2D`, отданный
скрипту модулем `game`. Он не входит в стандартную библиотеку и никогда не войдёт:
движок — не часть языка.

**Зачем он тогда есть.** Игра — самое требовательное приложение из тех, что зовут
скрипт: она зовёт его шестьдесят раз в секунду, из своего цикла, и ждёт ответа
до следующего кадра. Всё, что в таком режиме окажется неудобным, дорогим или
опасным, должно найтись здесь — на своём движке, — а не в чужой игре через полгода.
Поэтому `wdl-game` устроен как настоящее приложение-хозяин: он собирает `WdlEngine`,
кладёт рядом со стандартной библиотекой свой модуль и отдаёт управление скрипту.

```bash
./gradlew :wdl-game:run --args="examples/game/pong.wdl"
./gradlew :wdl-game:run                                  # без аргументов — тот же пример
./gradlew :wdl-game:installDist   # → wdl-game/build/install/wdgame/bin/wdgame
```

Запуск без аргументов — это «Run» из IDE, а не забытый параметр, поэтому движок
показывает себя, а не справку: он ищет `examples/game/pong.wdl` вверх по дереву
от рабочего каталога и запускает его.

## Три типа

| Тип | Что это |
|---|---|
| `World` | мир: окно, сцена со спрайтами и цикл кадров |
| `Sprite` | объект на сцене: положение, размер, скорость, цвет, форма |
| `Canvas` | холст кадра, приходящий в `onDraw` |

Классы стоят в области модуля рядом с миром, а не прячутся за фабриками:
`s is game.Sprite` — законный вопрос, и ответить на него можно только именем,
которое у скрипта есть.

```wdl
import game as g

world = new g.World(title: "Пример", width: 640, height: 360)
ball = world.spawn("ball", x: 100, y: 100, w: 12, h: 12, shape: "oval")
ball.vx = 220
ball.vy = 140

world.onUpdate(def (dt) {
    if (ball.y < 0 || ball.bottom > world.height) ball.vy = -ball.vy
    if (ball.x < 0 || ball.right > world.width) ball.vx = -ball.vx
})

world.run()
```

## Кадр

Порядок внутри кадра — это договор движка, и знать его надо, чтобы понимать,
что видит обработчик:

1. накопленные нажатия уходят в `onKey`;
2. **движок двигает спрайты** по их скорости: `x += vx * dt`;
3. `onUpdate(dt)` — скрипт видит уже сдвинутый мир и правит его: отбивает мяч,
   упирает ракетку в край, считает очки;
4. кадр заливается фоном, движок рисует спрайты, затем зовётся `onDraw(canvas)`;
5. картинка уходит в окно.

Порядок «сначала подумать, потом двигать» означал бы, что столкновение замечено
на кадр позже, чем случилось.

**Скорость задаётся в пикселях в секунду, а не в пикселях за кадр.** Поэтому
обработчику и приходит `dt`: игра, написанная в кадрах, на другой машине идёт
с другой скоростью, и виноват в этом оказывается движок. Длинный кадр (окно
перетащили, машина ушла в своп) обрезается до 50 мс: иначе мяч сдвинулся бы
на треть экрана за один шаг и пролетел сквозь ракетку.

## Жизненный цикл

```wdl
world.onStart(def () { ... })            // один раз, до первого кадра
world.onUpdate(def (dt) { ... })         // каждый кадр
world.onDraw(def (canvas) { ... })       // каждый кадр, поверх спрайтов
world.onKey(def (key, pressed) { ... })  // на нажатие и отпускание
world.onStop(def () { ... })             // один раз, после штатного конца

world.run()      // открыть окно и крутить, пока его не закроют или не позовут stop()
world.step(dt)   // один кадр без окна и без графики
world.stop()     // попросить цикл закончиться
```

Обработчик **вправе не брать аргументов**: `onUpdate(def () { ... })` — законная
запись, лишние аргументы отсекаются по числу параметров функции. Движок предлагает
данные, а не требует их принять.

### `run()` идёт в потоке скрипта

Цикл кадров крутится в том самом потоке, который позвал `world.run()`, — движок
не заводит своего. Из этого следуют три вещи, ради которых так и сделано:

* **ошибка обработчика доходит до автора скрипта обычным образом** — с местом
  в коде, через `try`/`catch`, без единого слова про потоки;
* **в потоке Swing не выполняется ничего, кроме показа готовой картинки**: кадр
  рисуется в память (`BufferedImage`) в потоке игры, а окно получает его собранным;
* `run()` не возвращает управления, пока игра идёт. Так и должно быть — это и есть
  игра.

Ошибка в обработчике прерывает игру, и `onStop` в этом случае **не зовётся**:
мир остался в непонятном состоянии, и звать по нему ещё один обработчик — это
второй способ упасть поверх первого. Окно закрывается в любом случае.

### Игру можно прогнать без окна

`world.step(dt)` делает то же, что кадр, минус графика: ввод, движение,
`onUpdate`. Сцена ничего не знает про окно — ради этого она и отделена, — поэтому
правила игры проверяются обычным тестом там, где графической среды нет вовсе:

```wdl
world.onUpdate(def (dt) {
    if (ball.y < 0) ball.vy = -ball.vy
})
for (i = 0; i < 60; i += 1) world.step(1.0 / 60)
println(ball.y)
```

## Спрайты

Спрайт заводится **по имени** и по имени же находится: `world.get("ball")` отдаёт
тот же самый объект, что вернул `spawn`. Так скрипт, разложенный на несколько
функций, не обязан таскать ссылки аргументами через полфайла. Второе имя того же
спрайта — ошибка, а не второй мяч.

```wdl
ball = world.spawn("ball", x: 0, y: 0, w: 12, h: 12, color: "#f2f2f2", shape: "oval")
world.get("ball") == ball        // true
```

| Член | Что это |
|---|---|
| `x`, `y`, `w`, `h` | положение и размер, читаются и пишутся |
| `vx`, `vy` | скорость в пикселях в секунду |
| `color`, `shape`, `visible` | как рисовать: цвет, `rect`/`oval`, показывать ли |
| `name`, `alive` | имя на сцене и стоит ли спрайт на ней ещё |
| `right`, `bottom`, `centerX`, `centerY` | производные от положения, только чтение |
| `moveTo(x, y)`, `move(dx, dy)`, `stop()` | переставить, сдвинуть, обнулить скорость |
| `hits(other)`, `contains(x, y)` | пересечение с другим спрайтом и попадание точки |
| `remove()` | снять со сцены |

**Всё это свойства, а не поля**, и это не формальность: положение меняет движок
каждый кадр, а поле экземпляра хранило бы снимок, сделанный при создании. Такой
снимок устарел бы к первому же обращению, а запись в него не дошла бы до движка
вовсе.

**Столкновение считается по прямоугольникам** даже у формы `oval`: форма — это
способ нарисовать, а не способ столкнуться.

Снятый спрайт исчезает со сцены, но ссылка на него у скрипта остаётся живой:
`brick.alive` отвечает `false`, `brick.name` по-прежнему работает, а сталкиваться
такой спрайт перестаёт.

## Ввод

Два разных вопроса, и нужны оба:

```wdl
world.down("up")        // держат ли клавишу прямо сейчас — спрашивать каждый кадр
world.pressed("space")  // нажали ли её именно в этом кадре
world.onKey(def (key, pressed) { ... })   // событие: нажали или отпустили
world.mouseX, world.mouseY, world.mouseDown
```

Ракетка едет, пока клавишу держат, — это `down`. Подача по пробелу повторилась бы
шестьдесят раз в секунду без `pressed`. Автоповтор клавиатуры в события не
превращается: `onKey` зовётся на настоящем переходе, а не на каждом сообщении
системы. Клавиша, отпущенная в чужом окне, отпускается и здесь — иначе ракетка
уехала бы в стену навсегда.

Имена клавиш — строки: `left`, `right`, `up`, `down`, `space`, `enter`, `escape`,
`shift`, `ctrl`, `alt`, `tab`, `backspace`, `a`–`z`, `0`–`9`, `f1`–`f12`.
Опечатка (`world.down("lft")`) — ошибка, а не вечное «не нажата».

## Холст

Холст приходит **аргументом в `onDraw`**, а не берётся у мира свойством. Рисовать
имеет смысл только внутри кадра: следующий начинается с заливки фоном, и всё,
нарисованное между кадрами, исчезнет, не показавшись. Попытка рисовать вне кадра
отвечает отказом, а не тишиной.

```wdl
world.onDraw(def (c) {
    c.color("#8d9aa8")                       // цвет по умолчанию
    c.clear("#101418")                       // заливка (движок уже сделал её сам)
    c.pixel(x, y, "#2b3440")                 // точка
    c.rect(x, y, w, h)                       // закрашенный прямоугольник
    c.frame(x, y, w, h, color: "#333", thickness: 2)
    c.oval(x, y, w, h, "#f2f2f2")
    c.line(x1, y1, x2, y2, color: "#333")
    c.text(x, y, "счёт: " + score, size: 24, color: "#7ec8ff")
    c.textWidth("счёт", 24)                  // чтобы поставить текст по центру
    c.width, c.height
})
```

Цвет у каждого метода последний и необязательный: пропустили — рисуют цветом,
заданным `c.color(...)`.

**`pixel` — это правда попиксельно**: точка пишется прямо в картинку кадра, минуя
сглаживание и перо. Координата за краем холста молча отбрасывается — рисование
по циклу почти всегда выходит за границу на краях, и падать на этом значило бы
заставить скрипт проверять то, что движок уже знает.

## Цвет

Строкой: `#rrggbb`, `#rgb`, `#aarrggbb` (первая пара — прозрачность) или имя
(`red`, `white`, `gray`, …). Строка читается глазами, переживает сохранение в JSON
и не требует отдельного типа языка с конструктором и печатью. Непонятный цвет —
ошибка, а не чёрный по умолчанию.

```wdl
g.rgb(126, 200, 255)          // "#7ec8ff"
g.clamp(value, min, max)      // загнать ракетку в поле, скорость — в предел
```

## Мир

| Член | Что это |
|---|---|
| `width`, `height` | размер сцены |
| `title`, `background` | заголовок окна и цвет заливки кадра, пишутся |
| `fps`, `frames`, `time`, `running` | измеренная частота, счётчик кадров, игровое время, идёт ли цикл |
| `count`, `all()`, `get(name)`, `spawn(...)`, `remove(sprite)`, `clear()` | сцена |
| `down(key)`, `pressed(key)`, `mouseX`, `mouseY`, `mouseDown` | ввод |
| `onStart`, `onUpdate`, `onDraw`, `onKey`, `onStop` | жизненный цикл |
| `run()`, `step(dt)`, `stop()`, `close()` | цикл кадров |

Окна, оставшиеся от скрипта, гасятся вместе с запуском — и, в отличие от
`sys.gui`, закрытие модуля **не ждёт** пользователя. Ждать нечего: игра держит
поток скрипта в `world.run()`, и раз запуск дошёл до закрытия, цикл кадров уже
кончился.

## Что внутри

Модуль разделён надвое, и граница между половинами — главное решение всей затеи.

| Пакет | Что там | Знает ли про wdl |
|---|---|---|
| `ru.wds.wdl.game.engine` | `Engine`, `Scene`, `Sprite`, `Input`, `Keys`, `Colors`, `Painter`, `GameWindow`, `GameLoop`, интерфейс `Game` | **нет** |
| `ru.wds.wdl.game.script` | `NativeWorld`, `NativeSprite`, `NativeCanvas`, `ScriptGame` | да |

Движок знает интерфейс `Game` из пяти методов — и ничего больше. Что стоит
за ним, дело вызывающего: `ScriptGame` подставляет туда функции скрипта, а тест —
обычную Java-лямбду. Снять слой встраивания, не тронув движка, можно в любой
момент; ради такой проверки модуль и написан.

Пример игры целиком — [`examples/game/pong.wdl`](../examples/game/pong.wdl):
две ракетки, мяч, счёт, соперник в две строки и разделительная сетка,
нарисованная попиксельно.
