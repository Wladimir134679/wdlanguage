# Игра со встроенными скриптами: `wdl-game`

`wdl-game` — маленький игровой движок на Java Swing и `Graphics2D` и пинг-понг
на нём. Игра написана на Java; на wdl написаны её **правила**, и лежат они
скриптами внутри jar.

**Зачем это здесь.** Игра — самое требовательное приложение из тех, что зовут
скрипт: она зовёт его шестьдесят раз в секунду, из своего цикла, и ждёт ответа
до следующего кадра. Всё, что в таком режиме окажется неудобным, дорогим или
опасным, должно найтись здесь — на своём движке, — а не в чужой игре через
полгода. Поэтому модуль устроен не как «язык, которым можно написать игру»,
а как настоящее приложение-хозяин: игра собирает `WdlEngine`, читает свои
скрипты и играет.

```bash
./gradlew :wdl-game:run          # играть
./gradlew :wdl-game:installDist  # → wdl-game/build/install/wdgame/bin/wdgame
```

Управление: **W/S** или стрелки — ракетка, **ПРОБЕЛ** — подача, **R** — новая
партия, **ESC** — выход. Аргументов у запуска нет, и это часть замысла: скрипт
здесь не «то, что запускают», а часть самой игры.

## Что на Java, а что в скриптах

Разделение проходит по линии «физика или правило».

| В Java (`ru.wds.wdl.game.pong`) | В скриптах (`resources/.../pong/*.wdl`) |
|---|---|
| поле, ракетки, мяч, их движение | скорость подачи и её разброс |
| ввод игрока и удержание ракеток в поле | направление и ускорение отскока |
| столкновения, стены, пересечение края поля | вся логика соперника |
| счёт и состояние партии | когда партия закончена |
| отрисовка спрайтов | сетка, счёт и надписи поверх кадра |

Как летит мяч, кто кого коснулся, когда он ушёл за край — физика: считать её
скриптом значило бы платить вызовом за каждое сравнение. С какой скоростью
подавать, куда отскочить, что делает соперник, что написано на экране — правила,
и меняются они чаще всего. Меняются — значит должны меняться без пересборки.

## Пять вопросов игры

Вся граница — интерфейс `PongHooks` из пяти методов и одноимённые функции
в `pong.wdl`:

```wdl
serve(game, ball)            // с какой скоростью подавать
bounce(game, ball, paddle)   // куда отскочить от ракетки
rival(game, ball, paddle)    // с какой скоростью ехать сопернику — вернуть число
point(game, side)            // закончилась ли партия этим очком — вернуть true/false
hud(game, canvas)            // что написать поверх кадра
```

**Хук по возможности возвращает решение, а не выполняет его.** `rival` отдаёт
скорость числом, `point` отвечает «да» или «нет» — такую функцию можно позвать
в тесте, не заводя ни поля, ни мяча. Там, где решение сложнее числа (`serve`,
`bounce`), скрипт правит скорость мяча прямо: придумывать ради этого тип
«намерение» дороже, чем отдать спрайт.

**Игра не спрашивает скрипт о том, что знает сама.** Счёт ведёт Java, и `Match`
у скрипта — только на чтение. Разрешить запись значило бы завести второе место,
где меняется счёт, и рано или поздно эти два места разошлись бы.

## Четыре файла

Скрипты лежат в ресурсах модуля, `wdl-game/src/main/resources/ru/wds/wdl/game/pong/`:

| Файл | За что отвечает |
|---|---|
| `pong.wdl` | корневой: импортирует остальные и объявляет пять имён, которые ищет игра |
| `rules.wdl` | подача, отскок от ракетки, конец партии |
| `rival.wdl` | соперник — одно число на кадр |
| `hud.wdl` | сетка, счёт, подсказка |

Правки здесь видны без пересборки Java-кода: `SPEED` в `rival.wdl` — насколько
соперник быстр, `SPIN` в `rules.wdl` — насколько круто закручивает ракетка,
`START_SPEED` — с какой скоростью летит первая подача.

```wdl
// rival.wdl — весь ум соперника
def speed(game, ball, paddle) {
    gap = aim(game, ball, paddle) - paddle.centerY
    if (abs(gap) < DEAD_ZONE) return 0;

    limit = ball.vx > 0 ? SPEED : IDLE_SPEED
    return g.clamp(gap * REACTION, -limit, limit);
}
```

Соперник нарочно не считает отскоки от стен: тот, кто их считает, не ошибается
никогда, и выиграть у него нельзя.

## Как это собрано

Всё встраивание — в одном классе, `ru.wds.wdl.game.PongScripts`.

* **Один запуск на все скрипты.** Файлов четыре, а `WdlInstance` один: корневой
  `pong.wdl` импортирует остальные обычным `import`, а исходники приходят
  не из каталога, а из ресурсов jar — `ModuleSource` для того и один метод.
  Разложить хуки по отдельным запускам было бы хуже, чем кажется: класс —
  значение запуска, и один и тот же спрайт получил бы в каждом свою обёртку
  своего класса, а `ball is g.Sprite` перестал бы значить хоть что-нибудь.
* **Скрипты выполняются один раз, до первого кадра.** На этом шаге они объявляют
  константы и функции; дальше игра только зовёт. Разбор файла шестьдесят раз
  в секунду не повторяется.
* **Обёртка на объект одна.** Мяч заворачивается один раз за игру — значение
  лежит в самом спрайте, — поэтому скрипт, положивший `ball` в переменную,
  получит на следующем кадре тот же объект. Холст — исключение: он живёт кадром.
* **Ошибка скрипта доходит до хозяина обычным образом.** Цикл кадров крутится
  в том потоке, который его позвал, поэтому падение внутри `bounce` прилетает
  в `main` с местом в `rules.wdl`, а не теряется в чужом потоке.
* **Классы модуля уезжают хозяину.** Обёртки для своих спрайтов делает
  приложение, а класс — один на запуск; поэтому `Games.library(listener)` отдаёт
  собранные `Sprite` и `Canvas` тому, кто заворачивает.

## Кадр

Порядок внутри кадра — договор движка, и знать его надо, чтобы понимать,
что видит скрипт:

1. накопленные нажатия уходят в игру (пробел, `R`, `ESC`);
2. **движок двигает спрайты** по их скорости: `x += vx * dt`;
3. игра правит уже сдвинутый мир: ракетки, стены, столкновения, голы —
   и по дороге спрашивает скрипт;
4. кадр заливается фоном, движок рисует спрайты, затем зовётся `hud(game, canvas)`;
5. картинка уходит в окно.

Порядок «сначала подумать, потом двигать» означал бы, что столкновение замечено
на кадр позже, чем случилось.

**Скорость задаётся в пикселях в секунду, а не в пикселях за кадр**: игра,
написанная в кадрах, на другой машине идёт с другой скоростью. Длинный кадр
(окно перетащили, машина ушла в своп) обрезается до 50 мс: иначе мяч сдвинулся бы
на треть экрана за один шаг и пролетел сквозь ракетку.

Отбитый мяч **сначала переставляется** за край ракетки и только потом попадает
в `bounce`: иначе на следующем кадре он снова оказался бы внутри неё и залип
до конца розыгрыша.

## Три типа

Скрипт не создаёт мир — объекты приходят к нему аргументами хука.

### `Sprite` — объект на сцене

| Член | Что это |
|---|---|
| `x`, `y`, `w`, `h` | положение и размер, читаются и пишутся |
| `vx`, `vy` | скорость в пикселях в секунду |
| `color`, `shape`, `visible` | как рисовать: цвет, `rect`/`oval`, показывать ли |
| `name`, `alive` | имя на сцене и стоит ли спрайт на ней ещё |
| `right`, `bottom`, `centerX`, `centerY` | производные от положения, только чтение |
| `moveTo(x, y)`, `move(dx, dy)`, `stop()` | переставить, сдвинуть, обнулить скорость |
| `hits(other)`, `contains(x, y)` | пересечение с другим спрайтом и попадание точки |
| `remove()` | снять со сцены |

**Всё это свойства, а не поля**, и это не формальность: положение меняет движок
каждый кадр, а поле экземпляра хранило бы снимок, сделанный при создании. Такой
снимок устарел бы к первому же обращению, а запись в него не дошла бы до движка
вовсе.

**Столкновение считается по прямоугольникам** даже у формы `oval`: форма — это
способ нарисовать, а не способ столкнуться.

### `Match` — партия, только чтение

| Член | Что это |
|---|---|
| `width`, `height` | размер поля |
| `player`, `rival`, `target` | счёт сторон и до скольких играют |
| `round`, `rally`, `time` | номер розыгрыша (с единицы), число отбитых мячей в нём, игровое время |
| `state` | `"serve"`, `"play"` или `"over"` |
| `serving`, `winner` | чья подача; победитель или `null`, пока партия идёт |

Стороны — строки `"player"` и `"rival"`: их ровно две, сравнивать их скрипт будет
с литералом, а тип ради двух значений — это ещё одно имя, которое надо знать,
чтобы написать простое условие.

### `Canvas` — холст кадра

```wdl
def draw(game, c) {
    c.color("#8d9aa8")                       // цвет по умолчанию
    c.clear("#101418")                       // заливка (движок уже сделал её сам)
    c.pixel(x, y, "#2b3440")                 // точка
    c.rect(x, y, w, h)                       // закрашенный прямоугольник
    c.frame(x, y, w, h, color: "#333", thickness: 2)
    c.oval(x, y, w, h, "#f2f2f2")
    c.line(x1, y1, x2, y2, color: "#333")
    c.text(x, y, "" + game.player, size: 46, color: "#7ec8ff")
    c.textWidth("счёт", 20)                  // чтобы поставить текст по центру
    c.width, c.height
}
```

Цвет у каждого метода последний и необязательный: пропустили — рисуют цветом,
заданным `c.color(...)`.

Холст приходит **аргументом**, а не берётся у мира свойством: рисовать имеет
смысл только внутри кадра, следующий начинается с заливки фоном. Попытка рисовать
вне кадра отвечает отказом, а не тишиной.

**`pixel` — это правда попиксельно**: точка пишется прямо в картинку кадра, минуя
сглаживание и перо; разделительная сетка в `hud.wdl` нарисована именно так.
Координата за краем холста молча отбрасывается — рисование по циклу почти всегда
выходит за границу на краях, и падать на этом значило бы заставить скрипт
проверять то, что движок уже знает.

## Модуль `game`

Всё, что модуль даёт сверх типов, — две функции:

```wdl
import game as g

g.rgb(126, 200, 255)          // "#7ec8ff"
g.clamp(value, min, max)      // загнать ракетку в поле, скорость — в предел
```

Мира, сцены и цикла кадров в модуле нет — они у приложения. Так и выглядит
встраивание в чужую игру: движок зовёт скрипт, а не наоборот, и кнопке
«запустить игру» в скриптовом модуле места нет.

Цвет задаётся строкой: `#rrggbb`, `#rgb`, `#aarrggbb` (первая пара —
прозрачность) или имя (`red`, `white`, `gray`, …). Строка читается глазами,
переживает сохранение в JSON и не требует отдельного типа языка с конструктором
и печатью. Непонятный цвет — ошибка, а не чёрный по умолчанию.

## Проверить без окна

Сцена ничего не знает про окно — ради этого она и отделена, — поэтому и правила,
и рисование проверяются там, где графической среды нет вовсе:

```java
Engine engine = Pong.arena();
Pong pong = new Pong(engine, hooks);
pong.start();
engine.step(pong, 1.0 / 60);      // кадр без графики: ввод, движение, правила
BufferedImage frame = engine.paint(pong);   // кадр в память: спрайты и hud
```

Именно так устроены тесты модуля: `PongTest` играет с хуками-лямбдами на Java
(если игре понадобилось от них что-то сверх `PongHooks`, граница проведена
неправильно), `PongScriptsTest` — с теми самыми файлами из ресурсов и проверяет,
что подачу разгоняет `rules.wdl`, ракетку соперника ведёт `rival.wdl`, а сетку
рисует `hud.wdl`.

## Что внутри

Четыре слоя, и границы между ними — главное решение всей затеи.

| Пакет | Что там | Знает ли про wdl |
|---|---|---|
| `ru.wds.wdl.game.engine` | `Engine`, `Scene`, `Sprite`, `Input`, `Keys`, `Colors`, `Painter`, `GameWindow`, `GameLoop`, интерфейс `Game` | **нет** |
| `ru.wds.wdl.game.pong` | `Pong`, `Match`, `PongHooks` — сама игра | **нет** |
| `ru.wds.wdl.game.script` | `NativeSprite`, `NativeCanvas`, `NativeMatch` — типы для скрипта | да |
| `ru.wds.wdl.game` | `Games` (модуль `game`), `PongScripts` (встроенные скрипты), `GameLauncher` | да |

Движок знает интерфейс `Game` из пяти методов — и ничего больше. Игра знает
`PongHooks` из пяти методов — и ничего больше. Снять два верхних слоя, не тронув
двух нижних, можно в любой момент: игра останется играбельной с правилами
на Java. Ради такой проверки модуль и написан.
