# Ошибки и их обработка

> **Сделано.** Всё описанное здесь работает, примеры запускаются:
> `examples/errors.wdl` и `examples/resources.wdl`. Чего ещё нет — перечислено
> в конце [плана работ](#что-осталось); это классы ошибок стандартной библиотеки
> и оператор `??`.

До этого любая ошибка выполнения была концом скрипта: `WdlRuntimeError` летел сквозь
все кадры до хозяина запуска, и автору скрипта нечем было сказать «файла может не быть,
и это нормально». Документ описывает, что появилось взамен: иерархия ошибок,
их бросок и ловля, освобождение ресурсов, трассировка и то, как всё это выглядит
на границе с приложением.

```wdl
fun loadTimeout(path) {
    try {
        return parseNumber(io.read(path));
    } catch (e is ParseError) {
        println("плохое значение: ", e.raw, " — беру 30")
        return 30;
    } catch (e is IoError) {
        return 30;
    }
}
```

## Пять решений, из которых следует остальное

1. **Ошибка — это значение**, экземпляр класса-наследника `Exception`. Не отдельный
   восьмой тип, не пара «ok/error», не магическая сущность: те же поля, тот же `is`,
   то же наследование, что у любого класса на wdl.
2. **Ошибка летит сама.** Промежуточные функции о ней не знают и ничего не объявляют:
   [сигнал уже проходит сквозь любую вложенность](#почему-это-ложится-на-существующее-ядро),
   этим же путём пойдёт и ошибка.
3. **Не всё ловится.** Прерывание потока, исчерпание стека и превышение глубины
   рекурсии — не `Exception`, и `catch` их не видит. Иначе `while (true) { try { … } catch (e) {} }`
   съел бы `thread.interrupt()`, а обещание «зациклившийся скрипт останавливается
   снаружи» перестало бы выполняться.
4. **Освобождение пишется рядом с захватом.** `defer` и `use` — не украшение к `finally`,
   а условие того, что первый же `throw` не начнёт течь дескрипторами.
5. **Java не протекает в скрипт.** Всё, что прилетело из библиотеки на Java и не стало
   ошибкой скрипта само, оборачивается в `JavaException` на границе вызова.

## Иерархия

Три семейства, один корень:

```
Exception                        ← корень всего ловимого, наследуется скриптом
├── RuntimeError                 ← ошибки движка: типы, имена, границы, арифметика
│   ├── TypeError
│   ├── NameError
│   ├── IndexError
│   ├── ArithmeticError
│   ├── ValueError
│   ├── CallError
│   ├── DeclarationError
│   └── ImportError
├── JavaException                ← то, что пришло из Java и не стало ошибкой скрипта
└── (ваши классы)                ← class ParseError(raw) : Exception("не число")

FatalError                       ← вне Exception: не ловится ничем, только хостом
```

`catch (e is Exception)` ловит всё, что вообще ловится. `catch (e)` без типа — то же
самое, короче записанное. `FatalError` не ловит ни то, ни другое.

### Exception — корень

```wdl
class Exception(message = "", cause = null, kind = "", at = "", trace = [], suppressed = []) {

    fun text() => kind == "" ? message : kind + ": " + message   // "IoError: файл не найден"

    fun report() { … }                                          // текст + место + трейс
}
```

Четыре последних поля стоят в заголовке, хотя заполняет их движок. Причина
техническая и стоит того, чтобы её знать: поля экземпляра появляются при создании,
а `kind` движок пишет при броске — и у ошибки, созданной, но ещё не брошенной,
`text()` не нашла бы имени, которого нет. Пустая строка в заголовке даёт им
существовать всегда, а бросок их перезаписывает.

Поля, которые есть у любой ошибки:

| Поле | Что в нём | Кто заполняет |
|---|---|---|
| `message` | сообщение для человека | заголовок класса |
| `cause` | ошибка-причина или `null` | тот, кто заворачивает |
| `kind` | имя класса ошибки: `"IoError"` | движок в момент `throw` |
| `at` | место броска: `"config.wdl:12:5"` | движок в момент `throw` |
| `trace` | [скриптовый стек](#трассировка-два-механизма): массив строк | движок в момент `throw` |
| `suppressed` | ошибки, [задавленные при закрытии](#подавленные-ошибки) | движок |

`kind` — поле, а не вызов встроенной функции, потому что спросить у значения имя его
класса язык [пока не умеет](classes.md#класс--тоже-значение), а ошибке это нужно чаще
всего: в лог, в сообщение, в сравнение. Когда такая функция появится, поле останется —
оно уже записано в экземпляр и переживает передачу ошибки куда угодно.

`kind`, `at`, `trace` и `suppressed` движок пишет в экземпляр обычной записью по ключу —
экземпляр это [карта пар](classes.md#что-такое-экземпляр), никакого особого механизма
для этого не нужно. **Заполняются они при броске, а не при создании**: `new IoError(…)`
может лежать в переменной сколько угодно, а место у ошибки одно — то, где её бросили.
Повторный бросок пойманной ошибки (`throw e`) место и трейс не затирает: иначе
перезаворачивание стирало бы ровно ту информацию, ради которой заворачивают.

### Встроенные ошибки движка

Всё, что сегодня бросает `WdlRuntimeError`, получает класс. Текст сообщения не меняется —
меняется только то, что его теперь можно поймать:

| Класс | Когда |
|---|---|
| `TypeError` | `"a" - 1`, `for (x in 5)`, обращение к числу через точку, `len(true)` |
| `NameError` | `переменная 'x' не определена` |
| `IndexError` | индекс вне границ, нецелый индекс, запись в строку |
| `ArithmeticError` | деление на ноль, остаток от нуля |
| `ValueError` | значение недопустимо для операции: неверный путь, неразбираемый JSON |
| `CallError` | вызов не-функции, неверное число аргументов, `new` от не-класса |
| `DeclarationError` | присваивание константе, невыполненное требование трейта, круг в наследовании, `new` от трейта |
| `ImportError` | модуль не найден, ошибка разбора модуля, упавшая фабрика библиотеки |
| `IoError` | файловые операции `std` и `sys.io` — **ещё не объявлен**, см. [что осталось](#что-осталось) |
| `JsonError`, `HttpError` | свои модули объявляют своё — тем же способом; тоже ещё нет |

**Зачем дробить.** `catch (e is IndexError)` — осмысленная реакция (взять значение
по умолчанию); `catch (e is RuntimeError)` — «любая ошибка движка»; `catch (e)` —
«вообще всё». Три уровня грубости вместо одного, и ни один не требует разбора строки
сообщения.

Классы объявлены в [прелюдии](#прелюдия) и лежат в корневой области видимости запуска,
рядом с `println`. Скрипт может их перекрыть (`IndexError = 5`) — пространство имён
одно, и исключений из этого правила язык не заводит; движок при броске берёт класс
не по имени из области, а [из реестра запуска](#как-это-устроено-в-коде), поэтому
перекрытие ломает только тот скрипт, который это сделал.

### JavaException

Библиотека, написанная по [правилам встраивания](embedding.md#ошибки), бросает
`WdlRuntimeError` и становится обычной ошибкой скрипта с местом в исходнике. Но
приложение может положить в область видимости что угодно, и оттуда прилетит
`NullPointerException`, `IllegalStateException` или `SQLException`. Для скрипта это
не должно выглядеть как крах движка:

```wdl
import app.db as db

try {
    rows = db.query("select * from players")
} catch (e is JavaException) {
    println("база недоступна: ", e.message)
    println("класс исключения: ", e.javaClass)      // java.sql.SQLTimeoutException
    println("в модуле: ", e.module)                 // app/db
    rows = []
}
```

| Поле | Что в нём |
|---|---|
| `message` | `getMessage()` исходного исключения, или имя класса, если сообщения нет |
| `javaClass` | полное имя класса: `"java.sql.SQLTimeoutException"` |
| `module` | имя модуля или библиотеки, из которой прилетело, или `null` |
| `javaTrace()` | стек Java массивом строк, по запросу — [не готовый массив](#трассировка-два-механизма) |

Оборачивание происходит **на границе вызова** — в `visitCall` и `visitNew`, вокруг
вызова нативного тела. Это единственное место, где Java-код зовётся из интерпретатора,
поэтому одна точка закрывает всё: встроенные функции, методы нативных классов, фабрики,
`init`.

### FatalError — то, что не ловится

```
выполнение прервано                     ← Thread.interrupt() от приложения
стек вызовов исчерпан                   ← вторая линия защиты от рекурсии
слишком глубокая рекурсия               ← MAX_CALL_DEPTH
дерево собрано неверно                  ← дефект движка, не скрипта
```

Эти четыре ситуации сегодня — обычные `WdlRuntimeError`, и после появления `catch`
их придётся развести: **`FatalError` не наследует `Exception`** и не ловится ни
типизированным `catch`, ни `catch (e)`, ни `try?`.

Причина простая: все четыре означают «выполнение больше не может продолжаться», а не
«эта операция не удалась». Скрипт, который «поймал» прерывание потока и продолжил
работу, — это ровно тот случай, ради которого приложение и звало `interrupt()`.
`finally` и `defer` при этом **выполняются**: закрыть файл на пути наружу можно
и нужно, а вот подавить причину — нет.

Хосту `FatalError` приходит отдельным типом, и по нему видно, что скрипт не просто
ошибся, а был остановлен.

### Свои ошибки

Наследование обычное, [со всеми правилами классов](classes.md#наследование).
Одна оговорка: поле [перекрывает метод](access.md), поэтому поле с именем `text`
закроет собой `text()` — своим полям стоит давать другие имена.

```wdl
class ParseError(raw) : Exception("не число: " + raw)

class HttpError(code, url) : Exception("HTTP " + code + " от " + url) {
    fun retriable() => code >= 500
}

class ConfigError(path, cause) : Exception("конфиг '" + path + "' не прочитан", cause)
```

Ловятся они так же, как встроенные, и по той же причине: `is` не различает, кто
объявил класс.

```wdl
try {
    load(path)
} catch (e is ConfigError) {
    println(e.message)
    if (e.cause != null) println("  причина: ", e.cause.text())
}
```

**Трейт вместо базового класса.** Если ошибки нужно группировать не по происхождению,
а по свойству — «это можно повторить», «это надо показать игроку», — для этого есть
[трейт](classes.md#трейты), и `catch (e is Retriable)` работает ровно так же, как
по классу:

```wdl
trait Retriable { fun delayMs() }

class HttpError(code, url) : Exception("HTTP " + code) with Retriable {
    fun delayMs() => 500 * code / 100
}
```

Это то, чего иерархия классов дать не может: одна ошибка бывает и `HttpError`,
и `Retriable`, а родитель у класса [ровно один](classes.md#наследование).

## throw

```wdl
throw new ParseError(text)
throw new Exception("так нельзя")
throw e                          // повторный бросок: место и трейс сохраняются
```

Инструкция, а не выражение — как `return`. Значение обязано быть экземпляром
`Exception` или его наследника:

```
config.wdl:8:11: ошибка: бросить можно только экземпляр Exception, а здесь string ("ой")
  8 |     throw "ой"
    |           ^^^^
```

**Почему нельзя бросать что попало.** Lua и JavaScript разрешают `throw 5`, и цена
этого видна в любом `catch`: прежде чем спросить у ошибки что-нибудь, надо проверить,
что это вообще объект. Ограничение здесь стоит одной строки в интерпретаторе и убирает
эту проверку из каждого обработчика навсегда.

`;` после `throw` подчиняется [общему правилу](statements.md#границы-инструкций-и-ошибки)
и обязательной не становится: в отличие от `return`, у `throw` аргумент всегда есть,
двусмысленности нет.

## try / catch / finally

```wdl
try {
    risky()
} catch (e is IoError, ValueError) {      // несколько типов в одном обработчике
    println("не вышло: ", e.text())
} catch (e is Exception) {
    println("что-то ещё: ", e.message)
    throw e
} finally {
    cleanup()
}
```

Правила:

* **тело `try` — всегда блок**, а не одиночная инструкция. Причина та же, что
  [у тела метода](classes.md#методы): следующей строкой идёт `catch`, и без скобок
  границу пришлось бы угадывать;
* **`catch`-ов сколько угодно, включая ноль**, если есть `finally`. `try { } finally { }`
  без обработчиков — законная и частая форма;
* **порядок важен**: берётся первый подходящий обработчик, сверху вниз, как в Java.
  Обработчик, до которого нельзя дойти (`catch (e)` выше `catch (e is IoError)`), —
  работа линтера, а не ошибка: правило «первый подходящий» читается однозначно и без
  анализа достижимости;
* **`catch (e)` без типа** — то же, что `catch (e is Exception)`. Отдельной формы
  «поймать вообще всё, включая фатальное» в языке нет;
* **имя обработчика живёт только в его блоке** — как параметр функции. Своя область
  на каждый `catch`, и `e` из одного не виден в другом.

Тип после `is` — **имя**, а не выражение, как после `:` и `with` в
[объявлении класса](classes.md#порядок-объявлений-свободен), и по той же причине:
имя видно глазами. Квалифицированная форма работает: `catch (e is db.QueryError)`.

### finally

Выполняется при **любом** выходе из `try`: нормальном, через ошибку, через `return`,
`break`, `continue` и на пути `FatalError`.

**`return`, `break` и `continue` внутри `finally` запрещены — ошибка разбора.**

```
job.wdl:14:9: ошибка: 'return' в блоке 'finally' запрещён: он молча погасил бы
ошибку, которая сейчас летит наружу. Верните значение из тела 'try' или из 'catch'
```

Это та же линия, что и `if (x = 5)`: конструкция, у которой единственное применение —
незаметно проглотить ошибку, не разбирается в принципе. В Java она разрешена и служит
источником багов, которые не видно при чтении.

Ошибка, брошенная в самом `finally`, [подавляет летящую](#подавленные-ошибки) —
не затирая её.

### Вложенность и перезаворачивание

```wdl
fun loadConfig(path) {
    try {
        return parse(io.read(path));
    } catch (e is IoError, ParseError) {
        throw new ConfigError(path, e);       // причина сохранена в cause
    }
}
```

Цепочка `cause` — единственный способ не потерять исходное место, когда ошибка
пересекает слой. `e.report()` печатает всю цепочку сверху вниз.

## Сахар: try? и try!

Две формы для случаев, где полный `try/catch` — три строки ради одного значения.
Обе — **выражения**, в отличие от инструкции `try`.

```wdl
n = try? parseNumber(text)            // ошибка → null
if (n == null) n = 30

port = try! config.port()             // «здесь ошибки быть не может»
```

| Форма | Ошибка `Exception` | `FatalError` |
|---|---|---|
| `try? выражение` | результат `null` | летит наружу |
| `try! выражение` | превращается в `FatalError` | летит наружу |

**`try?` — это «мне не важно, что именно случилось».** Ровно тот случай, ради которого
иначе пишут `catch (e) {}` — самую вредную конструкцию в языках с исключениями, потому
что по ней не видно, проглотили её намеренно или забыли дописать. `try?` видно в строке.

**`try!` — утверждение, а не подавление.** Он не «игнорирует» ошибку, а объявляет её
невозможной: если она всё-таки случилась, это дефект скрипта, и ловить его обработчиком
неправильно — поэтому ошибка становится `FatalError` и уходит в хост с исходной причиной
в `cause`. Так же устроены `try!` в Swift и `unwrap()` в Rust.

Записываются слитно (`try?`, `try!`), и парсер этого требует: `try ?` с пробелом —
ошибка разбора с подсказкой. Двусмысленности с тернарным оператором нет (после `try`
левого операнда для `?` не существует), но одинаковая запись двух разных вещей
читателя сбивает.

**`?? ` в этот набор не входит.** `try? f() || 30` не заменяет его — ложны
[не только `null`](types.md#истинность), и `0` подменился бы тридцаткой. Оператор
«взять правое, только если левое `null`» языку нужен, но он про `null`, а не про
ошибки, и приходит [отдельно](#что-дальше).

## defer

```wdl
fun process(path) {
    file = io.open(path)
    defer file.close()                 // выполнится на любом выходе из блока

    for (line in file.lines()) {
        if (line == "") continue
        handle(line)                   // бросил — файл всё равно закроется
    }
}
```

* **Выполняется на выходе из своей области**, а не из функции. Блок в языке
  [и так создаёт область](control-flow.md#блок-создаёт-область-видимости), и `defer`
  просто следует общему правилу — второго понятия «где кончается область» не заводим;
* **обратный порядок**: последний записанный выполняется первым. Иначе нельзя было бы
  освобождать зависящие друг от друга ресурсы;
* **выполняется при любом выходе**: нормальном, через `return`, `break`, `continue`,
  через ошибку, на пути `FatalError`;
* **`return`, `break`, `continue` внутри `defer` запрещены** — тем же правилом
  и по той же причине, что в [`finally`](#finally);
* **тело `defer`** — одна инструкция (обычно вызов) или блок.

**В цикле `defer` срабатывает на каждой итерации**, потому что тело цикла — блок:

```wdl
for (name in names) {
    f = io.open(name)
    defer f.close()                    // закроется в конце этого прохода
    handle(f.read())
}
```

Это главное отличие от Go, где `defer` привязан к функции и такой цикл копит открытые
файлы до самого выхода — известная ловушка, которую приходится обходить лямбдой.
Привязка к области видимости убирает её по построению.

### defer против finally

Оба нужны, и делают они разное:

| | `defer` | `finally` |
|---|---|---|
| Пишется | рядом с захватом ресурса | в конце конструкции |
| Область | любой блок | только `try` |
| Проверка «а был ли ресурс» | не нужна: `defer` не записан, пока `open` не вернулся | нужна: `if (file != null)` |

Второе — та самая причина, по которой `finally` в примерах на Java обрастает
проверками на `null`: блок `finally` существует независимо от того, дошло ли
выполнение до захвата. Отложенное действие записывается **после** успешного захвата,
и записывать его нечему, если захват не удался.

## Ресурсы: Closeable и use

`defer` — общий механизм, и им можно закрыть что угодно. Но у ресурса есть контракт,
и язык умеет его проверять при объявлении класса — этим и стоит воспользоваться.

### Трейт Closeable

```wdl
trait Closeable {
    fun close()                        // требование: класс обязан это уметь
}
```

Встроенный трейт, лежит в корневой области рядом с `Exception`. Класс, который держит
что-то живое, подмешивает его и получает проверку **при объявлении**, а не при первом
`use`:

```wdl
class Connection(host, port) with Closeable {

    fun Connection() {
        this.socket = net.connect(host, port)
    }

    fun send(text) => socket.write(text)
    fun close() => socket.close()
}
```

Забыли `close` — [ошибка на строке `class`](classes.md#требования-проверяются-при-объявлении-класса),
тем же текстом и в тот же момент, что у любого другого трейта. Ради этого трейты
и заведены; никакого отдельного механизма для ресурсов язык не заводит.

### use

```wdl
use (conn = new Connection("localhost", 8080)) {
    conn.send("привет")
}                                      // close() вызван, что бы ни случилось
```

Что делает `use`:

1. вычисляет выражение и связывает имя в своей области — как `for (x in …)`;
2. **проверяет, что значение подмешивает `Closeable`**, и если нет — ошибка на месте:

```
net.wdl:4:12: ошибка: 'use' работает со значением, которое умеет закрываться,
а класс 'Point' не подмешивает трейт 'Closeable'
```

3. выполняет тело;
4. зовёт `close()` на любом выходе — включая ошибку и `FatalError`.

Несколько ресурсов — через запятую, закрываются в обратном порядке:

```wdl
use (src = io.open(from), dst = io.create(to)) {
    dst.write(src.read())
}                                      // сначала dst.close(), затем src.close()
```

**Если бросил сам захват**, ресурсы, захваченные левее, закрываются, а тело
не выполняется вовсе. Это то же самое правило «отложено только после успеха»,
что у `defer`, — просто записанное конструкцией.

### Подавленные ошибки

Ошибка при закрытии, когда наружу уже летит другая, не должна её затирать: первая
ошибка объясняет, что пошло не так, вторая — лишь следствие.

```wdl
use (f = io.open(path)) {
    throw new ValueError("данные битые")    // ← эта уйдёт наружу
}                                           // ← f.close() бросил IoError: он в suppressed
```

```wdl
catch (e is ValueError) {
    println(e.message)                      // данные битые
    for (s in e.suppressed) println("при закрытии: ", s.text())
}
```

Если летящей ошибки нет, ошибка `close()` — обычная ошибка и летит сама. Правило то же
у `defer` и у `finally`: **подавляется то, что случилось на пути наружу, а не то, ради
чего мы шли наружу.**

### Почему у Closeable нет open()

Трейт мог бы требовать пару `open()`/`close()`, и `use` звал бы `open()` перед телом.
Мы этого не делаем, и вот почему:

* **открытие уже есть — это `new` и [фабрики](classes.md#фабрики-fun-userof)**.
  Второй способ инициализации означал бы объект в состоянии «создан, но не открыт»,
  по которому непонятно, что можно звать, а что нельзя. Сейчас у экземпляра одно
  состояние: он есть, значит он готов;
* **`use` без `open()` работает с чем угодно, что умеет закрываться** — в том числе
  со значением, полученным из функции (`use (f = pool.take())`), которое открывать
  второй раз нельзя;
* ленивое открытие никуда не девается — оно живёт внутри класса, как в примере
  `Connection` выше, и снаружи невидимо.

Если ресурс всё же обязан открываться отдельно (двухфазный протокол, повторное
использование), это выражается своим трейтом в библиотеке — `use` для него просто
не применяется, а `defer` применяется.

### Встроенные классы и Closeable

`File` ресурсом не является: его `read` и `write` открывают и закрывают поток внутри,
поэтому закрывать там нечего. Открытое отдают `io.open(path)`, `io.create(path)`
и `io.appendTo(path)` — классы `io.Reader` и `io.Writer`, у которых дескриптор
держится до `close()`.

**Нативный класс подмешивает трейт значением, а не именем**: `NativeClass.Builder`
получил `.with(trait)`, и `conformsTo` отвечает `true` подмешанному трейту.
Требования проверяются **при сборке класса** — то есть при старте приложения:
забыли `close` — исключение из построителя, а не непонятная ошибка у автора скрипта
через месяц. Это то же обещание и в тот же момент, что у класса на wdl.

Трейт при этом берётся **значением из области видимости запуска**, а не строится
построителем: `Closeable` объявлен прелюдией и принадлежит запуску — по той же
причине, по которой `IndexError` одного запуска не равен `IndexError` другого.
Поэтому классы потоков собираются в `installTo`, а не статическим полем.
Отдельный `NativeTrait` из [«Нативных модулей», 6.1](../Нативные%20модули.md)
для этого не понадобился; он всё ещё нужен для обратного направления — чтобы
скрипт реализовывал интерфейс, объявленный библиотекой.

## Трассировка: два механизма

У ошибки два разных стека, и путать их нельзя: один описывает путь по скрипту, другой —
путь по методам интерпретатора. Первый нужен автору скрипта, второй — тому, кто чинит
движок или библиотеку.

### Скриптовый трейс — всегда

```
config.wdl:5:16: ошибка: ValueError: не число: "abc"
  5 |     if (n == null) throw new ValueError("не число: " + text)
    |                    ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  в parseNumber (config.wdl:12:24)
  в loadTimeout (config.wdl:20:15)
```

Собирается из **кадров вызова**: имя функции, место вызова, файл. Кадр — неизменяемая
запись со ссылкой на родительский, и создаётся он там же, где уже создаётся контекст
вызова (`ExecutionContext.call`). Ничего изменяемого и никакого «стека» как структуры
данных: цепочка ссылок разворачивается в список только когда ошибку действительно
бросили.

Почему именно так, а не изменяемым списком в контексте: [контекст неизменяем](../wdl-core/src/main/java/ru/wds/wdl/runtime/ExecutionContext.java)
и это держит на себе изоляцию нескольких интерпретаторов в процессе. Изменяемый стек
пришлось бы либо делить между вложенными контекстами (и тогда функция, вызванная
из другого потока, писала бы в чужой), либо копировать на каждый вызов. Цепочка кадров
стоит одного маленького объекта на вызов — примерно как `callDepth`, который она
заодно и заменяет.

**Кадр называет функцию и место, откуда её позвали**, а не строку, на которой рвануло:
где рвануло, показывает сама ошибка, и повторять это в каждой строке трейса незачем.
Отсюда и файл в кадре — файл **вызывающего**: смещение места вызова осмысленно только
в его исходнике. Свой файл функция из модуля показывает в другом месте — в самой
ошибке, у которой место броска внутри тела.

Отдельной строки «в главном скрипте» нет: она повторяла бы место вызова из последнего
кадра, а имени у главного файла в этой роли всё равно нет.

### Java-трейс — только там, где он что-то значит

`WdlRuntimeError` сегодня стек Java не заполняет (`super(message, null, false, false)`),
и это остаётся: он описывал бы путь по `visitBinary` → `Operations.binary`, который
не интересен никому.

Java-стек есть ровно у одной категории — `JavaException`: исходное исключение пришло
из Java, стек у него уже собран, и выбрасывать эту информацию нельзя. Оно хранится
как `cause` самого `WdlRuntimeError`, а скрипту отдаётся **методом**, а не полем:

```wdl
catch (e is JavaException) {
    println(e.message)                          // коротко — это в лог всегда
    for (line in e.javaTrace()) println("  ", line)   // подробно — по требованию
}
```

Метод, а не массив, по двум причинам: сорок строк не должны попадать в `println(e)`
и в перебор полей, и собирать их незачем, пока не спросили. Внутри это поле, в котором
лежит функция, — для скрипта разницы нет (`e.javaTrace()` пишется одинаково), а языку
не понадобилось ни одного нового понятия: функция и так значение, а значение и так
кладётся в поле.

**Режим отладки.** Консольный запуск с `--debug` печатает Java-стек там, где он
вообще есть, — у `JavaException`. Заполнять стек ещё и у обычных ошибок движка
(`WdlRuntimeError` создаётся с `super(message, null, false, false)`) пока нельзя:
флаг принадлежал бы запуску, а ошибка создаётся в полусотне мест, у которых контекста
под рукой нет. Когда понадобится — это отдельная работа, и стоит она правки всех
этих мест.

| | Скриптовый трейс | Java-трейс |
|---|---|---|
| У кого | у всех ошибок | у `JavaException`; у остальных — по флагу отладки |
| Стоимость | объект на вызов | заполнение стека JVM на бросок |
| Кому нужен | автору скрипта | тому, кто чинит движок или библиотеку |
| Где виден | в выводе ошибки, `e.trace` | `e.javaTrace()`, лог хоста |

## Вывод и логирование

**Движок ничего не печатает сам.** Ошибка — не вывод скрипта, а результат запуска:
`Output` остаётся тем, куда пишет `println`, и подмешивать туда диагностику нельзя —
приложение, собирающее вывод скрипта в игровой чат, не ждёт там стектрейсов.

Непойманная ошибка доходит до хозяина запуска, и дальше решает он:

```java
try {
    interpreter.run(unit, context);
} catch (WdlRuntimeError error) {
    log.warn("скрипт {} упал: {}: {}", name, error.kindName(), error.getMessage());
    // Диагностика рисуется тем же кодом, что и ошибки разбора; трейс — рядом, строками.
    log.debug("{}", new Diagnostics(error.source()).render(error.toDiagnostic()));
    error.trace().forEach(frame -> log.debug("  {}", frame));
    useDefaults();
} catch (FatalError fatal) {
    log.error("скрипт {} остановлен: {}", name, fatal.getMessage());
} finally {
    context.shutdownModules();
}
```

Консольный запуск (`wdl-cli`) печатает в stderr полную форму — диагностику
с подчёркиванием плюс скриптовый трейс, — а с флагом `--debug` добавляет Java-стек
там, где он есть. Формат тот же, что у ошибок разбора: `Diagnostics.render` умеет всё,
кроме строк трейса, и они дописываются рядом.

**Внутри скрипта** логирование — обычный вывод:

```wdl
catch (e is Exception) {
    println("[warn] ", e.text())        // "IoError: не удалось обратиться к файлу: нет.txt"
    println(e.report())                 // текст + место + трейс + цепочка cause
}
```

`println(e)` печатает экземпляр [по общему правилу](classes.md#печать-и-равенство) —
`ValueError{"message": "не число", …}`. Когда язык научится [спрашивать у экземпляра
метод `text`](classes.md#печать-и-равенство), печать ошибок станет короткой сама собой,
без единого исключения из правил.

## Кейсы

Что происходит в углах — коротко и по одному месту на случай.

| Ситуация | Поведение |
|---|---|
| `return` внутри `try` с `finally` | `finally` выполняется, значение возвращается |
| `return` внутри `try`, `finally` бросает | ошибка `finally` побеждает, возврат отменяется |
| `break` из `try` внутри цикла | `finally` выполняется, цикл прерывается |
| ошибка в `catch` | летит наружу; `finally` выполняется |
| ошибка в `finally` при летящей ошибке | летит первая, вторая — в её `suppressed` |
| ошибка в `defer` при летящей ошибке | то же правило |
| ошибка в `close()` при `use` | то же правило |
| `throw e` внутри `catch` | место и трейс сохраняются от первого броска |
| ошибка в конструкторе класса | обычная ошибка; экземпляра нет, закрывать нечего |
| ошибка в захвате `use` слева направо | закрывается взятое левее, тело не выполняется |
| `close()` дважды у потока `sys.io` | не ошибка: второй раз отвечает `false` |
| ошибка в значении параметра по умолчанию | обычная ошибка на месте вызова |
| ошибка при выполнении `import` | `ImportError` с местом на строке `import` |
| ошибка внутри модуля | летит в импортировавший файл; в трейсе видны оба файла |
| `try` вокруг `import` | ловится: `import` — [обычная инструкция](modules.md) |
| прерывание потока внутри `try` | `FatalError`: `catch` не видит, `finally` и `defer` выполняются |
| глубокая рекурсия внутри `try` | то же |
| `try?` вокруг вызова, бросившего `FatalError` | не гасится, летит наружу |
| ошибка в `close()` библиотеки при `shutdownModules` | [не роняет отработавший запуск](embedding.md#что-закрывать-после-запуска) |

Разобранный пример на два ресурса и три вида ошибок:

```wdl
import sys.io as io

class ConfigError(path, cause) : Exception("конфиг '" + path + "' не прочитан", cause)

fun parseName(text) {
    if (text == "") throw new ValueError("имя пустое");
    if (len(text) > 32) throw new ValueError("имя длиннее 32 символов: " + len(text));
    return text;
}

fun loadName(path, fallback) {
    try {
        use (f = io.open(path)) {
            return parseName(f.read());
        }
    } catch (e is ValueError) {
        throw new ConfigError(path, e);           // это уже не «нормально»
    } catch (e is RuntimeError) {
        // Файла нет — и это нормально. Пока сюда приходит RuntimeError:
        // своего IoError у sys.io ещё нет, см. «что осталось».
        println("[info] ", path, " недоступен, беру ", fallback)
        return fallback;
    }
}

try {
    println("имя: ", loadName("app.cfg", "без имени"))
} catch (e is ConfigError) {
    println("[error] ", e.message)
    println("        причина: ", e.cause.text())
}
```

## Почему это ложится на существующее ядро

Половина механики уже есть, и это не совпадение — она заводилась под то же самое.

* **Сигналы.** `break`, `continue` и `return` — уже наследники `RuntimeException`,
  которые проходят сквозь любую вложенность, и ловят их ровно те методы, которым это
  нужно. Ошибка идёт тем же путём, а раскрутка достаётся от JVM бесплатно.
* **`WdlRuntimeError` уже везде.** Все существующие броски (их несколько десятков
  в `Interpreter`, `Operations`, `Files`, `Json`, `Http`) становятся ловимыми, не меняя
  ни строчки: класс ошибки по умолчанию — `RuntimeError`, а конкретные проставляются
  постепенно.
* **Экземпляр — это карта пар.** Поля `at`, `trace`, `suppressed` записываются обычным
  `put`, никакого нового вида значения не требуется.
* **Трейты уже проверяются при объявлении класса.** `Closeable` — обычный трейт,
  и «забыл `close`» ловится существующим кодом `Linker`.
* **`Span` есть у каждого узла.** Место броска и места кадров брать неоткуда больше
  и не надо.

Новых **типов значений** не появляется: ошибка — это `object`, `typeof(e)` даёт
`"object"`, `e is IoError` даёт `true`. Список `ValueType` остаётся закрытым.

## Как это устроено в коде

| Слой | Что добавилось |
|---|---|
| `lexer` | `THROW`, `TRY`, `CATCH`, `FINALLY`, `DEFER`, `USE` — по строке в `TokenType`, таблицы строятся из него же |
| `ast/stmt` | `ThrowStmt`, `TryStmt` (тело, список `Catch`, блок `finally`), `DeferStmt`, `UseStmt` (список привязок, тело) |
| `ast/expr` | `TryExpr(Expr inner, TryStyle style)` — `OPTIONAL` для `try?`, `FORCED` для `try!` |
| `ast/visitor` | по методу в `StmtVisitor` и `ExprVisitor` — компилятор проведёт по `Interpreter`, `AstDumper` и тестовому `SExprPrinter` |
| `parser` | разбор шести конструкций; тип в `catch` — имя или `alias.имя`, как у родителя класса; запрет `return`/`break`/`continue` внутри `finally` и `defer` — полем-счётчиком по образцу `functionDepth`; флаг `BlockStmt.hasDefer()` ставится при разборе |
| `runtime/WdlError` | общий предок `WdlRuntimeError` и `FatalError`: место, файл, `toDiagnostic()`. Нужен затем, что границы выполнения приписывают файл обоим одинаково, а хост ловит их по отдельности |
| `runtime/WdlRuntimeError` | поля `kind` (какой класс ошибки), `payload` (значение, созданное лениво), `trace`, `javaCause`, `module` |
| `runtime/FatalError` | новый `RuntimeException` вне `Exception`-иерархии языка; туда переезжают `checkInterrupted`, `stackExhausted` и превышение `MAX_CALL_DEPTH` |
| `runtime/Frame` | цепочка кадров: функция, место вызова, файл вызывающего, родитель; создаётся в `ExecutionContext.call` и заменяет собой `callDepth` — глубина считается один раз при создании, поэтому не `record` |
| `runtime/Prelude` | разобранная один раз `Program` прелюдии — неизменяемое статическое поле; выполняется в корневой области при `ExecutionContext.fresh` |
| `runtime/PreludeTypes` | реестр типов прелюдии на запуск (рядом с `Modules` и `Linker`): движок берёт `TypeError` и `Closeable` отсюда, а не поиском имени в области |
| `runtime/Deferred` | отложенные действия одной области: тело плюс контекст, в котором его записали |
| `runtime/Interpreter` | `visitThrow`, `visitTry`, `visitDefer`, `visitUse`, `visitTryExpr`; оборачивание чужих `RuntimeException` в `JavaException` в `visitCall` и `visitNew`; выполнение отложенных в `visitBlock`; `onTheWayOut` — одно правило подавления на `finally`, `defer` и `close` |
| `embed` | `NativeClass.Builder.with(trait)` и проверка требований при сборке класса; `TraitValue.requiredMethods()` — то единственное, что для этой проверки нужно знать о трейте |
| `wdl-stdlib` | `io.open`/`io.create`/`io.appendTo` и классы `io.Reader`, `io.Writer` с `close()`; собираются в `installTo`, потому что обещают трейт запуска |
| `wdl-cli` | печать вида ошибки и скриптового трейса, флаг `--debug` для Java-стека |

### Прелюдия

`Exception` и его потомки объявлены **на wdl**, а не построителем нативных классов,
и причина техническая: [наследоваться от нативного класса скрипт пока не может](embedding.md#чего-пока-нет),
а весь смысл `Exception` — в том, чтобы от него наследовались.

```
wdl-core/src/main/resources/ru/wds/wdl/runtime/prelude.wdl
```

Файл разбирается один раз при загрузке класса `Prelude`; дерево неизменяемо, поэтому
статическое поле здесь не нарушает [запрет на изменяемую статику](../CLAUDE.md).
Выполняется прелюдия в корневой области каждого запуска — там же, где `Builtins.installTo`
кладёт `println`.

Следствие, о котором стоит знать: формы классов принадлежат запуску, поэтому `IoError`
из одного запуска и `IoError` из другого — [разные классы для `is`](embedding.md#одно-дерево-много-запусков).
Внутри запуска всё как обычно; хосту, который различает ошибки между запусками,
надо смотреть на имя класса, а не на тождество.

### Ленивая материализация

Значение-экземпляр создаётся, только когда ошибку действительно ловят:

* движок бросает `WdlRuntimeError` с указанием класса — как сейчас, без аллокаций
  сверх самой ошибки;
* `visitTry`, найдя подходящий `catch`, создаёт экземпляр и связывает его с именем
  обработчика;
* `throw` из скрипта, наоборот, начинается со значения — оно кладётся в `payload`
  и переиспользуется.

Непойманная ошибка не материализуется никогда: на пути в хост объект не нужен.
Проверка `e is IoError` до материализации делается по классу из реестра — сравнением
форм, без создания экземпляра.

## План работ

Этапы шли так, чтобы каждый давал работающее целое. Все восемь сделаны.

1. ✅ **Иерархия без синтаксиса.** Прелюдия, реестр `PreludeTypes`, `kind`
   у `WdlRuntimeError`, `FatalError` и переезд в него трёх ситуаций.
2. ✅ **`throw` / `try` / `catch` / `finally`.** Токены, узлы, разбор, выполнение,
   материализация, запрет `return` в `finally`. Заодно сделаны и подавленные ошибки:
   без них ошибка из `finally` затирала бы ту, ради которой мы идём наружу.
3. ✅ **Скриптовый трейс.** `Frame`, замена `callDepth`, печать в CLI.
4. ✅ **`try?` и `try!`.**
5. ✅ **`defer`.** Флаг `hasDefer` в блоке, отложенные в контексте, обратный порядок.
6. ✅ **Ресурсы.** `Closeable` в прелюдии, `use`, `NativeClass.Builder.with(trait)`,
   `io.open`/`io.create`/`io.appendTo` с классами `io.Reader` и `io.Writer`.
7. ✅ **`JavaException`.** Оборачивание на границе вызова, `javaTrace()`, флаг `--debug`.
8. ✅ **Документы и примеры.** `examples/errors.wdl`, `examples/resources.wdl`,
   [состояние языка](overview.md#что-уже-работает) и `README.md`.

### Что осталось

* **Классы ошибок стандартной библиотеки.** `IoError`, `JsonError`, `HttpError`
  ещё не объявлены: `sys.io`, `sys.json` и `sys.net.http` бросают `RuntimeError`,
  и ловятся они пока по нему. Механизма для этого не хватает ровно одного —
  библиотека должна уметь объявить класс-наследник `Exception`, а
  [наследоваться от нативного класса пока нельзя](embedding.md#чего-пока-нет);
  значит, нужен либо кусок wdl в самой библиотеке, либо путь «класс скрипта
  наследует нативный» из раздела 6.3 «Нативных модулей».
* **`NativeTrait`.** Обратное направление: библиотека объявляет интерфейс, а скрипт
  его реализует. Подмешивание трейта нативному классу (`.with`) уже есть и закрывает
  `Closeable`; `NativeTrait` нужен для `net.Handler` и подобного — см.
  [«Нативные модули», 6.1](../Нативные%20модули.md).
* **`??`** и остальное — в разделе [что дальше](#что-дальше).

### Три расхождения с тем, что здесь написано изначально

Все три — не упрощения, а поправки, и причины у них разные:

1. **Заголовок `Exception` несёт `kind`, `at`, `trace` и `suppressed`** со значениями
   по умолчанию, хотя заполняет их движок при броске. Иначе `text()` у созданной,
   но ещё не брошенной ошибки искала бы имя, которого в экземпляре нет.
2. **Кадр трассировки помнит файл вызывающего, а не функции.** `callSite` — место
   в тексте того, кто позвал, и осмысленно оно только в его исходнике. Строки
   «в главном скрипте» нет: она повторяла бы место вызова из последнего кадра.
3. **`javaTrace` — поле с функцией, а не отдельный вид члена.** Для скрипта запись
   та же (`e.javaTrace()`), а языку не понадобилось ни одного нового понятия.

### Тесты

По сложившемуся разделению: `ErrorParserTest` сравнивает **форму дерева**,
`ErrorTest` — напечатанное и текст ошибки. Проверено:

* форма дерева: `try` с несколькими `catch`, `catch` без типа, `try` без `catch`,
  `use` с несколькими привязками, `try?`/`try!` в выражении и в инструкции,
  флаг `hasDefer` у блока и его отсутствие у внешнего;
* ошибки разбора: `catch` без `try`, `return` в `finally` и в `defer`, `try ?`
  с пробелом, тело `try` и `use` без скобок, два ресурса под одним именем;
* выполнение: порядок `finally` при `return`/`break`/ошибке, выбор первого подходящего
  обработчика, ловля по предку и по трейту, цепочка `cause`, повторный бросок,
  `suppressed` при ошибке в `finally`, в `defer` и в `close`;
* `FatalError`: прерывание не ловится, `finally` при нём выполняется, `try?` его
  не гасит, `try!` несёт причину;
* трейс: три уровня вызовов с точным текстом кадров, отсутствие трейса на верхнем
  уровне, доставка трейса хозяину запуска;
* ресурсы: `close()` при нормальном выходе, при ошибке и при `return`; обратный
  порядок; ошибка в самом захвате закрывает взятое левее; класс без `Closeable`
  в `use`; требование трейта на строке `class`;
* `JavaException`: библиотека-заглушка, бросающая `IllegalStateException`, и то,
  что `catch (e is RuntimeError)` её не видит;
* `sys.io`: `io.create`/`io.open` с `use`, чтение после `close()`.

## Открытые вопросы

1. **Ловится ли `NameError`.** Сейчас предложено «да»: опечатка в имени переменной —
   такая же ошибка выполнения, как остальные. Альтернатива — считать её дефектом
   скрипта и не давать ловить, как `FatalError`. Первое проще объяснить, второе
   надёжнее ловит опечатки в редко исполняемых ветках.
2. **Нужен ли `errdefer`** — отложенное действие только на пути ошибки (Zig). Нужен
   для отката частично построенного состояния; без него это пишется через флаг.
   Решение — после первого реального случая.
3. **`retry` и рестарты.** [Система условий Common Lisp](#что-дальше) даёт обработчику
   возможность вернуться в точку ошибки. Мощно, но требует не разрушать кадр
   при броске — решение уровня всего интерпретатора, и принимать его пришлось бы
   до трассировки, а не после.
4. **Двухфазные ресурсы** (`open()`/`close()` вместо одного `close()`) — [разобрано
   выше](#почему-у-closeable-нет-open); если найдётся случай, где ленивое открытие
   внутри класса не годится, решение придётся пересмотреть.

## Что дальше

* **`??`** — «взять правое, если левое `null`»: пара к `try?`, но про `null`, а не
  про ошибки, поэтому приходит отдельно.
* **`match` по ошибке.** Токены `MATCH` и `CASE` [уже зарезервированы](../wdl-core/src/main/java/ru/wds/wdl/lexer/TokenType.java);
  `catch` при этом никуда не денется — `match` про значения, `catch` про поток управления.
* **Лимиты в `ExecutionContext`** — шаги и таймаут. Ложатся в ту же категорию, что
  прерывание потока: `FatalError`, который скрипт поймать не может.
* **Печать через `text()`** — как только [`CallContext` научится звать функцию](classes.md#печать-и-равенство),
  `println(e)` начнёт печатать ошибку коротко, без единого исключения из правил печати.
