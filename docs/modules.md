# Модули

`import` выполняет другой файл и приносит оттуда имена. Всё остальное — следствия
одного решения: **модуль — это обычный скрипт, а не особый вид файла.** У него нет
ни списка экспорта, ни заголовка, ни объявления «я модуль». Содержимое модуля — то,
что осталось в его корневой области после выполнения.

```wdl
import lib.geometry            // имена модуля становятся своими
import lib.geometry as g       // имена модуля доступны через g
```

Рабочие примеры на все случаи — в [examples/modules/](../examples/modules).

## Две формы

**Развёрнутый** — `import lib.geometry` — заводит имена модуля в текущей области,
как будто их объявили здесь:

```wdl
import lib.geometry

println(PI)                    // 3.14159
println(area(2))               // 12.56636
p = new Point(3, 4)
```

**Именованный** — `import lib.geometry as g` — заводит одно имя, значение-модуль.
Дальше работает обычное обращение, и никакого особого синтаксиса для модулей
не понадобилось (см. [единое обращение](access.md)):

```wdl
import lib.geometry as g

println(g.PI)                  // 3.14159
println(g["PI"])               // то же самое
p = new g.Point(3, 4)          // класс — обычное значение, new берёт выражение
```

Обе формы нужны по разным причинам, и выбор между ними — вопрос читаемости, а не
возможностей. Развёрнутый короче там, где модуль один и имена в нём говорящие.
Именованный не даёт двум модулям молча перекрыть имена друг друга и сразу отвечает
на вопрос «откуда это взялось».

## Область действия

`import` — инструкция, а не объявление верхнего уровня. Стоять она может где угодно,
и живёт ровно столько, сколько живёт её область:

```wdl
def circle(radius) {
    import lib.geometry as g
    return g.area(radius);
}

println(circle(1))
// здесь ни g, ни PI, ни Point нет
```

Никакого особого правила для этого не писалось: имена заводятся в текущей области —
той же, куда их завели бы `def` или `const` на том же месте.

Исчезает при этом **имя, а не сделанное им**: присваивание `PI = 3` внутри функции
меняет переменную модуля, и это переживает выход из области ровно так же, как
переживает его вызов `g.bump()`. Область распоряжается именами, а не чужим файлом.

Отсюда же и второе: **импорт не поднимается** до начала выполнения, в отличие
от объявлений функций и классов ([функции](functions.md), [классы](classes.md)).
Причина в побочном эффекте: поднять `import` значило бы выполнить чужой файл
до первой строки скрипта — в порядке, которого в тексте не видно.

## Файл читается на своей строке

**Модуль не читается, пока до его `import` не дошло выполнение.** Ни разбор главного
скрипта, ни разбор модуля не открывают файлы, которые в них импортируются. Из этого
следует то, ради чего всё и сделано:

```wdl
def loadPlugin() {
    import plugins.generated       // этого файла ещё нет
    return start();
}

println("скрипт работает, плагин ещё не нужен")
```

Скрипт разбирается и работает, хотя модуля не существует. Он появится позже — его
создаст приложение, сгенерирует другой скрипт, отдаст база, — и `loadPlugin()`
загрузит его как обычно. Рабочий пример: [examples/modules/late.wdl](../examples/modules/late.wdl).

Второе следствие — за неиспользуемое не платят. Импорт в ветке, куда выполнение
не зашло, не стоит ничего: ни чтения файла, ни разбора.

Цена у этого одна, и она честная: **ошибки модуля называются на строке `import`,
а не до запуска.** Ненайденный файл, синтаксическая ошибка внутри модуля, невыполненное
требование трейта в его классе — всё это находится тогда, когда модуль загружается.
Строки скрипта выше уже отработали.

**Модуль не видит того, кто его импортирует.** Его корневая область стоит поверх
корня запуска — там, где лежат встроенные функции и библиотеки, подключённые
приложением, — а не поверх области с `import`. Иначе один и тот же модуль работал бы
по-разному в зависимости от места импорта.

## Пути

Путь пишется двумя способами:

```wdl
import lib.math                // именами через точку: точка — каталог
import "lib/math"              // строкой: слэш — каталог
import "lib/math.wdl"          // расширение можно не опускать
import "имя-модуля (1)"        // строка нужна для всего, что не является именем
```

Точка в первой форме означает каталог, а не обращение к полю: значения тут ещё нет —
файл не выполнялся. Ключевое слово в такой записи не принимается (`import lib.class`),
и совет в ошибке один: записать строкой.

**Путь считается от каталога того файла, где написан `import`.** Модуль в подкаталоге
ссылается на соседа по короткому имени и не знает, откуда запустили главный скрипт, —
поэтому набор файлов переносится целиком. Ведущий `/` означает «от корня запуска»,
то есть от каталога главного скрипта:

```wdl
// в файле lib/strings.wdl
import geometry                // это lib/geometry
import "/config"               // это config рядом с главным скриптом
```

Все записи одного пути приводятся к одному **ключу** — `lib/geometry`. Ключ и есть
имя модуля: он стоит в сообщениях об ошибках и по нему модуль узнают в реестре.
Путь вверх (`"../shared/util"`) разрешён, но оставляет `..` в ключе, и тот же файл,
найденный откуда-то ещё коротким путём, окажется для движка другим модулем.

Откуда брать исходники, решает не ядро, а запуск: консольный интерпретатор читает
файлы рядом со скриптом, встроенный движок задаёт источник сам
(`ExecutionContext.withModules`, см. [встраивание](embedding.md)). Пока источник
не задан, `import` отвечает ошибкой: движок внутри чужого приложения не должен
читать его файлы без спроса.

## Встроенные модули

Модуль бывает не файлом, а библиотекой на Java. Приложение регистрирует её под именем,
и дальше всё как обычно:

```wdl
import sys.io as io
import sys.json as json

data = json.parse(io.read("config.json"))
println(data.port)
```

Разницы для скрипта нет никакой, и это не совпадение: модуль в этом языке определён
как имена в области, а не как файл, — а кто их туда положил, интерпретатору незачем
знать. Поэтому у встроенного модуля те же две формы импорта, та же однократность,
тот же `typeof` → `module`, та же ошибка на опечатке в имени и та же изменяемость.
Что в библиотеке заморожено, решает она сама — `const` работает в ней так же, как
в файле модуля (в `sys.io` так объявлен `SEPARATOR`).

**Отличие ровно одно: встроенный модуль ищется по имени, а не по пути.** У него нет
каталога, значит и считать от каталога нечего:

```wdl
import sys.json               // всегда встроенный sys/json, из любого файла
import "sys/json"             // то же самое
import "./sys/json"           // файл sys/json.wdl рядом с этим файлом
import "/sys/json"            // файл sys/json.wdl рядом с главным скриптом
```

Путь, начинающийся с `.` или `/`, встроенным не считается никогда — это и есть способ
дотянуться до файла, чьё имя занято. В обратную сторону правило тоже работает:
`import sys.json` внутри `lib/tools.wdl` означает встроенный модуль, а не
`lib/sys/json.wdl`, — иначе одна и та же строка значила бы разное в разных файлах.

**Состав задаёт запуск.** Консольный интерпретатор даёт `sys.io`, `sys.json`,
`sys.net.http` и `std`; встроенный в приложение движок — то, что положило приложение,
и ничего сверх того. Не дали `sys.net.http` — его не существует, и обойти это нечем:
глобальной таблицы модулей в языке нет. Поэтому же в ошибке названы оба места,
где модуль искали:

```
модуль 'sys/sql' не найден, и встроенного модуля 'sys/sql' тоже нет
```

Что сейчас есть в наборе консольного запуска:

| Модуль | Что даёт |
|---|---|
| `sys.io` | `read`, `write`, `append`, `lines`, `exists`, `list`, `mkdirs`, `remove`, `size` и класс `File` |
| `sys.json` | `parse` — в значения языка, `stringify` — обратно, вторым аргументом отступ |
| `sys.net.http` | `get`, `post`, `put`, `delete`, `request` и класс `Response` (`status`, `body`, `headers`, `ok()`) |
| `std` | то же, что кладётся в область видимости по умолчанию: `pow`, `sqrt`, `abs`, `File`, `Random` |

```wdl
import sys.net.http as http
import sys.json as json

r = http.post("https://api.example.com/users",
        json.stringify({name: "Аня"}),
        {headers: {"Content-Type": "application/json"}, timeout: 5})

if (r.ok()) {
    println(json.parse(r.body).id)
} else {
    println("сервер ответил ", r.status)
}
```

Запрос синхронный: скрипт ждёт ответа на своей строке, как ждёт чтения файла.
Неблокирующая работа — отдельный механизм, которого пока нет.

Рабочий пример на файлы и JSON — [examples/sys.wdl](../examples/sys.wdl).
Как написать свой такой модуль — в [встраивании](embedding.md).

## Модуль выполняется один раз

Второй `import` того же файла отдаёт готовое значение — и это решение о смысле,
а не оптимизация. Иначе `import` внутри функции переразбирал бы файл на каждом
вызове, а два импорта одного модуля давали бы **два разных класса**:

```wdl
import lib.geometry
import lib.geometry as g

println(new Point(1, 2) is g.Point)    // true — класс один
```

Из однократности следует и то, что состояние модуля общее — и живое:

```wdl
import lib.counter as c

c.bump()
println(c.count)               // 1: обращение видит работу функций модуля
```

**И на запись тоже.** Импортировав модуль, с ним можно делать всё, что можно его
собственному коду: переменная меняется, `const` — нет. Иного правила не выйдет
объяснить — модуль и есть скрипт, а запрет снаружи означал бы, что импортёр слабее
автора файла без всякой причины.

```wdl
import lib.counter as c
import lib.geometry as g

c.count = 100
println(c.bump())              // 101: функции модуля считают от нового значения
g.PI = 3                       // ошибка: 'PI' нельзя присвоить: это константа
```

Развёрнутый импорт заводит **не копию, а то же самое имя**, поэтому обе формы
равносильны и после двух импортов одного файла означают одну ячейку:

```wdl
import lib.counter
import lib.counter as c

count = 5
println(c.count)               // 5
```

Цена у этого та же, что и у чтения, и следует из однократности: запись видят все,
кто импортировал модуль. Настроить модуль снаружи и починить его поведение из двух
разных файлов — одно и то же действие, и второе так же законно, как первое. Рабочий
пример — [examples/modules/mutate.wdl](../examples/modules/mutate.wdl).

Если модуль через цепочку импортов просит сам себя, отдавать нечего — он ещё
не выполнен. Такой скрипт останавливается с цепочкой в сообщении:

```
циклический импорт: ring/a → ring/b → ring/a
```

## Модуль — отдельный тип

`typeof(g)` даёт `module`, а не `object`. Устроен модуль так же — набор пар
«имя — значение», — но ведёт себя иначе, и обе разницы намеренные.

**Несуществующее имя — ошибка, а не `null`.** Состав объекта скрипт собирает сам
и вправе проверять ключи; состав модуля задан его файлом и автору известен. Опечатка
в `g.aria` должна называться сразу, а не через два шага, когда `null` попробуют вызвать.

Правило работает и на запись: `g.aria = ...` — та же ошибка. Присваивание модулю
не заводит новых имён, хотя объекту заводит, — и по той же причине.

Печатается модуль заголовком — `module lib/geometry`, — а не содержимым: в корне
файла бывают десятки имён, и `println(g)` не должен выливать в консоль весь модуль.

Рабочий пример на всё это — [examples/modules/inherit.wdl](../examples/modules/inherit.wdl).

## Ошибки знают свой файл

С импортом файлов выполняется много, и место в исходнике само по себе ничего не значит:
одно и то же смещение указывает в каждом файле на своё. Поэтому функция и класс
запоминают не только замыкание, но и **юнит** — файл, где они написаны. Ошибка
в теле функции модуля, вызванной из главного скрипта, показывает строку модуля:

```
lib/faulty.wdl:4:20: ошибка: деление на ноль
  4 | def half(value) => value / 0
    |                    ^^^^^^^^^
```

Ошибки разбора модуля собираются его собственной диагностикой и показываются целиком —
внутри сообщения на строке `import`, потому что именно она попросила этот файл.

## Наследование и трейты через файлы

Класс из модуля годится в родители, трейт — в примеси, обеими записями:

```wdl
import lib.shapes
import lib.shapes as s

class Circle(radius) : Shape("круг") { def area() => 3 * radius * radius }
class Square(side) : s.Shape("квадрат") with s.Countable { ... }
```

`s.Shape` здесь — обычное обращение к имени модуля, то же самое, что `s.area`. И это
не аналогия, а буквально оно: в заголовке класса стоит **выражение**, а не имя с точкой,
поэтому цепочка может быть любой длины и с любыми звеньями.

```wdl
import lib.re as r

class Circle : r.s.Shape("круг")            // модуль модуля — обычное дело
class Square : r.classes["Shape"]("квадрат") // класс из реестра модуля
```

Модуль у модуля как раз **бывает**: `import base as s` внутри файла кладёт значение-модуль
в его же члены, и наружу оно уходит вместе с остальными именами. Пока в заголовке стояло
имя ровно с одной точкой, до такого класса нельзя было дотянуться, хотя вызвать его
фабрику — можно. Подробности правила — в [классах](classes.md#ссылка-на-родителя--выражение).

**Тип из модуля виден только ниже своего `import`.** Отдельного правила для этого
не писалось: имя класса — такое же имя, как любое другое, и ищется оно там же,
в области видимости. Выше `import` его в ней просто нет:

```wdl
class Early : Shape("рано")    // ошибка: неизвестный класс 'Shape'
import lib.shapes
class Late : Shape("вовремя")  // а так — можно
```

Порядок здесь важен, в отличие от своих классов: `class Circle : Shape` может стоять
выше самого `Shape`, если оба объявлены в этом файле. Разница не в прихоти, а в том,
что импорт **выполняется**: выше него модуля ещё нет ни в каком смысле. Заодно из этого
правила выходит, что модулю незачем выполняться раньше своей инструкции — порядок
выполнения скрипта не меняется совсем.

Правило работает в любой области, включая тело функции:

```wdl
def describe() {
    import lib.shapes
    class Dot : Shape("точка")
    return new Dot().text();
}
// снаружи нет ни Shape, ни Dot
```

Никакого особого правила для таких классов при этом не нужно: **объявление существует
со своей строки** — и своё, и с родителем из модуля, и с родителем-выражением. Раньше
здесь было исключение, потому что обычные объявления расставлялись до первой инструкции;
теперь расставлять нечего, и правило осталось одно
([классы](classes.md#родитель-объявляется-выше-потомка)).

Проверки, которые язык делает при объявлении класса, работают через файлы без изменений
— невыполненное требование трейта, число аргументов родителю, «это трейт, а не класс», —
но срабатывают там же, где объявлен класс: на его строке ([классы](classes.md)).
До создания экземпляра ошибка не откладывается никогда, поэтому загруженный модуль
всегда проверен целиком: его классы объявлены на верхнем уровне, а значит, к концу
`import` они уже связаны.

Два ограничения:

* **Развёрнутый импорт не перекрывает свой тип молча.** Если модуль приносит `Shape`,
  а `class Shape` объявлен в этой же области, это ошибка с советом использовать
  `import ... as`. Два разных класса под одним именем — выше и ниже одной строки —
  худшее, что можно предложить читателю: по имени уже не понять, чей экземпляр
  создаётся и что ответит `is`. Затенить класс из внешней области импорт при этом
  вправе — как и `def` или `const` на том же месте. Классы прелюдии (`Exception`,
  `ValueError`, …) и [дескрипторы типов](types.md#проверка-типа) (`Number`,
  `String`, …) — та же по духу внешняя область: они лежат в корневой, а не в области
  файла, поэтому безымянный `import` на верхнем уровне скрипта их так же тихо
  затеняет, как и любое внешнее имя. Совет тот же — `import ... as`, — если модуль
  приносит имя, которое должно остаться именно дескриптором или прелюдией.
* **Наследоваться от модуля, который ещё выполняется, нельзя.** Круг в импортах
  останавливает скрипт с цепочкой в сообщении, и наследование тут ничем не отличается
  от обращения к функции: значения, которого ещё нет, не получить.

## Чего пока нет

* **Выбирать отдельные имена** (`import lib.math as {PI, add}`) нельзя: есть либо
  всё, либо ничего. Встроенным модулям это нужнее, чем файлам, но решаться должно
  для обоих сразу — это фича языка, а не вида модуля.
* **Наследоваться от класса встроенного модуля** нельзя: `class My : http.Response`
  даёт ошибку. Реализовать «интерфейс» такого модуля тоже пока нечем — трейтов
  на Java нет. Обе задачи описаны в [Нативные модули.md](../Нативные%20модули.md).
