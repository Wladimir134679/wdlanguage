# Метрики: время стадий

Сколько заняли лексер, парсер, выполнение и закрытие запуска. Включается флагом
консоли или одной строкой при сборке движка; отчёт можно напечатать, а можно
разобрать геттерами.

```bash
wdl --metrics examples/modules/plain.wdl
```

```
PI = 3.14159
площадь круга радиуса 2: 12.56636
точка (3, 4), длина 5.0
── метрики ──────────────────────────────
  лексер            2,3 мс
  парсер           29,5 мс
  выполнение       11,9 мс   в т.ч. модули 2,0 мс
  модули: разбор    1,4 мс   1 файл
  закрытие          0,0 мс
── сумма замеров 47,3 мс · по часам 106,6 мс
```

Таблица идёт в поток ошибок, а не в вывод скрипта: то, что напечатал скрипт, — это
данные, и `wdl script.wdl > out.txt` не должен получить в файл ещё и её.

## Что меряется

Четыре стадии — ровно те, из которых состоит [конвейер](overview.md#как-это-устроено),
плюс закрытие запуска.

| Стадия | Что засчитывается |
|---|---|
| `LEX` | текст → токены |
| `PARSE` | токены → дерево |
| `EXECUTE` | выполнение файла целиком — главного скрипта или модуля |
| `SHUTDOWN` | остановка потоков скрипта и закрытие библиотек |

Закрытие — отдельная стадия не для симметрии: оно бывает основным временем запуска.
`sys.gui` в своём `close()` ждёт, пока пользователь закроет окна, и всё это время
работают обработчики кнопок.

У каждого замера есть **над чем** — путь файла или ключ модуля — и признак «это
модуль». Поэтому в таблице разбор модулей отделён от разбора главного файла, а время
их выполнения показано строкой «в т.ч. модули».

**Что не меряется: отдельные вызовы функций.** `EXECUTE` засчитывается на верхнем
уровне файла, а не на каждом входе в скрипт — вызов функции скрипта из приложения тоже
вход, и считать его стадией конвейера значило бы складывать несравнимое. «Какая функция
самая горячая» — вопрос к профилировщику, у него другая цена и другой способ включения.

## Почему сумма не равна времени по часам

Два разных числа в последней строке — не небрежность, а две настоящие причины.

**Потоки.** Внутри запуска их [сколько угодно](threads.md), и два `EXECUTE` могут идти
одновременно: сумма их времён больше прошедшего. Когда замеры пришли из разных потоков,
таблица дописывает `· потоков N` — чтобы разница не выглядела ошибкой измерения.

**Вложенность.** `import` выполняется внутри `EXECUTE` главного файла, поэтому время
модуля входит во время скрипта и в общем «итого» посчиталось бы дважды.

Одно число вместо двух врало бы ровно на многопоточном скрипте с модулями, то есть там,
где метрики и нужны.

## Строка на каждую стадию

Когда запуск длинный, ждать итога незачем — `--metrics-each` печатает стадию сразу,
как только она закончилась, и вдобавок даёт обычную таблицу в конце:

```bash
wdl --metrics-each examples/threads.wdl
```

```
  · лексер examples\threads.wdl — 3,1 мс
  · парсер examples\threads.wdl — 39,7 мс
поток worker-1 запущен, работает: true
...
  · выполнение examples\threads.wdl — 454,3 мс
  · закрытие examples\threads.wdl — 0,3 мс
── метрики ──────────────────────────────
  лексер         3,1 мс
  парсер        39,7 мс
  выполнение   454,3 мс
  закрытие       0,3 мс
── сумма замеров 497,3 мс · по часам 564,0 мс
```

Так видно, какой именно модуль тормозит, ещё до того, как скрипт закончится.

## Из приложения

Метрики — такая же зависимость, как вывод: приёмник задаёт хозяин запуска, движок
сам ничего не считает.

```java
WdlEngine engine = WdlEngine.builder()
        .stdlib(Stdlib.STANDARD)
        .output(Output.standard())
        .metrics(true)                  // считать время стадий
        .build();

WdlScript script = engine.compile(Path.of("handler.wdl"));
System.out.println(script.metrics().total(Stage.PARSE));   // сколько занял разбор

try (WdlInstance instance = script.instance()) {
    instance.execute();
    System.err.print(instance.metrics().render());
}
```

Разбор делается один раз, а запусков может быть много — поэтому его время живёт
в `WdlScript`. Экземпляр эти замеры **втягивает** в свой отчёт: `instance.metrics()`
отвечает за всё, что со скриптом произошло, включая разбор, а складывать два числа
руками не приходится.

Логирование каждой стадии — тот же метод со слушателем вместо флага:

```java
WdlEngine engine = WdlEngine.builder()
        .metrics(measurement -> log.info("{} {} — {} мкс", measurement.stage().title(),
                measurement.subject(), measurement.durationNanos() / 1000))
        .build();
```

Слушателя зовут в том потоке, где шла стадия, и сразу по её завершении — ждать конца
запуска не нужно. Долгой работы в нём делать не стоит по той же причине.

### Что можно спросить у отчёта

`MetricsReport` — только на чтение; писать в него умеет `Metrics`, и это разные права.

| Метод | Ответ |
|---|---|
| `all()` | все замеры в порядке завершения |
| `byStage()` | сумма по каждой стадии |
| `total(stage)` / `total(stage, module)` | сумма стадии целиком или отдельно по модулям |
| `count(stage)` / `count(stage, module)` | сколько раз стадия отработала |
| `sum()` | сумма всех замеров |
| `wall()` | время по часам — от начала запуска до `close()` |
| `threads()` | сколько разных потоков успело что-то намерить |
| `render()` | готовая таблица для человека |

Один замер (`Measurement`) несёт стадию, `subject`, признак модуля, начало,
длительность и имя потока. По началу и длительности видно, какой замер вложен
в какой: `module.insideOf(script)`.

## Сколько это стоит, когда выключено

Ноль. `Metrics.off()` — один объект на процесс, он же и заглушка замера: `begin`
возвращает себя, `close()` пуст. Ни аллокации, ни обращения к часам на выключенном
пути — поэтому проверять «а включены ли метрики» в вызывающем коде не нужно.

Это то же правило, что у вывода: движок, встроенный в чужое приложение, не платит
за то, чего не просили, и не печатает никуда по умолчанию.

## Как это устроено внутри

**Стадию меряет тот, кто её запускает, а не она сама.** `Lexer.tokenize`
и `Parser.parseProgram` о метриках не знают вовсе — их время целиком видно снаружи
одним охватом. Исключение одно и вынужденное: разбор и выполнение модуля случаются
внутри движка в ответ на `import`, снаружи туда не дотянуться, поэтому приёмник
передаётся в `ModuleUnits` и в контекст запуска.

Накопитель принадлежит запуску, а не движку: движок — это
[рецепт](embedding.md), а замеры — состояние, и одного на всех у них быть не может.

Замер закрывается из `finally`, а не `try`-с-ресурсами: тело такого `try` к самой
переменной не обращается, а сборка идёт с `-Xlint:all`, где это законное предупреждение
о забытом ресурсе. Из `finally` — ещё и затем, чтобы время стадии, которая упала,
не пропало: у скрипта, свалившегося на середине, отчёт всё равно есть.
