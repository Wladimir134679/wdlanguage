# Потоки

Скрипт на wdl может считать в нескольких потоках одновременно — по-настоящему, поверх
общего состояния. Всё, что для этого нужно, это модуль `sys.thread` и одно ключевое
слово `synchronized`. Готовые примеры целиком:
[`examples/threads.wdl`](../examples/threads.wdl) и
[`examples/threads_pool.wdl`](../examples/threads_pool.wdl).

```wdl
import sys.thread as th

worker = th.spawn("worker-1", def () => heavy(data))
println(worker.join())
```

## Обещание языка: одно обращение атомарно

Это вся модель памяти wdl, и она умещается в две строки.

> **Одна операция доступа — атомарна и видима всем потокам.** Чтение и запись
> переменной, поля объекта, элемента массива не могут увидеть «половину» значения
> и не могут потеряться.
>
> **Выражение — не атомарно.** `count = count + 1`, `t[k] += 1`, «проверил и положил»
> из двух потоков теряют обновления.

Почему именно так. Гарантия сильнее, чем в C: там гонка по хеш-таблице — это не «другое
значение», а испорченная структура, потерянные элементы при перестройке и, в худшем
случае, зацикливание чтения. Такое автор скрипта отладить не может в принципе, и движок
обязан этого не допускать сам: области видимости, объекты, массивы и реестр модулей
внутри конкурентны.

Гарантия слабее, чем транзакция: движок не знает, где у автора кончается одна логическая
операция, и делать атомарным каждое выражение значило бы держать глобальный замок —
то есть не иметь параллельности вовсе. Границу проводит тот, кто её видит:

```wdl
count = 0

def bump() {
    count = count + 1        // ← два обращения: прочитать и записать
}
```

Два потока читают одно и то же `count`, оба пишут одно и то же — один инкремент пропал.
Ошибки при этом нет, и в маленьком тесте она не проявится: потерянное обновление
случается раз в тысячу вызовов. Средств склеить несколько обращений в одно ровно три:
`synchronized` на функции, `th.lock()` и `th.counter()`.

### Обращение к свойству под обещание не подпадает

[Свойство](classes.md#свойства) выглядит как поле, но за именем стоит вызов, а вызов
целиком не атомарен. Значит, обещание про ячейку на него не распространяется:

```wdl
class Counter() {
    property value = 0 {
        def get() => field
        def set(v) { field = v }
    }
}

c = new Counter()
c.value += 1        // ← getter, сложение, setter: три шага, а не один
```

Хуже того, теряться может и одиночное обращение: тело аксессора — обычный код,
и что оно делает с общим состоянием, знает только его автор. Поэтому `synchronized`
у аксессора и запрещён — он создавал бы видимость защиты там, где защищать надо
не одно обращение, а всю логическую операцию. Границу здесь, как и везде, проводит
тот, кто её видит: `th.lock()` вокруг обращения либо `synchronized`-метод, внутри
которого свойство читают и пишут.

## `synchronized`

Модификатор перед `def`. Вызовы такой функции не идут одновременно.

```wdl
count = 0

synchronized def bump() {
    count = count + 1        // теперь атомарно относительно других вызовов bump
}
```

Работает у объявления, у метода класса, у фабрики и у анонимной функции:

```wdl
handler = synchronized def (event) { log = log + [event] }
```

### Замок принадлежит значению-функции

Не имени. Замыкание, созданное дважды, даёт два значения и два замка:

```wdl
def makeCounter() {
    total = 0
    return synchronized def () {
        total = total + 1
        return total;
    };
}

first = makeCounter()
second = makeCounter()       // своё 'total' — и свой замок

println(first(), " ", first(), " ", second())    // 1 2 1
```

Это верно по смыслу: у них разное захваченное состояние, и защищать его одним замком
было бы неправдой — два независимых счётчика ждали бы друг друга без всякой причины.

### У метода класса замок — экземпляр

```wdl
class Basket(items) {

    synchronized def add(item) {
        items = items + [item]
    }

    synchronized def clear() {
        items = []
    }
}
```

Метод защищает поля **своего** объекта, поэтому:

* два `synchronized`-метода одной корзины взаимно исключаются — `add` и `clear`
  одновременно не идут, чего обычно и хотят;
* две разные корзины друг другу не мешают вовсе.

Замок на методе (а не на объекте) дал бы обратное: все корзины в приложении стояли бы
в очереди к `add`, а `add` и `clear` одной корзины шли бы одновременно. Это почти всегда
не то, что нужно.

### Реентрантность

`synchronized`-функция вправе позвать себя рекурсивно и позвать соседний
`synchronized`-метод того же объекта — замок уже её, и второй раз он ничего не стоит.

### Прерывание сильнее замка

Ожидание входа в `synchronized`-функцию прерываемо. Иначе `t.interrupt()` не снял бы
поток, застрявший на замке, и остановка зациклившегося скрипта перестала бы работать
именно тогда, когда она нужнее всего.

### Дедлок языком не лечится

Две `synchronized`-функции, захватывающие объекты в обратном порядке, встанут — это
ответственность автора скрипта, ровно как в любом языке с замками. Что помогает:
`th.lock().tryRun(fn, ms)`, `t.join(ms)` и диагностика при закрытии запуска —
незавершившиеся потоки называются по именам.

## `sys.thread`

### Потоки

```wdl
import sys.thread as th

t = th.spawn(def () => heavy())              // запустить
t = th.spawn("worker-1", def () => heavy())  // с именем: оно попадёт в диагностику

t.join()             // дождаться и вернуть результат функции
t.join(2000)         // с таймаутом; null, если не дождались
t.result             // результат или null
t.error              // текст ошибки или null — она не теряется
t.alive              // работает ли прямо сейчас
t.name
t.id
t.interrupt()        // кооперативная остановка

th.current()         // текущий поток: {name, id}
th.sleep(250)        // засыпание, прерываемое
th.yield()
```

Три вещи, которые стоит знать про `spawn`:

* **Поток — демон.** Он не держит процесс живым: мод не вправе не дать игре закрыться,
  а скрипт настроек — серверу. Дождаться работы — явное дело автора, и делается оно
  `t.join()`. Признак демона поэтому и не меняется: `spawn` отдаёт уже запущенный поток,
  а после старта его менять поздно.
* **Ошибка потока не теряется.** Она ложится в `t.error`, а если поток никто не ждёт —
  печатается в вывод скрипта с именем потока. Молча исчезнувшая работа хуже громкой
  строки.
* **Прерывание — не ошибка скрипта.** `t.interrupt()` останавливает выполнение, и поймать
  это `catch (e)` нельзя: иначе `while (true) { try { ... } catch (e) {} }` съел бы
  собственную остановку.

### Пул и обещания

```wdl
use (pool = th.pool(4)) {                    // без аргумента — по числу процессоров
    results = pool.map(items, def (item) => handle(item))   // ждёт всех, порядок сохранён

    f = pool.submit(def () => compute(x))
    f.get()          // ждать до конца
    f.get(1000)      // с таймаутом; null, если не успел
    f.done
    f.error
    f.cancel()
}
```

`Pool` подмешивает `Closeable`, поэтому работает с [`use` и `defer`](errors.md): пул
держит живые потоки, и забыть его закрыть — значит утечь. Даже забытый скриптом, он
закроется вместе с запуском, но полагаться на это не стоит: до конца запуска потоки
будут жить.

Ошибка задачи остаётся **ошибкой языка**: `f.get()` бросает тот же `IndexError`
с тем же местом, что и прямой вызов, и ловится обычным `catch (e is IndexError)`.

`f.result` здесь нет намеренно, хотя у потока `t.result` есть: за результатом задачи
надо ждать, и поле, молча отдающее `null`, было бы ловушкой. Метод честно говорит,
что это ожидание.

### Синхронизация

```wdl
lock = th.lock()
lock.run(def () { shared = shared + [x] })   // отдаёт то, что вернула функция
lock.tryRun(def () { ... }, 100)             // null, если замок занят

c = th.counter(0)
c.inc(); c.dec(); c.add(5); c.set(0)
c.get()
c.compareAndSet(5, 6)                        // «проверил и положил» одним шагом

ch = th.channel(100)                         // без аргумента — без ограничения
ch.send(v)                                   // false, если канал закрыт
ch.take()                                    // null, если канал закрыт и пуст
ch.poll(500)                                 // null, если за 500 мс ничего не пришло
ch.size(); ch.close()

latch = th.latch(3)
latch.countDown()
latch.await(5000)                            // дождался ли; await() — без предела
latch.left()
```

У замка только `run` и `tryRun`, пары `lock()`/`unlock()` нет намеренно: забытый
`unlock` — это не «упало», а «встало намертво, и непонятно где». Здесь освобождение
написано внутри и забыть его нельзя.

Счётчик отдельно от замка не из экономии строк: `c.inc()` атомарен без единого захвата,
а `lock.run(def () { n = n + 1 })` — это захват, вызов функции и выход из области.
На горячем счётчике разница заметная.

`ch.close()` **будит ждущих**. Без этого консюмер, стоящий на пустом канале, не узнал
бы, что продюсер закончил, и висел бы вечно; поэтому цикл
`while ((item = ch.take()) != null)` заканчивается сам собой.

## Что чем закрывается

| Задача | Средство |
|---|---|
| Долгая работа по кнопке без заморозки окна | `th.spawn` в обработчике + `gui.later(fn)` для возврата в интерфейс |
| Параллельная обработка списка | `pool.map` |
| Периодическая фоновая задача | `th.spawn` + `th.sleep` в цикле, `t.interrupt()` на выходе |
| Продюсер/консюмер, конвейер | `th.channel` |
| Общий кэш, счётчик, аккумулятор | `synchronized def`, `th.counter`, `th.lock` |
| Запрос с таймаутом и отменой | `pool.submit` + `f.get(ms)` + `f.cancel()` |
| Чат-сервер: клиенты в своих потоках | `server.onConnection` + `client.onLine` + `synchronized def broadcast` |

## Интерфейс: только `gui.later` и `gui.sync`

Swing не потокобезопасен, и трогать окно из потока скрипта нельзя:

```wdl
th.spawn(def () {
    data = load()                    // долго — и потому в своём потоке
    gui.later(def () {
        label.text = data            // ← а это уже в потоке интерфейса
    })
})
```

`gui.later(fn)` ставит действие в очередь интерфейса и не ждёт; `gui.sync(fn)` ждёт —
он нужен там, где у интерфейса надо что-то **спросить**. Раньше это было незаметно
только потому, что внутри запуска работал один поток; теперь мост обязателен.

## Приложению, встраивающему движок

Экземпляр `WdlInstance` можно звать из любого числа потоков одновременно — вызовы больше
не выстраиваются в очередь. Что из этого следует и как закрывать запуск с живыми
потоками, описано во [встраивании](embedding.md#потоки-и-вызовы-из-приложения).

Скрипту, писавшемуся тогда, когда движок обещал «внутри запуска один поток», нужна
одна правка: `synchronized` перед `def` там, где несколько обращений обязаны быть
одним целым. Режима «вернуть прежний замок» нет — почему, разобрано ниже.

## Чего здесь нет

* **`async`/`await` и промисов.** Другая модель и другой планировщик; потоки её
  не требуют и ей не мешают.
* **Автоматического поиска дедлоков и гонок.** Дорого; вместо них — таймауты
  (`join(ms)`, `tryRun(fn, ms)`, `get(ms)`) и диагностика незавершившихся потоков
  при закрытии запуска.
* **Ограничений сверх квоты запуска.** Сколько потоков скрипту можно, задаёт
  `Limits.maxThreads` — и считает он оба способа их завести, `th.spawn` и `th.pool`
  (пул занимает своё место целиком, пока не закрыт). Отказ приходит обычной ошибкой,
  которую можно поймать: подождать и попробовать снова — законное поведение. Ровно
  благодаря этой квоте `sys.thread` и входит теперь в набор `SAFE`; подробно —
  в [лимитах](limits.md).
* **Иммутабельных значений и глубокой заморозки объекта.** Полезно для передачи между
  потоками без замков, но это отдельное решение о типах.
* **Режима «вернуть глобальный замок».** Такой был — переходный флаг на сборщике
  движка для скриптов, писавшихся до потоков. Оказалось, что он несовместим с
  `sys.thread`: главный поток входит в скрипт и держит замок, порождённый поток встаёт
  на нём, `t.join()` ждёт вечно — то есть простейший `spawn` + `join` вешался намертво.
  Совместимость с невыпущенной версией не стоит мины под самой заметной возможностью
  языка, поэтому семантика здесь одна.
