# Инструментам: позиции, токены, обход дерева, имена

Всё, на что опирается редактор — подсветка, переход к объявлению, дополнение,
форматтер, будущий LSP-сервер. Документ отвечает на пять вопросов: в каких единицах
считаются позиции, как получить поток токенов с комментариями, как пройти по дереву,
что про дерево гарантировано и как узнать, где объявлено имя.

Само выполнение скрипта ничего отсюда не использует: путь `Source → Lexer → Parser
→ Interpreter` остался прежним, а всё описанное здесь — второй режим лексера,
дополнительные поля узлов и чистые функции обхода.

## Позиции

**Смещение — индекс в `String`, то есть единица UTF-16.** Не байт и не кодовая точка:
эмодзи занимает две единицы, и `span.length()` у него равна двум. Так же считает
документ IntelliJ и позиция LSP по умолчанию, поэтому перевод в их координаты
не требует пересчёта.

**Интервал полуоткрыт:** `Span(start, end)` — это `[start, end)`, `end` указывает
за последний символ. Пустой интервал (`Span.point(offset)`) — законный: его ставит
парсер на месте недописанного.

**Строки и столбцы нумеруются с единицы** (`Position`). Нумерация с нуля — дело
адаптера: LSP считает с нуля, ядро о нём не знает.

Перевод обратим в обе стороны:

```java
Source source = Source.ofString("count = 1\nname = \"мир\"");
Position position = source.positionOf(10);       // 2:1
int offset = source.offsetOf(position);          // 10
int caret = source.offsetOf(2, 5);               // курсор внутри второй строки
```

`offsetOf` принимает и столбец за последним символом строки — там стоит курсор,
дописывающий строку, и именно эту позицию редактор присылает чаще всего.

Строку заканчивает `\n`; `\r` перед ним — обычный символ текста: он входит
в позиции, но `lineText` его не отдаёт. Маркер кодировки (BOM) — тоже обычный символ
позиции 0; пропускает его лексер, а не `Source`, поэтому **редактор обязан лексить
текст своего документа, а не байты файла** — иначе позиции разъедутся на единицу.

## Два режима лексера

Обычный разбор пробелы и комментарии выбрасывает: грамматике они не нужны никогда.
Редактору нужны все — подсветка обязана покрыть документ целиком, форматтер не вправе
съесть комментарии, подсказка по наведению берёт из них документацию.

```java
List<Token> forParser = Lexer.tokenize(source, diagnostics);                        // RUNTIME
List<Token> forEditor = Lexer.tokenize(source, diagnostics, LexerMode.LOSSLESS);    // с тривией
```

В режиме `LOSSLESS` в потоке появляются `WHITESPACE`, `LINE_COMMENT`, `BLOCK_COMMENT`
и `BAD_CHARACTER` — все с `type().isTrivia() == true`. Гарантия режима: **интервалы
идут встык от нуля до конца документа**, без дыр и пересечений, последним стоит пустой
`EOF`. Значимые токены в обоих режимах одни и те же — это проверяется тестом,
а не обещанием.

Две частности, о которых стоит знать:

* **Текст токена-тривии пуст.** Содержимое читается из `Source` по интервалу — то же
  правило, что у строкового литерала, где `text()` хранит уже развёрнутое значение.
* **`BAD_CHARACTER` бывает только в `LOSSLESS`.** В обычном режиме неизвестный символ,
  как и раньше, уходит только в `Diagnostics`: попади он в поток, парсер выдал бы
  вторую ошибку на ту же беду. Подсветке же токен необходим — до диагностики она
  не дотягивается.

Посмотреть глазами:

```bash
wdl --tokens --trivia examples/hello.wdl
```

## Обход дерева

Состав детей каждого узла знает одно место — `ru.wds.wdl.ast.Nodes`. Ходить
по дереву своим `switch` не надо: он разойдётся с деревом на первом же новом виде узла.

```java
Program program = Parser.parseProgram(tokens, diagnostics);

List<Node> children = Nodes.children(program);          // прямые дети, слева направо
Nodes.walk(program, node -> { /* весь обход сверху вниз */ });

Node under = Nodes.deepestAt(program, offset);          // узел под смещением
List<Node> path = Nodes.pathAt(program, offset);        // путь от корня до него
Node editing = Nodes.deepestAtCaret(program, offset);   // узел, который правит курсор
Node declaration = Nodes.declarationNameAt(program, offset);  // курсор в имени объявления
Span name = Nodes.nameSpanOf(declaration);              // место этого имени
```

Разница между `deepestAt` и `deepestAtCaret` — в границе. Первый работает строго
внутри интервала (`end` не входит), второй помнит, что курсор стоит **между** символами:
позиция сразу за концом узла — это всё ещё он. Для дополнения нужен второй: у `obj.`
в конце строки справа от курсора нет уже ничего.

### Фрагменты — тоже узлы

`Node` состоит из трёх ветвей: `Expr` (даёт значение), `Stmt` (выполняется ради
действия) и `Fragment` — часть узла со своим местом в тексте: параметр, аргумент,
запись объекта, обработчик `catch`, привязка `use`, ветка `match`, свойство, аксессор,
требование трейта, ссылка на родителя. До появления `Fragment` половина кусков дерева
узлами не была, и каждый обход обязан был знать их в лицо.

Разборы по `Expr` и `Stmt` от этого не меняются: полнота `switch` проверяется
по `permits` своей иерархии, а фрагмент — другая ветвь и туда не попадает.

## Что гарантировано про интервалы

Проверяется тестом по всем примерам из `examples/` **и** по корпусу нарочно
недописанного текста (`wdl-core/src/test/resources/malformed/`):

1. у каждого узла есть место в исходнике, и оно лежит внутри текста;
2. **интервал ребёнка вложен в интервал родителя**;
3. дети идут слева направо и соседи не пересекаются;
4. интервал программы доходит до конца документа.

Из этого следует правило, которому подчиняется разбор: **узел покрывает ровно то,
что парсер прочитал.** Токен съеден — интервал его; токен оставлен вызывающему
(закрывающая скобка, начало следующей инструкции) — интервал нулевой, в точке,
где чего-то не дождались. Поэтому `x = obj.` даёт `AccessExpr` с пустым `ErrorExpr`
сразу за точкой, а не с проглоченным токеном следующей строки.

Отдельная тонкость — аннотации. Блок `@{...}` пишется перед объявлением, и в интервал
объявления он входит: записи аннотаций — его дети. Но если между блоком и `def` стоит
декоратор, объявление до блока не дотягивается — иначе его интервал перепрыгнул бы
через декоратор и наехал на него; такие блоки покрывает `DecoratedStmt`, который
начинается с первого `@`. В обоих случаях правило одно: **владелец записи — тот узел,
чей интервал её накрывает.**

## Имена объявлений

У объявления два интервала: место всего объявления (`span`) и место его имени
(`nameSpan`) — то, к чему ведёт переход к объявлению и что меняет переименование.

| Объявление | Где имя |
|---|---|
| `def f()`, метод, конструктор, фабрика, аксессор | `FunctionExpr.nameSpan()` |
| параметр, включая параметр-дырку | `FunctionExpr.Param.nameSpan()` |
| `*rest`, `**named` | `FunctionExpr.Rest.span()` |
| `class`, `trait` | `nameSpan()` |
| требование трейта | `TraitDeclStmt.Requirement.nameSpan()` |
| `const`, свойство, привязка `use`, переменная `catch` | `nameSpan()` |
| `import ... as` | `aliasSpan()`, иначе `pathSpan()` |

У анонимной функции `nameSpan` — `Span.NONE`, даже когда имя подставлено от переменной
(`handler = def(e) => e`): написано оно у переменной, туда и должен вести переход.
Одна таблица на все виды — `Nodes.nameSpanOf(Node)`.

## Диагностика с кодом

Текст сообщения пишется для человека и меняется свободно; редактору нужно устойчивое
имя проблемы — по нему гасят проверку, вешают быструю правку, настраивают строгость.
Для этого у `Diagnostic` есть `code` (`DiagnosticCode`).

```java
diagnostics.error(span, DiagnosticCode.UNKNOWN_CHARACTER, "неизвестный символ " + описание);
```

Код есть не у всех сообщений: `DiagnosticCode.NONE` — значение по умолчанию, и оно
ведёт себя ровно так, как вело до появления кодов. Новые коды заводятся тогда, когда
у проблемы появляется потребитель, а не заранее.

## Перечисление области

`Environment` умеет назвать свои имена: `namesHere()` — заведённые в этой самой
области, `names()` — все видимые отсюда, с учётом внешних. Нужно это двоим, и оба
снаружи выполнения: панели переменных отладчика и дополнению в REPL. Окружение,
написанное приложением, отвечает пустым множеством — реализация по умолчанию.

## Анализ имён

Всё выше — про текст и дерево. Ответ на вопрос «что здесь за имя и где оно объявлено»
даёт отдельный слой: `ru.wds.wdl.tools.analysis`, точка входа — `FileAnalysis`.

```java
FileAnalysis analysis = FileAnalysis.of(source);

analysis.symbols();                 // все объявления файла — структура файла
analysis.visibleAt(offset);         // что видно в этой точке — дополнение
analysis.resolve(offset);           // объявление под курсором — переход к объявлению
analysis.usages(symbol);            // где ещё встречается — поиск и переименование
analysis.scopeAt(offset);           // область: файл, тело функции, блок, catch...
analysis.comments().before(span);   // документация над объявлением — подсказка
```

**Правило видимости повторяет язык дословно, обе его половины.** Имя существует
с той строки, где его завели, — поэтому на верхнем уровне видно только объявленное
выше. Но тело функции выполняется позже, и оттуда видно всё, включая объявленное
ниже по файлу: на этом стоят рекурсия и взаимная рекурсия. Признак, который всё
решает, один — пересечена ли по дороге наружу **граница вызова** (тело функции
или аксессора).

Области — те же, что заводит выполнение, и ни одной лишней: файл, тело функции,
блок `{}`, заголовок `for`, шаг `for ... in`, `use`, `catch`, тело класса, трейта
и расширения, тело аксессора (там существует `field`). Тело `if` без скобок области
не создаёт — там нет блока.

**Анализ не выполняет пользовательский код** — ни ради типа, ни ради значения
по умолчанию, ни ради `import`, — и **не добавляет диагностики**. Имя, которое
не нашлось, это не ошибка: оно может быть встроенным, прийти из библиотеки или
от приложения. Проверка «имя не определено» без каталога внешних имён дала бы
ложную ошибку на каждом `println`.

### Чего слой пока не знает

* **Встроенных имён и `std`/`sys.*`** — каталог внешних имён идёт следующим этапом.
* **Типов**: `obj.` после точки не дополняется, обращение по ключу употреблением
  имени не считается — без типа получателя неизвестно, куда оно ведёт.
* **Других файлов**: `import lib.math as m` заводит символ-псевдоним, и на этом всё;
  развёрнутый `import lib.math` приносит имена другого файла, а их узнает анализ
  нескольких файлов.
* **Членов, доставшихся от родителя и трейтов**: они ищутся по таблице членов
  экземпляра, а не по областям. Свои члены класса анализ видит, включая поля,
  заведённые через `this.name = ...`.
